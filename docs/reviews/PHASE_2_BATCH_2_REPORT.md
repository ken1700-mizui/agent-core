## 2. Sandbox の残存の問題（S-R01〜S-R05）

- **S-R01（推奨の停止の設計）：** 案 B。P1・P2 の寿命に依存しない、小さな期限の監督のプロセス（P3、別の OS 利用者、systemd の `Restart=always` と `WatchdogSec`）。
  - P2 は開始の**前に** P3 に期限を登録する。P3 の確認がなければ開始しない（`DEADLINE_UNAVAILABLE`）。
  - P3 は期限で、登録された cgroup のプロセスだけに KILL を送る。Docker API には届かない。承認・Permit・費用・Journal の経路を持たない。
  - 期限は boot ID と CLOCK_BOOTTIME で持つ。戻せなければ直ちに止める。
  - 受入の条件の案は6項目（同じ文書）。新しい OS の権限が要るので、**実装は別の承認**。案 A（systemd の `RuntimeMaxSec`）は未検証。
- **S-R02：** 受け付けたときに boot ID と CLOCK_BOOTTIME を記録する。
  - 壁時計を1日戻しても期限は延びない（試験）。
  - 違う boot、時計が読めない：直ちに止める。boot の時計がない：開始の前に拒否する。
  - 止められないもの：P1 の側は OUTCOME_UNKNOWN で保留のまま。
- **S-R03：** 次の場合、許可を拒否する。
  - 古い epoch、違う監視、違う Broker、未来の時刻、期限切れ。
  - 書き込みの失敗、破損、MAC の不一致。
  - ファイルが通常のファイルでない、自分の所有でない、0600 でない。

  この確認は Permit の発行（意図を書く前）と Sandbox の開始（P2 に頼む前）に入れた。書き込みは原子的で、ファイルとディレクトリを同期する。
- **S-R04：** P1 から P2 への入力と、作業ツリーへの反映は未実装。設計は WP-08 の経路を通す。SG-1 の条件に入れた。
- **S-R05：** 次の項目は、試験の成功を安全上の合格と扱わない。
  - 項目 6：同じ boot の中でだけ満たす。
  - 項目 B：中のコードが監督を止められることを確認しただけ。
  - 項目 E：文面は満たすが、P2 が止まっている間はコンテナが止まらない。

  時間の上限（3、8、H、A）は、P1 と P2 が両方止まると働かない。

- 対応：この場面に、既存の `privileged`（CHOWN）の印を付けた（`32f8bff`）。root で実行し、成功した。飛ばしてはいない。
