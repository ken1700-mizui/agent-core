## 0. 基本方針

1. **評価する対象：** Agent Core は、モデルを学習し直す仕組みではない。評価するのは、**同じモデル**に Runtime・Context・Memory・Planning・Tool・Recovery などの仕組みを加えたときに、どれだけ良くなるか。
2. **1つの総合点だけで判定しない：** 成功率、品質、時間、トークン、費用、人間の介入、障害からの復旧、安全性を、それぞれ分けて測る。
3. **事前に登録する：** 評価の条件、指標、分析の方法、採用の基準は、実験を始める前に固定する。結果を見てから変えることはしない。
4. **公平に比べる：** 変えるのは、評価したい機能だけ。わざと弱い比較の相手は作らない。
5. **安全は、取引の材料にしない：** Safety Gate を通らない構成は、性能がどれだけ高くても採用しない。
6. **分からないときは、分からないと言う：** 結論が出なければ `INCONCLUSIVE` とする。

## 1. 評価の目的と、測る項目（D01）

| 観点 | 主な指標 | 定義 |
|---|---|---|
| タスクの成功 | 成功率 | 事前に定めた成功条件（7章）を満たした割合。タスクを単位として集計する（8.1） |
| 成果物の品質 | 品質の指標 | 隠しテスト以外の項目（後退していないか、静的解析、差分の大きさ、規約に合っているか、評価の基準に照らした点数）。成功率とは別に集計する |
| 実行の時間 | 経過時間 | Run の開始から終了まで。p50 と p95 も出す |
| トークンの使用量 | 種類ごとのトークン | 入力、出力、キャッシュの書き込みと読み込み、補助的な呼び出し |
| 金銭的な費用 | 費用 | 12章。照合して確定した値を主に使う |
| 人間の介入 | 回数と時間 | 承認、確認、手で直した回数と、かかった分数 |
| 障害からの復旧 | 復旧できた割合 | 障害を入れたタスクで、正しく復旧して完了した割合。設計A の不変条件の違反の件数 |
| 安全性 | 違反の件数 | Safety Gate の試験と、評価中に観測した違反（権限のない操作、送信、境界を越えたもの）。**0 件が条件** |

## 2. アーキテクチャ

```
 ┌──────────── 開発の側（dev と validation） ────────────┐   ┌────── 評価の側（holdout。C2 の10章） ──────┐
 │ Experiment Registry（事前登録、ハッシュで固定）         │   │ Eval Controller・Test Vault・Sandbox        │
 │ Task Catalog（dev と validation）                      │   │ Verifier・Signer・Aggregator                 │
 │ Benchmark Runner（dev 用）→ Agent の各構成（Sandbox）   │   │ Benchmark Runner（holdout 用）               │
 │ Evaluation Engine（採点の手配。dev 用の Verifier）      │   │                                             │
 │ Statistics Engine（登録した分析の計画を実行する）       │◀──│ 制限した報告（C2 の11.1）                    │
 │ Cost Engine（見積もり・予約・照合・報告）               │   └─────────────────────────────────────────────┘
 │ Decision Recorder（ゲートの判定、採用、取り消し）       │
 │ Results Store（試行の記録。ハッシュの連鎖）             │
 └────────────────────────────────────────────────────────┘
```

| 部品 | 役割 |
|---|---|
| Experiment Registry | 実験の仕様（13章）を、始める前に登録し、ハッシュを記録して固定する。固定した後は変えられない。変えるには、新しい実験として登録し直す |
| Task Catalog | タスクの仕様（3.1）を、版付きで管理する。dev と validation は開発の側に、holdout は評価の側にだけ置く |
| Benchmark Runner | 実験の仕様に従って、構成とタスクと試行の順番を組み、Run を実行する。順番は無作為に入れ替える（13.2） |
| Evaluation Engine | 採点を手配する。採点は、Agent 自身ではなく、Verifier（Sandbox の外）が行う（C2 の10.2） |
| Statistics Engine | 登録した分析の計画どおりに、推定と判定を行う。計画にない分析は、「探索的なもの」と印を付ける |
| Cost Engine | 費用の見積もり、予算の予約、照合、報告（10〜12章） |
| Decision Recorder | 3つのゲートの判定と、採用・不採用・取り消しを、根拠と一緒に記録する |
| Results Store | 試行と採点の記録。開発の側の分（dev と validation）と、評価の側の分（holdout）を分ける |

- Evaluation Engine と Statistics Engine は、**評価する対象の Agent からは独立**させる。Agent の構成を変えても、採点のプログラムと分析のプログラムは変わらない。
- 採点と分析のプログラムを変えるのは、オーナーが承認した、別の変更として行う（7.3・9.5）。

## 4. 比較の相手（D02）と、公平性（D03）

### 4.1 構成

| 構成 | 内容 | 判定に使うか |
|---|---|---|
| **Baseline A：Minimal Agent** | モデルの呼び出し、ツールの実行、履歴の保持（枠を超えたら古い順に切り捨てる。ただし上位の命令と安全上の制約は切り捨てない。B1 の11章）、終了の条件 | 参考と、下限の確認 |
| **Baseline B：Competent Agent** | 一般的な実用のエージェントとして妥当な構成。次を持つ。<br>- 適切なツールの設計（`rg`、範囲を指定した読み込み、編集のツール）<br>- 基本的な文脈の管理（古いツールの結果の置き換えと、切り詰め。B1 の S1・S2）<br>- 一時的な失敗の再試行<br>- 完了を報告する前にテストを実行する検証の手順 | **主な比較の相手** |
| **Baseline C：External Reference** | 既存の外部のエージェント。具体的な製品と版は、実験の前に確かめる | **参考の値だけ**。モデル、費用、内部の構成を完全にはそろえられないため、採用の判定には使わない |
| **Agent Core** | 評価する構成 | 評価の対象 |
| **Ablation** | Agent Core から、機能を1つずつ外した構成（9.5） | 機能ごとの効果の推定 |

**わざと弱い相手にしないための決まり**

- Baseline B の構成は、実験の前に独立審査者が確かめ、「妥当な実用の構成である」と記録する。
- dev の集合で調整に使える手間（試行の回数と費用）は、Baseline B と Agent Core で同じにし、その量を記録する。
- Baseline B に、Agent Core の機能の一部（記憶など）を入れるかどうかは、事前登録のときに決めて、理由を記録する。

**安全のために必須の機能は、どの構成でも外さない**

- 必須の機能：PDP と PEP、Permit、Sandbox、Gateway、SAG、予算の強制、B1 の権限の階層、ProtectedFact のうち安全上の制約と変更禁止事項。
- Baseline A と B も、この同じ安全の仕組みの上で動かす。

### 4.2 公平性の条件（D03）

**すべての構成で、そろえるもの**

- モデルとその版、推論の設定
- タスクの入力、完了の条件、作業を始めるときのファイル
- 使えるツールと操作の能力（ツールの「設計」は構成ごとに違ってよいが、できることの範囲は同じにする）
- セキュリティの制約、Sandbox、時間の上限、トークンの予算、金銭の予算
- 人間が介入する条件

**変えるのは、評価したい機能だけ。** そろえられなかった条件は、`condition_deviations` として実験の記録に残す。

**2つの比べ方を分ける**

| 比べ方 | 何を固定し、何を比べるか |
|---|---|
| 固定の予算での比較 | 予算と時間を同じにして、成功率と品質を比べる |
| 品質を達成するための費用の比較 | 成功、または事前に決めた品質の水準に達するまでの費用と時間を比べる。達しなかった試行は、**実際に使った費用の時点で打ち切られた**ものとして扱う（12.2）。上限の額を払ったことにはしない |

## 5. ベンチマークの構成（D04）

### 5.1 タスクの分類

| 軸 | 値 |
|---|---|
| 種類 | 小さなバグの修正、複数のファイルの修正、新しい機能の追加、テストの作成、リファクタリング、既存のコードの理解（質問に答える）、長時間の作業、障害からの復旧（障害を入れたもの）、あいまいな要求への対応（確認の質問をすべきもの） |
| 難易度 | S・M・L。目安は、触るファイルの数、変える行の数、必要な手順の数、熟練者が要する時間。基準は Task Catalog に記録する |
| 規模 | リポジトリの大きさ（ファイルの数、行の数）、文脈に必要な量 |
| 分野 | 最初は `coding` だけ。`research`、`web`、`sales` などを、同じ TaskSpec の形で、後から加えられるようにする |

### 5.2 最初の 20〜50 タスク

- 評価の仕組みを試すことと、予備の評価（分散と効果の大きさを見積もること。8.5）に使う。
- **統計的な検出力を保証する件数としては扱わない。**

### 5.3 タスクの出どころと、汚染

- 公開されているリポジトリや課題は、モデルがすでに学習している可能性がある。
- そのため、holdout には、非公開か、新しく作ったか、モデルの知識の時点より後のタスクを優先する。
- 出どころを `provenance` に記録する。汚染の疑いは `contamination_notes` に記録する。

## 6. 評価データの分離（D05）

### 6.1 分割

| 分割 | 用途 | 置き場所 | 開発の側に返す情報 |
|---|---|---|---|
| Dev | 開発とデバッグ | 開発のリポジトリ | 詳しく返す（タスクごとの結果、ログ、成果物） |
| Validation | 構成や機能の選択 | 開発のリポジトリ（ただし、開発の作業の中で中身を見ない運用にする） | タスクごとの結果まで。エラーの詳細は、必要なものだけ |
| Holdout | 独立した最終的な性能の評価 | **独立した非公開のリポジトリ**（D3）。開発の側の AI には接続しない | C2 の11.1 の制限した集計だけ |

### 6.2 holdout の使い方

- **holdout の結果を使って、機能を何度も調整することは禁止する。**
- 使ってよいのは、Phase 3D の採用の判定などの、事前に登録した節目だけ。
- **使う回数（候補の値。PROVISIONAL）：** holdout の**評価セットの版ごとに、実験をまたいで累積で**数える。1つの版につき、主な判定に1回、確認のための再評価に1回まで。
  - 確認のための再評価は、最初の holdout の実行の**前に**、条件を固定して事前登録しておく。結果を見てから条件を変えることはしない（V7）。
  - 使った回数と、公開した集計の量は、Experiment Registry の `holdout_usage[eval_set_version]` に記録する。
- **公開する集計（C2 の11.1）：**
  - 全体の点数と信頼区間、分類ごとの件数を出す。
  - 件数が下限に満たない分類は、まとめる。下限の候補は、分類ごとに 10 タスク以上（PROVISIONAL）。
  - タスクごとの結果と、エラーの詳細は出さない。
- **入れ替える条件：**
  - 使う回数の上限に達した。
  - 漏えいの疑いがある（開発の側の記録や記憶に、holdout のフィンガープリントが見つかった）。
  - 評価するモデルが、新しい知識の時点のものに変わった。
  - 一定の期間（候補は 1年。PROVISIONAL）が過ぎた。

### 6.3 重複、類似、既存の知識による汚染

- **重複と類似：** 分割の間で、ハッシュ、似た文章、同じ元のリポジトリとコミット、同じ課題番号を照合する。似ているものは、同じ分割にまとめる。照合は、評価の側で行い、結果だけを開発の側に知らせる。
- **既存の知識による汚染：**
  - holdout に目印の文字列（canary）を入れ、モデルの出力に現れないかを見る。
  - 公開された課題だけで作ったタスクは、参考の扱いにする。
  - 汚染を完全に確かめる方法はない（残存リスク）。

## 7. 採点（D06、C2-P06、D-R07）

### 7.1 結果の分類（タスクごとに、事前に定義する）

**タスクの結果と、安全の結果は、別々の項目として記録する**（D-R07）。

| `task_outcome` | 定義 | 成功率での扱い |
|---|---|---|
| `SUCCESS` | 成功の条件をすべて満たした | 成功。ただし、同じ試行で `safety.violations > 0` なら、失敗として数える（事前登録の規則） |
| `PARTIAL` | 部分的な成功の条件を満たした（評価の基準と点数を、事前に定義する） | 失敗。品質の指標では、部分の点数を使う |
| `FAIL` | 失敗の条件に当たった、または成功の条件を満たさなかった | 失敗 |
| `TIMEOUT` | 時間の上限を超えた | 失敗。件数を別に報告する |
| `BUDGET_EXCEEDED` | 予算を超えて止まった | 失敗。件数を別に報告する |
| `INVALID_ENV` | **評価の環境の側の**障害（7.2） | 集計から外す。件数・理由・**費用**を報告する |

| `safety` の項目 | 定義 | 扱い |
|---|---|---|
| `violations`（安全性の違反） | 安全でない効果が実際に起きた。または、安全の不変条件が破られた（C1・C2） | **0 件が Safety Gate の条件** |
| `blocked_attempts`（通常の認可の拒否） | Agent が、許されていない操作を提案し、PDP や PEP が正しく拒否した | 違反ではない。安全の副指標として数え、比較の相手より増えていないかを見る（9.2 の維持すべき指標） |

### 7.2 失敗の原因の切り分け（D-R07）

| 原因 | 例 | 分類 |
|---|---|---|
| 評価の環境の障害 | 採点のプログラムの異常終了、Runner や Sandbox のホストの障害、評価の側の Gateway の障害 | `INVALID_ENV` |
| **評価する対象の Agent が起こした障害** | Agent の異常終了、無限の繰り返し、Agent による資源の使い尽くし、ツールの誤用、自分の作業ツリーを壊した | `FAIL` か `TIMEOUT` か `BUDGET_EXCEEDED`。**`INVALID_ENV` として外さない** |
| モデルの提供元の一時的なエラー | 個別のエラーや遅延 | 運用の条件の一部として、Agent の側の結果に数える。再試行も Agent の仕事である |
| モデルの提供元の大規模な障害 | 事前に決めた条件（例：その時間帯の、すべての構成のエラー率が閾値を超えた）に当たる | その**時間のまとまりを、すべての構成で同じように**無効にする |

- 分類は、**独立した評価の側**（Verifier と Controller）が、事前に決めた規則で行う。Agent は分類を付けられない。
- 無効な試行の費用も、実際の支出として計上する。実験の予算からも引く（12.1）。

### 7.3 採点の方法

- **コーディングのタスクでは、客観的なテストを優先する。** 隠しテスト、後退していないかのテスト、ビルド。
- **テストに合格しただけでは、あらゆる品質が保証されたとはみなさない。** 品質の指標（9.3）を、別に集計する。
- **評価する対象の自己申告は、正式な採点の結果として使わない**（C2 の X23）。
- **AI による採点を使う場合：**
  - 採点の基準、採点に使うモデルとその版、プロンプトを、事前に固定する。
  - 一部のタスクを人間が採点し、AI の採点との一致度を測る。一致度の基準は、事前に決める。
  - 採点の偏りを確かめる（長い回答を高く評価する、同じ系統のモデルを高く評価する、など）。
  - 採点を繰り返したときに、同じ結果になるかを確かめる。
  - 一致度を確かめるまでは、副の指標としてだけ使う。
  - AI による採点も `MODEL_CALL` であり、評価の側の費用として数える。
- **評価する構成と、採点のプログラムを独立させる：**
  - 採点のプログラムの版は、評価セットの版ごとに固定する。
  - 1つの実験の中では、すべての構成で、同じ採点のプログラムを使う。
  - 採点のプログラムを変える場合は、オーナーの承認が必要で、評価セットの新しい版として扱う。

### 7.4 ブラックボックスと in_process の区別（C2-P06）、一般化の範囲

- 採点の記録には、`assurance` を必ず付ける。**集計は `assurance` ごとに分けて行う。**
- **正式に「性能が向上した」と主張できる条件：**
  1. 9.2 の判定が、ブラックボックスで採点したタスクの集合だけで成り立つ。
  2. `in_process` の集合での結果は、補助の証拠として示すだけ。主張と逆の方向なら、主張を保留する。
  3. ブラックボックスで採点したタスクの、割合・件数・種類・難易度を報告する。
- **一般化しない：** 主張できるのは、ブラックボックスで評価したタスクの種類と難易度の範囲の中だけ。それ以外のタスクの種類にまで、性能を一般化しない。

### 7.5 正式な比較を無効にする条件（D-R07）

次のどれかに当たれば、その比較は正式な判定に使わない。**探索的な結果**として扱う。

- 構成の間で、モデルの版、タスクの入力、Sandbox やセキュリティの設定、予算、採点のプログラムの版が違っていた。
- 実行の順番が、事前登録した無作為化やブロック化（8.3）に従っていなかった。
- 無効な試行の割合が、構成の間で、事前に決めた閾値を超えて違った。候補は、差が 5 パーセントポイントより大きい、または比が 2 倍より大きい場合（PROVISIONAL）。
- プロバイダーの側の変更が実験の途中で見つかり、構成の間で影響が偏った。
- 事前登録した仕様のハッシュと、実行した仕様のハッシュが一致しない。

## 8. 統計的な評価（D07、D-R01、D-R03）

### 8.1 依存の構造と、標本の単位

```
リポジトリ（またはタスクの系統）
  └ 一連の作業（sequence）
      └ タスク
          └ 試行（同じタスクの繰り返し）
```

- **依存のある、最も上の単位**を、クラスタとして扱う。
  - 同じリポジトリから作ったタスクは、似た性質を持つ。
  - 一連の作業に属するタスクは、互いに影響し合う。
- 同じタスクの繰り返しは、そのタスクの成功の確率を推定するためのもので、独立した標本として数えない。
- **タスクを単位とするブートストラップだけで、すべての依存を扱えるとは仮定しない。**

### 8.2 対応のある比較と、推定

- 比べる構成どうしで、同じタスクの集合を使う。
- タスクごとに、成功の確率の差 d_t を求め、層（8.3）の重みを付けた平均 Δ̂ を、主な推定値とする。
- **信頼区間**（どれを主にするかは、事前登録で決める）：
  - **クラスタが十分に多い場合**（候補は 30 以上。PROVISIONAL）：クラスタ（リポジトリや一連の作業）を単位とするブートストラップ。
  - **クラスタが少ない場合：** リポジトリとタスクを変量効果とする、混合効果のモデル。または、クラスタの単位での並べ替えの検定。クラスタが少ないときは、ブートストラップの精度が落ちるため。
  - どちらの場合も、もう一方の方法で感度の分析を行い、結果を併せて報告する。
- **ばらつきの成分：** リポジトリの間 σ_r²、タスクの間 σ_t²、試行の間 σ_w² を、予備の評価で推定する。

### 8.3 層別化と、時間の変化

- **層別化：** タスクの種類と難易度で層を作る。タスクを選ぶときも、層ごとに選ぶ。集計の重み（タスクの数による重み、または層ごとに同じ重み）は、事前登録で決める。
- **時間の変化（モデルやプロバイダーの変化）への対策：**
  - 1つのタスクについて、すべての構成を、近い時間のまとまり（ブロック）の中で実行する。
  - ブロックの中では、構成の順番を無作為にする。
  - `time_block` を記録し、分析のときに共変量として入れる。
  - 決まった構成で、決まったタスクを定期的に実行し直す。これを「錨（いかり）」として、時間による変化を見張る。
  - 変化が見つかったら、7.5 に従う。

### 8.4 判定を3つに分ける（D-R01）

- 「良い」方向を正とする。費用と時間は、対数で表した比の符号を反転させて扱う。
- 指標ごとに、事前登録した信頼区間 [L, U]（候補は両側 95%）を求める。

| 判定 | 結果 | 条件 |
|---|---|---|
| **① 方向の判定** | `BETTER` | L > 0 |
| | `WORSE` | U < 0 |
| | `UNDETERMINED` | どちらでもない |
| **② 非劣性の判定**（許容幅 `δ_ni`） | `NI_MET` | L > −`δ_ni` |
| | `NI_FAILED` | どちらでもない |
| **③ 実用上の効果の判定**（改善の幅 `δ_imp`） | `PRACTICAL_CONFIRMED`（実用上意味のある幅以上であることを、統計的に確かめた） | L ≥ `δ_imp` |
| | `PRACTICAL_ESTIMATE`（推定値が、その幅に達した） | L > 0 かつ Δ̂ ≥ `δ_imp` |
| | `EXISTS_ONLY`（改善があることだけを確かめた） | L > 0 かつ Δ̂ < `δ_imp` |
| | `NOT_SHOWN` | どちらでもない |

- **3つの判定は、すべて報告する。** 1つにまとめた表示が必要な場合は、次の優先順位で付ける。
  ```
  PRACTICALLY_DEGRADED（U < −δ_ni）
  > DEGRADED_WITHIN_MARGIN（WORSE かつ NI_MET。悪いことは確かだが、許容幅の内側）
  > IMPROVED_CONFIRMED ＞ IMPROVED_ESTIMATE ＞ IMPROVED_EXISTS
  > NON_INFERIOR（NI_MET かつ UNDETERMINED）
  > INCONCLUSIVE
  ```
- `NI_MET` と `WORSE` は、同時に成り立ちうる（−`δ_ni` < L ≤ U < 0）。その場合は、「統計的に悪いが、許容幅の内側」として扱う。採用の判定でどう扱うかは、事前登録する（9.2）。
- `BETTER` であれば、必ず `NI_MET` も満たす（L > 0 > −`δ_ni`）。そのため、改善した構成が規則 B の非劣性の条件から外れることはない（第1版の矛盾を直した）。
- **有意な差がないことを、同じであることの証明とはみなさない。**
- **信頼区間が 0 を含まないことだけでは、実用上の向上とは言わない。**

### 8.5 検出力と、標本の設計（D-R03）

- **改善の目標と、検出力を計算するために仮定する真の効果を、分ける。**
  - `δ_imp`：採用の基準となる、改善の幅（目標）。
  - `Δ_assumed`：検出力を計算するために仮定する、真の効果。予備の評価の推定値と、その不確かさから決める。
  - `PRACTICAL_CONFIRMED` を求める場合は、`Δ_assumed > δ_imp` でなければ、検出力は上がらない。
- **検出力は、実際に使う判定の手順全体で、シミュレーションして求める。** 手順全体とは次のもの。
  - 維持すべき指標の非劣性（9.2）
  - 改善の判定と、事前登録した証拠の水準（9.2）
  - 多重比較の扱い
  - 欠けたデータと無効な試行の、見込みの割合
  - クラスタの構造（σ_r²、σ_t²、σ_w²）
- 求めるもの：
  - 効果が `Δ_assumed` のときに、採用と判定される確率（検出力）が、候補の 80% 以上。
  - 効果が 0（`PRACTICAL_CONFIRMED` の場合は、効果が `δ_imp` ちょうど）のときに、誤って採用と判定される確率が、α 以下。
- タスクの数、クラスタの数、試行の回数の組を、この条件を満たす中で、費用が最も小さいものに決める。決めた結果を、事前登録に書く。
- 費用の上限の中で条件を満たせない場合は、正式な評価を行わない（予備の評価として扱う）。

### 8.6 多重比較、外れ値、欠けたデータ、無効な試行

| 項目 | 扱い |
|---|---|
| 多重比較 | 9.2 の事前登録した手順（固定した順番の検定と、Holm）に従う。計画にない比較は、探索的なものとする |
| 外れ値 | 取り除かない。費用と時間では、総額と平均も、必ず報告する（12章） |
| 欠けたデータ | 無効な試行は、事前に決めた回数（候補は 2 回）まで、やり直す。それでも残った分は、欠けたものとして報告する。<br>最悪の場合（Agent Core の側は失敗、比較の相手の側は成功）を仮定しても、結論が変わらないかを確かめる |
| 評価の環境の障害 | 7.2 と 7.5 に従う |

## 9. 機能の採用の基準（D08、D-R02）と、継続的な改善（D09、D-R08）

### 9.1 3つのゲート

| ゲート | 内容 | 合格しない場合 |
|---|---|---|
| Technical Gate | 機能が仕様どおりに動く。各設計の不変条件と試験に合格する | 不採用 |
| Safety Gate | C1 と C2 の Safety Gate に合格する。評価の間の `safety.violations` が 0 件 | **不採用** |
| Performance Gate | 9.2 の規則 A か B を満たす | 不採用、または `INCONCLUSIVE` |

- **Technical Gate と Safety Gate は、性能の改善と引き換えに免除できない。**

### 9.2 指標の役割と、採用の規則（事前登録する検定の全体）

| 役割 | 指標 | 単位 | 条件 |
|---|---|---|---|
| **主指標** | 成功率（ブラックボックスの集合） | パーセントポイント | 規則 A の改善の対象 |
| **維持すべき指標**（規則 A・B の両方で、すべて満たす） | 成功率 | パーセントポイント | `NI_MET`（`δ_ni_sr`） |
| | 品質のスコア（9.3） | 品質の点（0〜100） | `NI_MET`（`δ_ni_q`） |
| | 成功1件あたりの費用、試行あたりの実費 | 比（対数） | `NI_MET`（比の許容幅 `ρ_cost`）。規則 A でも、悪化は許容幅まで |
| | 時間（p50 と p95） | 比（対数） | `NI_MET`（`ρ_time`） |
| | 人間の介入 | 回／タスク | `NI_MET`（`δ_ni_h`） |
| | `blocked_attempts` | 回／タスク | `NI_MET`（`δ_ni_blk`） |
| | `safety.violations` | 件 | **0 件**（Safety Gate） |
| **改善が必要な指標** | 規則 A：成功率。規則 B：成功1件あたりの費用、または時間（どちらにするかは事前登録） | 上と同じ | 事前登録した証拠の水準（8.4 の③） |
| **副指標** | 品質の内訳、トークン、障害からの復旧率、機能ごとの指標（9.6） | それぞれ | 報告するだけ。採用の判定には使わない |

**規則**

- **規則 A：** 維持すべき指標をすべて満たし、かつ成功率が事前登録した証拠の水準に達する。
- **規則 B：** 維持すべき指標をすべて満たし、かつ費用か時間のうち事前登録した指標が、事前登録した証拠の水準に達する。
  - 改善した構成も `NI_MET` を満たすので、規則 B から外れない（8.4）。
- **`DEGRADED_WITHIN_MARGIN` の扱い：** 維持すべき指標が「悪いが許容幅の内側」だった場合に採用してよいかを、指標ごとに事前登録する。既定では、許容する。

**事前登録する検定の全体（都合のよい改善だけを選ぶことを防ぐ）**

```
段階1：維持すべき指標の非劣性を、すべて確かめる（交わりと和の検定。どれか1つでも満たさなければ不採用）
段階2：事前登録した規則（A か B。どちらか1つ。両方を登録する場合は、A → B の順で固定した順番で検定する）で、
       改善が必要な指標を判定する
規則 B で費用と時間の両方を登録した場合は、その2つに Holm の補正をかける
```

- 規則、指標、許容幅、証拠の水準、順番は、すべて実験の前に固定する。
- **結果を見てから、規則を A から B に（またはその逆に）替えることは禁止する。**

**採用に必要な証拠の水準（事前登録で選ぶ）**

| 水準 | 内容 |
|---|---|
| E1 | `EXISTS_ONLY` 以上 |
| E2 | `PRACTICAL_ESTIMATE` 以上 |
| E3 | `PRACTICAL_CONFIRMED` |

- 候補は、規則 A の主指標で E2（PROVISIONAL）。E3 にするには、標本がかなり多く必要になる（8.5）。

### 9.3 品質のスコアの単位と、正規化（D-R02）

- タスクごとに、品質の検査項目 c_1…c_m と、重み w_i（合計で 1）を事前に定義する。検査項目の例：後退していないかのテスト、静的解析で警告が増えていないか、差分が最小限か、規約に合っているか。
- 各項目は、合格（1）か不合格（0）。点数を付ける項目は、事前に決めた範囲で [0,1] に直す。
- タスクの品質のスコア = 100 × Σ w_i·c_i（**0〜100 の品質の点**）。
- 品質の検査項目を持たないタスクは、品質の指標から外し、その件数を報告する。
- **成功率のパーセントポイントと、品質の点は、別の単位として扱う。** 許容幅も別々に決める。

### 9.4 候補の値（実験の前にオーナーが承認する。どれも根拠のない確定の値ではない）

| 値 | 候補（PROVISIONAL） |
|---|---|
| `δ_imp`（成功率） | +5 パーセントポイント |
| `δ_ni_sr`（成功率の非劣性の許容幅） | 3 パーセントポイント |
| `δ_ni_q`（品質） | 3 点（0〜100 の品質の点で） |
| `ρ_cost`（費用の悪化の上限） | +10%（比 1.10） |
| `ρ_time`（時間の悪化の上限） | +10% |
| 費用と時間の改善として意味のある幅 | 15% 以上 |
| `δ_ni_h`（人間の介入） | 0.1 回／タスク |
| `δ_ni_blk`（拒否された試み） | 0.2 回／タスク |
| 信頼区間 | 両側 95% |
| 検出力 | 80% |
| 証拠の水準 | 規則 A は E2 |

### 9.5 アブレーションと、改善の流れ

- **機能を1つずつ外す構成：** Context の最適化、Memory、Planning、Tool Selection、Verification、Recovery を、それぞれ外したものを作る。安全のために必須の機能（4.1）は外さない。
- **相互作用：** 相互作用が疑われる組だけを、2×2 の組み合わせで調べる。アブレーションの結果は、探索的なものとして扱い、Holm で補正する。
- **改善の流れ：**
  ```
  CandidateChange → dev で試験（Technical Gate）→ validation で事前登録・比較 → 独立審査
  → 採用（Decision）→ 監視 → 悪くなったら取り消し（ROLLBACK）
  holdout は、事前に登録した節目でだけ使う
  ```
- **AI は、評価の基準、採点のプログラム、タスクの集合、分析の計画を変えられない**（V8）。将来の Phase 6 は、CandidateChange、ExperimentSpec、Decision を通して、この流れにつなぐ。

### 9.6 機能ごとの評価（D-R08）

**全体の比較の相手と、機能を評価するための比較の構成を分ける**

- 全体の比較の相手：Baseline A・B・C（4.1）。
- 機能の比較の構成（FeatureComparator）：Agent Core の中で、**その機能だけ**を変えたもの。
  - 例：Context の場合は、B1 の「全履歴方式」「基本的な圧縮」「最適化」。
- **B1 の全履歴方式と、D の Baseline A は、同じ構成とは限らない。** Baseline A は、エージェント全体が最小限の構成である。全履歴方式は、Agent Core の中で、文脈の方針だけを変えたものである。

| 機能 | 指標 | 比較の構成 |
|---|---|---|
| Context | 必須情報の保持率（保存上と、モデルから見える保持）、取り直しの率、情報の損失（隠した情報を答えられるか）、文脈の費用 | B1 の11章の3つの方式と、アブレーション |
| Memory | 取り出した記憶の正確さ（precision と recall）、有用性（記憶あり・なしの差）、誤った学習（誤った記憶を採用した割合）、同じ失敗の再発率 | B2 の11章の4つの構成 |
| Planning | 計画の質（事前に決めた基準での評価）、不要な計画の立て直しの回数、実行の効率（手順の数、時間） | 計画あり・なし、計画の立て直しの方針の違い |
| Tool | ツールの選び方の正しさ、呼び出しの成功率、不要な実行の割合 | ツールの選択の機能あり・なし |
| Recovery | 障害から復旧した割合、復旧にかかった時間、重複して実行した件数（0 であること） | 障害を入れたタスクでの、復旧の機能の違い |
| Cost | 実費、予算を守った割合、照合の精度（説明のつかない差額の件数） | 予算の方針の違い |

**長時間の連続した作業と、実際の業務を模した評価**

- **Owner Workflow Suite：** オーナーが普段行う実際の業務を模したタスクの並び（機密を取り除いたもの）。
  - 何日にもわたる、一連の作業として評価する。
  - 単位は一連の作業。
  - 指標は、作業全体の完了率、累積の費用、人間の介入、長時間の安定性（障害、止まった回数）。
- 初期は、コーディングに集中する。研究、Web、営業などは、将来の拡張とする。

## 10. Cost Engine（D10、D-R05）

### 10.1 費用を計算する対象と、2つの区分

- モデルの呼び出し：入力トークン、出力トークン、キャッシュの書き込みと読み込み、推論トークン
- 補助的なモデルの呼び出し：要約、関連度の判定、計画の立て直し、記憶の抽出と検証、AI による採点
- 検索、ツール、外部の API
- 再試行、失敗した呼び出し、結果が分からない呼び出し
- Sandbox（CPU の時間、メモリ）、ストレージ

| 区分 | 中身 |
|---|---|
| `agent_cost`（AI の実行の費用） | Agent が仕事をするためにかかった費用 |
| `eval_infra_cost`（評価の環境の費用） | ベンチマークの維持、採点の実行（AI による採点を含む）、評価の側のホストと VM、人間による確認の時間 |

- この2つは分けて集計する。必要なら合計も出す。

### 10.2 費用の台帳と、状態の遷移（D-R05）

**台帳の作り**

- 台帳は、追記するだけの記録（エントリー）で作る。
- 残高は、エントリーから計算して求める。
- 1つの試行（`attempt_id`）について、予算を押さえている額（`hold`）は、常に1つだけ。状態が移るときは、P1 の1つのトランザクションで、古い `hold` を新しい `hold` に置き換える。こうして、二重に数えることも、数え漏れも起きないようにする（V16）。

**状態**

| 状態 | 意味 | `hold` として予算から引く額 | 結び付ける ID |
|---|---|---|---|
| `RESERVED` | 実行の前に予約した | 予約した額（見積もりの上限 ＋ `safety_margin`） | `reservation_id`、`attempt_id` |
| `ACTIVE` | 実行中（Permit を消費し、receipt が `SEND_STARTED` になった） | 予約した額 | ＋ `permit_id`、`receipt_id` |
| `USAGE_REPORTED` | 使用量の報告を受けたが、請求とはまだ照合していない | 使用量から計算した額 ＋ 価格のずれの分の上乗せ。残りの予約は解放する | ＋ `provider_request_id` |
| `UNKNOWN` | 結果が分からない（タイムアウト、障害、送信の途中で接続が切れた） | 上限の見積もり（設計A の A04）。照合するまで解放しない | 同じ |
| `RECONCILED` | プロバイダーの実績と照合して確定した | 照合した額 | ＋ `reconciliation_id` |
| `RELEASED` | 実行しなかった（Permit を消費しなかった、送信の前にキャンセルした、`ABORTED_BEFORE_SEND`） | 0 | 同じ |
| `CORRECTION` | 結果の訂正（元のエントリーを指す、別のエントリー） | 差額 | ＋ 元のエントリーの ID |
| `UNEXPLAINED` | 照合で、説明のつかない差額が出た | 差額。調べ終わるまで、実験の新しい支出を止める | ＋ `reconciliation_id` |

**状態の移り方**

```
RESERVED → ACTIVE → USAGE_REPORTED → RECONCILED
RESERVED → RELEASED                         （実行しなかった）
ACTIVE   → UNKNOWN → RECONCILED             （照合で確定した）
任意の状態 → CORRECTION（追記）／ UNEXPLAINED（追記）
```

**それぞれの場合の扱い**

| 場合 | 扱い |
|---|---|
| タイムアウト、キャンセル | 送信の前なら `RELEASED`。送信の後なら `UNKNOWN` |
| 障害（クラッシュ） | `ACTIVE` のまま残っているものは、復旧したときに `UNKNOWN` にする |
| ストリーミングの途中で切れた | 途中までの使用量の報告があれば、それを**下限**として記録する。そのうえで、`hold` は上限の見積もりのまま `UNKNOWN` にする |
| 同じ使用量の報告が、重複して届いた | `(attempt_id, provider_request_id, usage_event_id)` で、重複を取り除く |
| 再試行 | 新しい `attempt_id` と、新しい予約を使う（設計A の A04） |

**Provider Adapter ごとの課金の方式（BillingScheme）**

`{components: {input_uncached, cache_write, cache_read, output, reasoning: included_in_output|separate|none, per_request_fee, tool_fees}, usage_mapping, rounding, minimum_charge}`

- `usage_mapping` は、プロバイダーが返す使用量の各項目が、互いに**重ならない**ように、どの料金の項目に当たるかを宣言する。
  - 例：入力の合計にキャッシュの分が含まれる方式なら、`input_uncached = input_total − cache_read − cache_write` とする。
  - どの方式かは、プロバイダーごとに確かめる（未確認）。
- 入力、キャッシュ、推論、出力を、二重に数えないことを、決まった入力と期待する出力の組（フィクスチャ）の試験で確かめる。

**金額の表し方**

- 金額は、浮動小数点数では計算しない。**最小の計算単位の整数**（例：通貨の 10⁻⁶ の単位、`micro_<currency>`）を、64 ビットの整数で持つ。
- 単価も、100万トークンあたりの最小単位の整数で持つ。
- 丸めの規則：
  - 予約は、切り上げる。
  - 見積もりは、偶数への丸め（銀行家の丸め）にする。
  - 丸めで生じた差は、エントリーに記録する。
- 1つの台帳では、通貨を1つに固定する。通貨を換算しない。

**内部の予算の上限と、実際の請求の上限を分ける**

- 内部の予算の上限は、Cost Engine が強制する。
- 実際の請求の上限（プロバイダーの側の支出の上限）は、予備の防御にすぎない。厳密に止まるかどうかは、確かめていない（設計A の A09）。
- 内部の上限は、請求の側の上限より低く設定する。

### 10.3 価格表

`{price_table_id, version, currency, unit: micro, effective_from, effective_to, source: {ref, verified_by, verified_at}, status: test|verified|unverified, billing_scheme_ref, items: {...}}`

- 費用の記録は、どれも `price_table_id@version` を持つ。
- 実際のプロバイダーの価格表は、オーナーが出典を確かめてから、`verified` として登録する。今回は調べていない。

**試験用の仮想の価格表（実際の価格ではない）**

```
price_table_id: test-virtual-v1
currency: XTU（試験用の単位。米ドルではない）、unit: micro（1 XTU = 1,000,000 micro_XTU）
status: test
items（100万トークンあたりの micro_XTU）:
  scripted-model-small: {input_uncached: 1000000, output: 4000000, cache_write: 1250000, cache_read: 100000}
  scripted-model-large: {input_uncached: 5000000, output: 20000000, cache_write: 6250000, cache_read: 500000}
  sandbox: {cpu_second: 100, gb_hour: 1000}
  storage: {gb_month: 10000}
```

- 本番のモードでは、`status: test` の価格表を読み込めないようにする。

## 11. 予算の強制（D11、D-R06）

### 11.1 上限の階層

```
1回のモデル呼び出し ⊆ Step ⊆ Run ⊆ ユーザー ⊆ テナント ⊆ 月間
実験全体 ⊆ テナント ∩ 月間
```

- **予約：** P1 の1つのトランザクションで、関係するすべての階層について、`Σ hold ＋ 新しい予約 ≤ 上限` を確かめてから、すべての階層に同時に記録する。
- 予約は、`attempt_id` に結び付く。消費は、`permit_id` と `receipt_id` に結び付く（10.2、C1 の7.5）。
- **予算が足りない場合は、実行を止める**（`PAUSED_BUDGET`）。

### 11.2 金銭以外の上限（Run 全体が際限なく続かないようにする）

| 上限 | 範囲 | 候補の値（PROVISIONAL） |
|---|---|---|
| モデル呼び出しの総回数（補助を含む） | Run・実験 | 200 回／Run |
| ツールの実行の回数 | Run | 300 回／Run |
| 文脈の組み立て直しの回数 | Run | 50 回／Run |
| 計画の立て直しの回数 | Run | 10 回／Run |
| 記憶の抽出と検証 | Run・テナント | 20 回／Run |
| 再試行の回数（種類をまとめた合計） | Run | 30 回／Run |
| 総実行時間（経過時間） | Run・実験 | タスクの `timeout`。Run の上限は 2 時間 |
| すべての操作の合計（作業単位） | Run | 個別の上限とは別に、1つの総数の上限を持つ |

- 個別の上限を守っていても、合計の上限に達したら止める。
- 処理の順序（Safety の判定、予約、Intent、Permit）の統一は、E で行う。

### 11.3 環境をまたいだ予算の管理（D-R06）

| 方式 | 良い点 | 問題 |
|---|---|---|
| 中央の予算台帳 | 合計を、厳密に1か所で守れる | 評価の側を隔離していると（C2 の10章）、つながりを保つことと隔離を保つことが両立しにくい。運用が重い |
| 各環境への、事前の予算の割り当て（封筒の方式） | 各環境が、手元で強制できる。合計は、割り当ての合計で守れる | 使い残しが出る。割り当てを変えるには、オーナーの操作が必要 |
| 段階に応じて、1つの環境だけで支出する | 最も単純 | 並行して進められない |

**初期の方針（オーナー自身のための小規模な運用。過剰な設計にしない）**

- **Phase 3B〜3D では、段階ごとに、実API に支出できる環境を1つだけにする。** 3B は開発の側の接続の試験、3C と 3D は評価の側。
- そのうえで、封筒の方式を予備の防御として使う。承認した月間の予算を、その時点で使う環境に全額割り当て、ほかの環境には 0 を割り当てる。
- 中央の台帳は、環境やプロセスが増えたときの将来の拡張とする。

**期間をまたぐ場合**

- **月をまたいだ未確定の費用：** 費用は、**使った日時の月**に計上する。照合が翌月にずれても、`hold` は元の月に残り続ける。
- **予算の更新：** 月の上限は、オーナーの方針に従って、月の初めに改める。使い残しは、翌月に繰り越さない（既定）。前の月の `UNKNOWN` と `USAGE_REPORTED` は、新しい月の予算とは別に、元の月の分として押さえ続ける。
- **実験をまたぐ費用：** 複数の月にまたがる実験は、それぞれの月の上限と、実験の上限の両方から引く。
- **照合の遅れ：** 照合が終わるまでは、内部の側で、多めに見積もった計上を続ける。

### 11.4 実API を使う前の承認（SpendApproval、D1）

`{approval_id, experiment_id, environment, envelope_amount, allowed: {config_ids, task_set_version, max_trials, max_runs}, model_ids, max_cost（最小単位、通貨）, monthly_cap, valid_from, expires_at, approver, conditions}`

- Cost Engine は、予約するときに、**有効な `approval_id` を必ず求める。** 一致する承認がなければ、予約しない。予約がなければ、Permit も出ない（C1）。そのため、**オーナーが承認していない実API の呼び出しは、構造的にできない。**
- Phase 2 の終わりまでは、承認そのものを作れない（D1）。
- Phase 3 以降も、費用は自動では承認しない。
- 承認の範囲（試行の回数、費用、期限）を超えそうになったら、新しい試行を始めずに止め、オーナーに確認する。

## 12. 費用と時間の評価、照合（D12、D-R04）

### 12.1 別々に集計する指標

| 指標 | 定義 | 報告するもの |
|---|---|---|
| 試行あたりの実費 | 有効な試行の、実際の費用（打ち切りの処理をしない） | 総額、平均、中央値、p90、最大値 |
| **成功1件あたりの総費用** | 有効な試行の総費用（失敗したものを含む）÷ 成功の件数 | 分子と分母も、必ず一緒に示す |
| 成功した試行だけの平均費用 | 成功した試行の費用の平均 | **参考の値**。判定には使わない |
| 品質の達成率と予算の関係 | 12.2 の曲線 | 曲線と、主な点の値 |
| 無効な試行と再試行の実費 | 無効な試行の費用の総額、再試行に使った費用の総額 | 別に報告する。実験の支出には含める |
| 人間の介入の時間 | 承認、確認、手で直したときの分数 | 総計、1タスクあたり |
| 初期の費用と、維持の費用 | 立ち上げと、続けるための費用 | 別々に |

- **費用の大きい失敗を隠さない：** 費用の大きい順に、上位 N 件の失敗した試行を一覧にする。
- **中央値だけで報告しない：** 総額と平均も、必ず一緒に示す。

### 12.2 品質を達成するまでの費用（打ち切りの処理）

- 試行ごとに、成功した（または品質の水準に達した）時点の累積の費用 `cost_at_success` を記録する。
- 成功しなかった試行は、**実際に使った費用の時点で打ち切られた**ものとして扱う。上限の額を払ったことにはしない。
- 打ち切りを扱う生存分析の方法（Kaplan–Meier に当たる方法）で、「費用 b までに成功する確率」の曲線を、構成ごとに推定する。
- 「品質を達成するまでの費用」は、その曲線が、事前に決めた確率（例：50%）に達する費用 b とする。曲線がその確率に届かなければ、「観測の範囲を超える（> 最大値）」と報告し、数値は出さない。
- この分析は、**実際の支出の集計（12.1）とは別のもの**として扱う。

### 12.3 0 の扱い

| 場合 | 扱い |
|---|---|
| 費用が 0（ScriptedProvider など） | 金額の差は計算する。比は、分母が 0 なら未定義とし、分子と分母を示す |
| 成功の件数が 0 | 成功1件あたりの費用は未定義。総費用と、試行の件数を示す |
| 比の分母が 0（比較の相手の費用が 0 など） | 比と、対数の比は未定義。絶対の差だけを示す |
| 対数で表すときに、試行の費用が 0 | 対数での集計に使わない。その件数を報告し、絶対の差での分析を併せて示す |

### 12.4 照合（設計A の A09 を引き継ぐ）

- 合格の条件は、変えない。
  - `unexplained_diff = 0`
  - 説明できる差額が、許容誤差の範囲内
  - 実際の請求が、承認した上限の範囲内
- **許容誤差の候補（オーナーが承認する。PROVISIONAL）：** 照合の期間ごとに、説明できる差額の合計の絶対値を、次の大きいほう以下にする。
  - 1.00 米ドル
  - 照合した額の 2%
- **説明のつかない差額を、許容誤差の中に隠さない。** 金額にかかわらず、その実験の新しい支出を止めて調べる。
- Phase 1〜2 では、`XTU` の仮想の価格表と、偽の利用の実績で、照合の処理を試す。

## 13. 実験の再現性と管理（D13）

### 13.1 実験ごとに記録する項目

- `experiment_id`
- Agent Core のコミットの SHA、構成のハッシュ（`config_hash`）
- モデルの ID と版、`ModelProfile@version`、推論の設定
- タスクの集合の版、採点のプログラムの版、`assurance` の内訳
- Sandbox の構成（`sandbox_profile_hash`）、ポリシーの版（`policy_version`）
- 予算と、承認（`SpendApproval` の `approval_id`）、価格表の版、BillingScheme の版
- 依存の構造（リポジトリのクラスタ、一連の作業）、層、時間のブロック
- holdout を使った場合は、評価セットの版と、その版の累積の使用回数
- 実行の順番、乱数の種、試行の回数
- 成功、失敗、無効な試行の件数と理由
- 実行の時間、費用（状態ごと）
- 評価の結果の信頼度（`assurance`、無効な試行の割合、条件の違い（`condition_deviations`））
- 事前登録の仕様のハッシュ（`spec_hash`）と、登録した時刻

### 13.2 固定と、実行の順番

- 評価の条件と採用の基準は、実験を始める前に固定する（`spec_hash` を Journal と Results Store に記録する）。
- 実行の順番は、構成とタスクを無作為に交ぜて決める。こうして、時間の経過による変化（プロバイダーの側の負荷や変更）が、特定の構成に偏らないようにする。乱数の種を記録する。

### 13.3 再現性の限界

- モデルの出力は、同じ条件でも毎回同じになるとは限らない。プロバイダーの側でモデルや設定が変わることもある。
- そのため、完全に同じ結果になるとは限らない。
- 再現性は、「同じ仕様で実行し直したときに、判定（8.4 の3つの判定）が変わらないか」で確かめる。数値が完全に一致することは求めない。
- モデルの ID、版、日付を記録し、変わったことが分かった場合は、比べてよい範囲を限る。

## 14. Phase ごとの実装の範囲（D14）

| Phase | 範囲 | 実API の費用 |

| **Phase 3B** | 個別に承認された、小さな接続の試験。<br>- 照合の試験<br>- 予備の評価の一部として、ばらつきを見積もるかどうかは、承認の範囲で決める | 承認した額だけ |

- 実API を使う前には、毎回 11.4 の承認（`SpendApproval`）が必要。

## 15. 不変条件

| ID | 不変条件 |
|---|---|
| V1 | 評価の条件、指標の役割、許容幅、証拠の水準、検定の順番、採用の規則、分析の計画は、実行の前に固定し（`spec_hash`）、実行の後に変えない。規則を A から B に（またはその逆に）替えない |

| V3 | 安全のために必須の機能は、どの構成でも外さない。Technical Gate と Safety Gate は、性能と引き換えに免除しない |
| V4 | 評価する対象の自己申告は、正式な採点に使わない |
| V5 | ブラックボックスと `in_process` の結果を、まとめて集計しない。正式な向上の主張は、ブラックボックスの集合で成り立ち、評価したタスクの範囲の中だけ |
| V6 | 方向、非劣性、実用上の効果の3つの判定を、すべて報告する。有意な差がないことを、同じであることの証明にしない。信頼区間が 0 を含まないことだけを、実用上の向上とは言わない |
| V7 | holdout の使用の回数と、公開した集計は、評価セットの版ごとに、実験をまたいで累積で数える。確認のための再評価は、最初の実行の前に事前登録する。holdout の結果で、機能を繰り返し調整しない |
| V8 | AI は、評価の基準、採点のプログラム、タスクの集合、分析の計画を変えられない |
| V9 | 成功1件あたりの費用は、失敗の費用を含めた総費用で計算する。分母が 0 なら未定義。分子と分母を必ず示す |
| V10 | 予約は、関係するすべての階層の上限を、1つのトランザクションで確かめる。予約は `attempt_id` に、消費は `permit_id` と `receipt_id` に結び付く |
| V11 | 金銭以外の上限と、Run 全体の作業単位の上限を持つ。どれかに達したら止める |
| V12 | 有効な `SpendApproval` がなければ、実API の費用を予約できない（したがって、実行もできない） |
| V13 | 説明のつかない差額を、許容誤差の中に隠さない |
| V14 | 試験用の価格表（`XTU`、`status: test`）を、本番のモードで使わない |
| V15 | 判定に使えない比較（Baseline C、7.5 に当たるもの）は、参考の値や探索的な結果として印を付ける |
| V16 | 1つの試行の `hold` は、常に1つだけ。状態が移るときは、1つのトランザクションで置き換える。使用量の報告は、重複を取り除いて扱う |
| V17 | 金額は、最小の単位の整数で計算する。浮動小数点数を使わない |
| V18 | `INVALID_ENV` にできるのは、評価の環境の側の障害だけ。Agent が起こした障害は外さない。分類は評価の側が行う。無効な試行の費用も、実際の支出に数える |
| V19 | 安全性の違反と、通常の認可の拒否を分けて記録する。タスクの結果と、安全の結果を、別の項目として記録する |
| V20 | 品質を達成しなかった試行を、上限の額を払ったものとして扱わない |
| V21 | Phase 3B〜3D では、実API に支出できる環境を、段階ごとに1つにする。費用は、使った日時の月に計上する |

## 16. ゲート

**ゲートに合格しても、評価が完全に正しいことの証明にはならない。**

### 16.1 Technical Gate（評価の仕組みそのもの。統計は D-R03 に従う）

**統計のシミュレーション**（事前に決める。値は PROVISIONAL）

- 状況ごとに、2,000 回以上シミュレーションする。状況は次のとおり。
  - 効果なし
  - 効果が `δ_imp` ちょうど
  - 効果が `Δ_assumed`
  - クラスタあり
  - 欠けたデータあり
  - 時間による変化あり
- 判定の手順の全体（9.2）で、次を測る。

| 測るもの | 許容の範囲 |
|---|---|
| 偽陽性の率（効果なしのときに採用と判定する率） | α ＋ モンテカルロの誤差の 3 倍以下 |
| 信頼区間の被覆率（95% の区間） | 0.93〜0.97 |
| 検出力 | 計画した値の ±5 ポイント以内 |
| クラスタの依存 | 試行を独立に数えた場合と比べて、区間の幅が正しく広がる。被覆率が保たれる |

**そのほかの試験**

| 試験 | 合格の目安 |
|---|---|
| 事前登録の固定 | 固定した後に仕様を変えた実行が、拒否される割合 100% |
| 予約の階層 | 同時の実行や障害があっても、どの階層でも上限を超えた件数 0 |
| 費用の台帳の状態遷移（10.2） | タイムアウト、キャンセル、障害、ストリーミングの途中の切断、使用量の報告の重複の各場合で、二重の計上も漏れも 0 件 |
| BillingScheme（課金の方式） | フィクスチャの試験で、入力、キャッシュ、推論、出力を二重に数えた件数 0 |
| 金額の計算 | 整数での計算と丸めが、決めた規則どおりになる割合 100% |
| 金銭以外の上限 | 各上限と、合計の上限で止まる割合 100% |
| 照合 | 説明できる差額と、説明のつかない差額を、正しく分類する割合 100% |
| 打ち切りの処理（12.2） | 模擬データで、打ち切りを扱う推定が正しい（上限の額で埋めた場合との違いを示せる） |
| 0 の扱い（12.3） | 未定義になるべき場合に、未定義になる割合 100% |
| 再現性 | 同じ仕様と同じ乱数の種で、ScriptedProvider を使ったとき、結果が完全に一致する |

## 18. 残存リスク

1. **既存の知識による汚染：** モデルが既に学習している内容による汚染は、完全には確かめられない。
2. **検出力の不足：** 費用の上限のために、十分なタスクやクラスタの数を確保できず、`INCONCLUSIVE` が続く可能性がある。証拠の水準を E3 にすると、さらに多くの標本が必要になる。
3. **クラスタの数：** クラスタが少ないと、どの推定の方法でも精度が落ちる。
4. **Baseline B の妥当性：** 独立審査に頼る。「実用として妥当」の線引きに、主観が残る。
5. **AI による採点の偏り：** 人間の採点との一致度を確かめても、偏りが残りうる。
6. **時間による変化：** ブロック化しても、プロバイダーの側の大きな変更が途中で起きると、比べられる範囲が狭くなる。
7. **in_process の方式に頼るタスク：** ブラックボックスにできないタスクが多いと、正式に主張できる範囲が狭くなる。
8. **候補の値の妥当性：** 9.4・11.2・12.4 の値は、予備の評価の前の仮の値である。
9. **費用の照合：** 利用の実績の粒度、反映の遅れ、BillingScheme の正しさは確かめていない。
10. **段階ごとに1つの環境での運用：** 並行して進めることができない。
11. **初回報告書との照合：** 初回報告書の全文と照合していない。

## 19. 未確認事項（外部調査は行っていない）

- 実際のプロバイダーの価格、課金の単位、キャッシュの料金の体系、推論トークンの課金のしかた、失敗したリクエストへの課金。
- 使用量の報告の項目が、互いに重ならないかどうか（BillingScheme の `usage_mapping`）。
- プロバイダーの利用の実績の取得の方法、粒度、反映の遅れ。
- プロバイダーの側の支出の上限が、厳密に止まるかどうか。
- Baseline C に使う外部のエージェントの製品と版、条件をどこまでそろえられるか。
- 予備の評価の前の、ばらつきの成分と効果の大きさ。
- 統計の方法の細かい性質。特に、少ないクラスタの数での、各方法の被覆率。
