>
> 範囲と前提

## 0. 基本方針

1. **評価する対象：** Agent Core は、モデルを学習し直す仕組みではない。評価するのは、**同じモデル**に Runtime・Context・Memory・Planning・Tool・Recovery などの仕組みを加えたときに、どれだけ良くなるか。
2. **1つの総合点だけで判定しない：** 成功率、品質、時間、トークン、費用、人間の介入、障害からの復旧、安全性を、それぞれ分けて測る。
3. **事前に登録する：** 評価の条件、指標、分析の方法、採用の基準は、実験を始める前に固定する。結果を見てから変えることはしない。
4. **公平に比べる：** 変えるのは、評価したい機能だけ。わざと弱い比較の相手は作らない。
5. **安全は、取引の材料にしない：** Safety Gate を通らない構成は、性能がどれだけ高くても採用しない。
6. **分からないときは、分からないと言う：** 結論が出なければ `INCONCLUSIVE` とする。

## 1. 評価の目的と、測る項目（D01）

| 観点 | 主な指標 | 定義 |
|---|---|---|
| タスクの成功 | 成功率 | 事前に定めた成功条件（7章）を満たした割合。タスクを単位として集計する（8.1） |
| 成果物の品質 | 品質の指標 | 隠しテスト以外の項目（後退していないか、静的解析、差分の大きさ、規約に合っているか、評価の基準に照らした点数）。成功率とは別に集計する |
| 実行の時間 | 経過時間 | Run の開始から終了まで。p50 と p95 も出す |
| トークンの使用量 | 種類ごとのトークン | 入力、出力、キャッシュの書き込みと読み込み、補助的な呼び出し |
| 金銭的な費用 | 費用 | 12章。照合して確定した値を主に使う |
| 人間の介入 | 回数と時間 | 承認、確認、手で直した回数と、かかった分数 |
| 障害からの復旧 | 復旧できた割合 | 障害を入れたタスクで、正しく復旧して完了した割合。設計A の不変条件の違反の件数 |
| 安全性 | 違反の件数 | Safety Gate の試験と、評価中に観測した違反（権限のない操作、送信、境界を越えたもの）。**0 件が条件** |

## 2. アーキテクチャ

```
 ┌──────────── 開発の側（dev と validation） ────────────┐   ┌────── 評価の側（holdout。C2 の10章） ──────┐
 │ Experiment Registry（事前登録、ハッシュで固定）         │   │ Eval Controller・Test Vault・Sandbox        │
 │ Task Catalog（dev と validation）                      │   │ Verifier・Signer・Aggregator                 │
 │ Benchmark Runner（dev 用）→ Agent の各構成（Sandbox）   │   │ Benchmark Runner（holdout 用）               │
 │ Evaluation Engine（採点の手配。dev 用の Verifier）      │   │                                             │
 │ Statistics Engine（登録した分析の計画を実行する）       │◀──│ 制限した報告（C2 の11.1）                    │
 │ Cost Engine（見積もり・予約・照合・報告）               │   └─────────────────────────────────────────────┘
 │ Decision Recorder（ゲートの判定、採用、取り消し）       │
 │ Results Store（試行の記録。ハッシュの連鎖）             │
 └────────────────────────────────────────────────────────┘
```

| 部品 | 役割 |
|---|---|
| Experiment Registry | 実験の仕様（13章）を、始める前に登録し、ハッシュを記録して固定する。固定した後は変えられない。変えるには、新しい実験として登録し直す |
| Task Catalog | タスクの仕様（3.1）を、版付きで管理する。dev と validation は開発の側に、holdout は評価の側にだけ置く |
| Benchmark Runner | 実験の仕様に従って、構成とタスクと試行の順番を組み、Run を実行する。順番は無作為に入れ替える（13.2） |
| Evaluation Engine | 採点を手配する。採点は、Agent 自身ではなく、Verifier（Sandbox の外）が行う（C2 の10.2） |
| Statistics Engine | 登録した分析の計画どおりに、推定と判定を行う。計画にない分析は、「探索的なもの」と印を付ける |
| Cost Engine | 費用の見積もり、予算の予約、照合、報告（10〜12章） |
| Decision Recorder | 3つのゲートの判定と、採用・不採用・取り消しを、根拠と一緒に記録する |
| Results Store | 試行と採点の記録。開発の側の分（dev と validation）と、評価の側の分（holdout）を分ける |

- Evaluation Engine と Statistics Engine は、**評価する対象の Agent からは独立**させる。Agent の構成を変えても、採点のプログラムと分析のプログラムは変わらない。
- 採点と分析のプログラムを変えるのは、オーナーが承認した、別の変更として行う（9.6）。

## 3. データ構造

### 3.1 TaskSpec（タスクの仕様）

`{task_id, task_set, split: dev|validation|holdout, version, domain: coding|research|web|sales|..., type, difficulty, scale, input_ref, start_state_ref（作業を始めるときのファイル）, success_criteria, partial_criteria, failure_criteria, timeout, budget, safety_rules, grading: {method: blackbox|in_process|rubric_ai|human, grader_version}, provenance（作った人、元のリポジトリ、作った日）, contamination_notes, sequence_id?}`

- `type`：4.2 の9種類のどれか
- `contamination_notes`：既存の知識による汚染の可能性についての記録
- `sequence_id`：一連の作業に属するタスクの場合だけ

### 3.2 ConfigSpec（評価する構成）

`{config_id, kind: baseline_a|baseline_b|baseline_c|agent_core|ablation, agent_core_commit, enabled_features[], disabled_features[], config_hash, model_profile@version, inference_params, tools[], sandbox_profile_hash, policy_version, budget_caps}`

- 安全のために必須の機能は、`disabled_features` に入れられない（V3）。

13.1 の項目すべてに加えて、次を含む。

## 4. 比較の相手（D02）と、公平性（D03）

### 4.1 構成

| 構成 | 内容 | 判定に使うか |
|---|---|---|
| **Baseline A：Minimal Agent** | モデルの呼び出し、ツールの実行、履歴の保持（枠を超えたら古い順に切り捨てる。ただし上位の命令と安全上の制約は切り捨てない。B1 の11章）、終了の条件 | 参考と、下限の確認 |
| **Baseline B：Competent Agent** | 一般的な実用のエージェントとして妥当な構成。次を持つ。<br>- 適切なツールの設計（`rg`、範囲を指定した読み込み、編集のツール）<br>- 基本的な文脈の管理（古いツールの結果の置き換えと、切り詰め。B1 の S1・S2）<br>- 一時的な失敗の再試行<br>- 完了を報告する前にテストを実行する検証の手順 | **主な比較の相手** |
| **Baseline C：External Reference** | 既存の外部のエージェント。具体的な製品と版は、実験の前に確かめる | **参考の値だけ**。モデル、費用、内部の構成を完全にはそろえられないため、採用の判定には使わない |
| **Agent Core** | 評価する構成 | 評価の対象 |
| **Ablation** | Agent Core から、機能を1つずつ外した構成（9.4） | 機能ごとの効果の推定 |

**わざと弱い相手にしないための決まり**

- Baseline B の構成は、実験の前に独立審査者が確かめ、「妥当な実用の構成である」と記録する。
- dev の集合で調整に使える手間（試行の回数と費用）は、Baseline B と Agent Core で同じにし、その量を記録する。
- Baseline B に、Agent Core の機能の一部（記憶など）を入れるかどうかは、事前登録のときに決めて、理由を記録する。

**安全のために必須の機能は、どの構成でも外さない**

- 必須の機能：PDP と PEP、Permit、Sandbox、Gateway、SAG、予算の強制、B1 の権限の階層、ProtectedFact のうち安全上の制約と変更禁止事項。
- Baseline A と B も、この同じ安全の仕組みの上で動かす。

### 4.2 公平性の条件（D03）

**すべての構成で、そろえるもの**

- モデルとその版、推論の設定
- タスクの入力、完了の条件、作業を始めるときのファイル
- 使えるツールと操作の能力（ツールの「設計」は構成ごとに違ってよいが、できることの範囲は同じにする）
- セキュリティの制約、Sandbox、時間の上限、トークンの予算、金銭の予算
- 人間が介入する条件

**変えるのは、評価したい機能だけ。** そろえられなかった条件は、`condition_deviations` として実験の記録に残す。

**2つの比べ方を分ける**

| 比べ方 | 何を固定し、何を比べるか |
|---|---|
| 固定の予算での比較 | 予算と時間を同じにして、成功率と品質を比べる |
| 品質を達成するための費用の比較 | 成功、または事前に決めた品質の水準に達するまでの費用と時間を比べる。達しなかった試行は、上限の費用で打ち切られたものとして扱い、件数も報告する |

## 5. ベンチマークの構成（D04）

### 5.1 タスクの分類

| 軸 | 値 |
|---|---|
| 種類 | 小さなバグの修正、複数のファイルの修正、新しい機能の追加、テストの作成、リファクタリング、既存のコードの理解（質問に答える）、長時間の作業、障害からの復旧（障害を入れたもの）、あいまいな要求への対応（確認の質問をすべきもの） |
| 難易度 | S・M・L。目安は、触るファイルの数、変える行の数、必要な手順の数、熟練者が要する時間。基準は Task Catalog に記録する |
| 規模 | リポジトリの大きさ（ファイルの数、行の数）、文脈に必要な量 |
| 分野 | 最初は `coding` だけ。`research`、`web`、`sales` などを、同じ TaskSpec の形で、後から加えられるようにする |

### 5.2 最初の 20〜50 タスク

- 評価の仕組みを試すことと、予備の評価（分散と効果の大きさを見積もること。8.4）に使う。
- **統計的な検出力を保証する件数としては扱わない。**

### 5.3 タスクの出どころと、汚染

- 公開されているリポジトリや課題は、モデルがすでに学習している可能性がある。
- そのため、holdout には、非公開か、新しく作ったか、モデルの知識の時点より後のタスクを優先する。
- 出どころを `provenance` に記録する。汚染の疑いは `contamination_notes` に記録する。

## 6. 評価データの分離（D05）

### 6.1 分割

| 分割 | 用途 | 置き場所 | 開発の側に返す情報 |
|---|---|---|---|
| Dev | 開発とデバッグ | 開発のリポジトリ | 詳しく返す（タスクごとの結果、ログ、成果物） |
| Validation | 構成や機能の選択 | 開発のリポジトリ（ただし、開発の作業の中で中身を見ない運用にする） | タスクごとの結果まで。エラーの詳細は、必要なものだけ |
| Holdout | 独立した最終的な性能の評価 | **独立した非公開のリポジトリ**（D3）。開発の側の AI には接続しない | C2 の11.1 の制限した集計だけ |

### 6.2 holdout の使い方

- **holdout の結果を使って、機能を何度も調整することは禁止する。**
- 使ってよいのは、Phase 3D の採用の判定などの、事前に登録した節目だけ。
- **使う回数（候補の値。PROVISIONAL）：** holdout の1つの版につき、主な判定に1回、確認のための再評価に1回まで。使った回数は Experiment Registry に記録する。
- **公開する集計（C2 の11.1）：**
  - 全体の点数と信頼区間、分類ごとの件数を出す。
  - 件数が下限に満たない分類は、まとめる。下限の候補は、分類ごとに 10 タスク以上（PROVISIONAL）。
  - タスクごとの結果と、エラーの詳細は出さない。
- **入れ替える条件：**
  - 使う回数の上限に達した。
  - 漏えいの疑いがある（開発の側の記録や記憶に、holdout のフィンガープリントが見つかった）。
  - 評価するモデルが、新しい知識の時点のものに変わった。
  - 一定の期間（候補は 1年。PROVISIONAL）が過ぎた。

### 6.3 重複、類似、既存の知識による汚染

- **重複と類似：** 分割の間で、ハッシュ、似た文章、同じ元のリポジトリとコミット、同じ課題番号を照合する。似ているものは、同じ分割にまとめる。照合は、評価の側で行い、結果だけを開発の側に知らせる。
- **既存の知識による汚染：**
  - holdout に目印の文字列（canary）を入れ、モデルの出力に現れないかを見る。
  - 公開された課題だけで作ったタスクは、参考の扱いにする。
  - 汚染を完全に確かめる方法はない（残存リスク）。

## 7. 採点（D06、C2-P06）

### 7.1 結果の分類（タスクごとに、事前に定義する）

| 結果 | 定義 | 集計での扱い |
|---|---|---|
| `SUCCESS` | 成功の条件をすべて満たした | 成功 |
| `PARTIAL` | 部分的な成功の条件を満たした（評価の基準と点数を事前に定義する） | 成功率では失敗として数える。品質の指標では、部分の点数を使う |
| `FAIL` | 失敗の条件に当たった、または成功の条件を満たさなかった | 失敗 |
| `TIMEOUT` | 時間の上限を超えた | 失敗。件数を別に報告する |
| `BUDGET_EXCEEDED` | 予算を超えて止まった | 失敗。件数を別に報告する |
| `SAFETY_VIOLATION` | 安全上の規則に違反した | 失敗として数える。さらに、安全性の指標として別に数える（Safety Gate） |
| `INVALID_ENV` | 評価の環境の障害（Agent の責任ではない） | 無効な試行として、集計から外す。件数と理由を報告する（8.5） |

### 7.2 採点の方法

- **コーディングのタスクでは、客観的なテストを優先する。** 隠しテスト、後退していないかのテスト、ビルド。
- **テストに合格しただけでは、あらゆる品質が保証されたとはみなさない。** 品質の指標（1章）を、別に集計する。
- **評価する対象の、自分自身の成功の報告は、正式な採点の結果として使わない**（C2 の X23）。
- **AI による採点を使う場合：**
  - 採点の基準、採点に使うモデルとその版、プロンプトを、事前に固定する。
  - 一部のタスクを人間が採点し、AI の採点との一致度を測る。一致度の基準は事前に決める。
  - 採点の偏り（長い回答を高く評価する、同じ系統のモデルを高く評価する、など）を確かめる。
  - 同じ入力で採点を繰り返し、結果が再現するかを確かめる。
  - 一致度を確かめるまでは、副の指標としてだけ使う。
  - AI による採点も `MODEL_CALL` であり、評価の側の費用として数える。

### 7.3 ブラックボックスと in_process の区別（C2-P06）

- 採点の記録には、`assurance` を必ず付ける。
- **集計は、`assurance` ごとに分けて行う。** ブラックボックスと同じ信頼性のものとして、まとめて集計しない。
- **正式に「性能が向上した」と主張できる条件：**
  1. 主仮説の判定（8.6 の `IMPROVED`）が、ブラックボックスの方式で採点したタスクの集合だけで成り立つ。
  2. `in_process` の集合での結果は、補助の証拠として示すだけ。その結果が主仮説と逆の方向なら、主張を保留する。
  3. ブラックボックスの方式で採点したタスクの割合と件数を、報告する。
- `in_process` の集合だけで得られた改善は、「探索的な所見」として扱う。

## 8. 統計的な評価（D07）

### 8.1 標本の単位

- **単位は、タスク**（一連の作業を評価する場合は、その作業の並び。B2 の11章）。
- 同じタスクの、繰り返しの試行は、そのタスクの成功の確率を推定するために使う。**独立した標本として数えない。**

### 8.2 対応のある比較

- 比べる構成どうしで、同じタスクの集合を使う。
- タスクごとに、成功の確率の差 d_t = p̂_t(Agent Core) − p̂_t(比較の相手) を計算する。
- 主な推定値は、タスクの間での平均の差 Δ̄（パーセントポイント）とする。

### 8.3 信頼区間

**主な方法：** タスクを単位として、ブートストラップで信頼区間を求める。

- タスクを、置き換えながら取り出す。
- その中で、同じタスクの試行をまとめて扱う。

**感度の分析：** タスクを変量効果とする、混合効果のロジスティック回帰でも確かめる。

**報告するもの**

- 効果の大きさ：差（パーセントポイント）を主な指標にし、比も併せて出す。
- 費用と時間：裾が重いことが多いので、中央値と、対数で変換した後の平均の比を出す。信頼区間は、ブートストラップで求める。

### 8.4 検出力と、必要な件数

- 予備の評価（20〜50 タスク、タスクごとに k 回）で、次を見積もる。
  - タスクの間のばらつき σ_b²
  - タスクの中のばらつき σ_w²
  - 効果の大きさの、おおよその値
- 差の推定値の分散は、おおよそ σ_b²/T ＋ σ_w²/(T·k) になる（T はタスクの数）。
  - **試行の回数 k を増やしても、タスクの間のばらつきは減らない。** タスクの数 T を増やすほうが、効果が大きい。
- 正式な評価のタスクの数と試行の回数は、シミュレーションで決める。条件は、承認された改善の幅（9.3）を、検出力 80%（候補の値。PROVISIONAL）で見つけられること。その結果を、事前登録に書く。
- 費用の上限の中で必要な件数を満たせないときは、正式な評価を行わない。予備の評価として扱う（`INCONCLUSIVE` の見込みであることを、先に明示する）。

### 8.5 多重比較、外れ値、欠けたデータ、無効な試行

| 項目 | 扱い |
|---|---|
| 多重比較 | 主仮説は1つ（Agent Core と Baseline B の、主な指標の比較）。副の仮説には、Holm の方法で補正をかけるか、「探索的なもの」と印を付ける。アブレーションは、Holm で補正する |
| 外れ値 | 取り除かない。費用と時間には、頑健な統計量（中央値、刈り込み平均）を使い、取り除かない場合の結果も併せて報告する |
| 欠けたデータ | 無効な試行は、事前に決めた回数（候補は2回）まで、やり直す。それでも残った分は、欠けたものとして報告する。<br>感度の分析として、最悪の場合（Agent Core の側は失敗、比較の相手の側は成功）でも結論が変わらないかを確かめる |
| 評価の環境の障害 | `INVALID_ENV` の割合を、構成ごとに報告する。構成によって割合が大きく違う場合は、結論を保留して調べる |

### 8.6 結論の4つの分類

- 「良い」方向を正とする。費用と時間は、符号を反転させる。
- 主な指標の差 Δ の、両側 95% の信頼区間を [L, U] とする（候補の値。PROVISIONAL）。
- 事前に承認した値として、次の2つを使う。
  - `δ_imp`：実用上意味のある改善の幅
  - `δ_ni`：非劣性の許容幅（> 0）

| 結論 | 条件 |
|---|---|
| `IMPROVED`（向上を確認した） | L > 0、**かつ**推定値 ≥ `δ_imp`。改善の方向（どの指標が、どちらへ）を明記する |
| `NON_INFERIOR`（非劣性を確認した） | L > −`δ_ni`。`IMPROVED` には当たらない |
| `DEGRADED`（低下を確認した） | U < 0。さらに U < −`δ_ni` なら、実用上の低下として印を付ける |
| `INCONCLUSIVE`（証拠が足りず、結論を出せない） | 上のどれにも当たらない |

- **信頼区間が 0 を含まないことだけでは、性能が向上したとは言わない。** 方向と、`δ_imp` との関係を必ず示す。
- **有意な差がないことを、性能が同じであることの証明とはみなさない。** 「同じ」と言えるのは、事前に許容幅を定めた同等性の判定を通った場合だけ。それも、事前に登録した場合に限る。
- 途中で結果を見て、止めたり延ばしたりすることはしない（事前に登録した中止の規則に従う場合を除く）。

## 9. 機能の採用の基準（D08）と、継続的な改善（D09）

### 9.1 3つのゲート

| ゲート | 内容 | 合格しない場合 |
|---|---|---|
| Technical Gate | 機能が仕様どおりに動く。各設計の不変条件と試験に合格する | 不採用 |
| Safety Gate | C1 と C2 の Safety Gate に合格する。評価の間に、安全の違反（`SAFETY_VIOLATION`）が 0 件。安全の指標が、比較の相手より悪くならない | **性能にかかわらず不採用** |
| Performance Gate | 9.2 の規則 A か B を満たす | 不採用、または `INCONCLUSIVE` |

### 9.2 採用の規則

- **規則 A：** 成功率か品質で `IMPROVED` となる。そのうえで、費用、時間、人間の介入が、事前に決めた制約の範囲内にある（悪くなっていても、許容幅の内側にある）。
- **規則 B：** 成功率と品質の両方で `NON_INFERIOR` となる。そのうえで、費用か時間で `IMPROVED` となる。
- どちらでもなく、どれかが `INCONCLUSIVE` の場合は、全体を `INCONCLUSIVE` とし、**採用しない**。その後の扱いは、追加の評価を新しい実験として登録し直すか、取りやめるか。
- 判定は、ブラックボックスの方式で採点した集合で行う（7.3）。

### 9.3 候補の値（実験の前にオーナーが承認する。どれも根拠のない確定の値ではない）

| 値 | 候補 | 考え方 |
|---|---|---|
| `δ_imp`（成功率） | +5 パーセントポイント | 予備の評価のばらつきを見て、検出できる幅かどうかを確かめてから決める |
| `δ_ni`（成功率・品質） | 3 パーセントポイント | 費用の改善と引き換えに許せる低下の上限 |
| 費用の改善として意味のある幅 | 成功1件あたりの費用で 15% 以上 | 価格の変動と照合の誤差より大きいこと |
| 時間の改善として意味のある幅 | p50 で 15% 以上 | 同じ |
| 人間の介入 | 増やさない（非劣性の許容幅 0.1 回／タスク） | 承認の疲れへの対策（C1） |
| 信頼区間 | 両側 95% | — |
| 検出力 | 80% | — |

### 9.4 アブレーションと、機能の間の相互作用

- **機能を1つずつ外す構成：** Context の最適化、Memory、Planning、Tool Selection、Verification、Recovery を、それぞれ外したものを作る。安全のために必須の機能（4.1）は外さない。
- **相互作用：** 相互作用が疑われる組（例：Context の圧縮と Memory）は、2×2 の組み合わせの実験で調べる。すべての組み合わせは調べない。費用が大きすぎるため。
- アブレーションの結果は、探索的なものとして扱い、Holm で補正する。

### 9.5 改善の流れ

```
改善の候補（CandidateChange）を作る
 → dev で試験する（Technical Gate）
 → validation で比較する（事前登録 → 実行 → 判定）
 → 独立審査
 → 採用（Decision に記録）
 → 監視（その後の validation と、運用の指標）
 → 悪くなった場合は、取り消し（ROLLBACK。採用の前の構成に戻す。根拠を記録する）
holdout は、事前に登録した節目（Phase 3D など）でだけ使う
```

### 9.6 評価の基準と、採点のプログラムを守る

- **AI が、評価の基準、採点のプログラム、タスクの集合、分析の計画を自動で変えて、高い点数を得ることは禁止する。**
- 守り方は次のとおり。
  - これらは、版を固定し、ハッシュで照合する。
  - 書き込めるのはオーナーだけ（holdout は C2 の10章。dev と validation の採点のプログラムも、オーナーの承認が必要な別の変更として扱う）。
  - Experiment Registry は、固定した仕様のハッシュと、実行したときの仕様のハッシュを照合する。
- 将来の Phase 6（継続的な改善）は、CandidateChange、ExperimentSpec、Decision を通して、この流れにつなぐ。ここでは、その本体は設計しない。

## 10. Cost Engine（D10）

### 10.1 費用の状態（設計A の4.1 を引き継ぎ、`reserved_cost` を加える）

| 項目 | 意味 |
|---|---|
| `estimated_cost` | 価格表と、トークンなどの使用量から計算した、内部の見積もり |
| `safety_margin` | 価格表のずれと、推定の誤差に備えた上乗せ |
| `reserved_cost` | 実行の前に予約した額（見積もりの上限 ＋ 上乗せ） |
| `pending_cost` | 結果が分からない呼び出しの費用。上限の見積もりで計上し続ける |
| `reconciled_cost` | プロバイダーの利用の実績や、請求と照合して確定した額 |
| `unexplained_diff` | 説明のつかない差額 |

### 10.2 費用を計算する対象

- モデルの呼び出し：入力トークン、出力トークン、キャッシュの書き込みと読み込み
- 補助的なモデルの呼び出し：要約、関連度の判定、計画の立て直し、記憶の抽出と検証、AI による採点
- 検索、ツール、外部の API
- 再試行、失敗した呼び出し、結果が分からない呼び出し
- Sandbox（CPU の時間、メモリ）、ストレージ

**2つに分けて集計する（必要なら合計も出す）**

| 区分 | 中身 |
|---|---|
| `agent_cost`（AI の実行の費用） | Agent が仕事をするためにかかった費用 |
| `eval_infra_cost`（評価の環境の費用） | 次の費用。<br>- ベンチマークの維持<br>- 採点の実行（AI による採点を含む）<br>- 評価の側のホストと VM<br>- 人間による確認の時間 |

### 10.3 価格表

`{price_table_id, version, currency, effective_from, effective_to, source: {ref, verified_by, verified_at}, status: test|verified|unverified, items: {model_id: {input_per_mtok, output_per_mtok, cache_write_per_mtok, cache_read_per_mtok}, tool_or_api: {...}, sandbox: {cpu_second, gb_hour}, storage: {gb_month}}}`

- 費用の記録は、どれも `price_table_id@version` を持つ。
- 実際のプロバイダーの価格表は、オーナーが出典を確かめてから、`verified` として登録する。今回は調べていない。

**試験用の仮想の価格表（実際の価格ではない）**

```
price_table_id: test-virtual-v1
currency: XTU（試験用の単位。米ドルではない）
status: test
items:
  scripted-model-small: {input_per_mtok: 1.0, output_per_mtok: 4.0, cache_write_per_mtok: 1.25, cache_read_per_mtok: 0.1}
  scripted-model-large: {input_per_mtok: 5.0, output_per_mtok: 20.0, cache_write_per_mtok: 6.25, cache_read_per_mtok: 0.5}
  sandbox: {cpu_second: 0.0001, gb_hour: 0.001}
  storage: {gb_month: 0.01}
```

- 通貨を `XTU` にするのは、実際の価格と取り違えないため。
- 本番のモード（試験用の印のない設定）では、`status: test` の価格表を読み込めないようにする（C1 の9.7 と同じ考え方）。

## 11. 予算の強制（D11）

### 11.1 上限の階層

```
1回のモデル呼び出し ⊆ Step ⊆ Run ⊆ ユーザー ⊆ テナント ⊆ 月間
実験全体 ⊆ テナント ∩ 月間
```

- **予約：** 予約するときは、P1 の1つのトランザクションで、関係するすべての階層の「確定額 ＋ 予約額 ＋ 未確定の額 ＋ 新しい予約 ≤ 上限」を確かめてから、すべての階層に同時に記録する（設計A の I5 を階層全体に広げたもの）。
- **二重に使わない：** 予約は、`attempt_id` に結び付ける。1つの予約を、2つの呼び出しで使うことはできない（設計A の A04、C1 の7.5）。
- **結果が分からない操作：** 照合できるまで、上限の見積もりで計上し続ける。
- **再試行：** 新しい予約が必要。
- **予算が足りない場合：** その Run は `PAUSED_BUDGET` に移り、実行を止める。実験の予算が尽きたら、その実験の新しい試行を始めない。
- **プロバイダー側の支出の上限：** 確かめるまでは、厳密に止まる仕組みとしては扱わない（設計A の A09）。

### 11.2 金銭以外の上限（Run 全体が際限なく続かないようにする。B1-P04 の一部）

| 上限 | 範囲 | 候補の値（PROVISIONAL） |
|---|---|---|
| モデル呼び出しの総回数（補助を含む） | Run・実験 | 200 回／Run |
| ツールの実行の回数 | Run | 300 回／Run |
| 文脈の組み立て直しの回数 | Run | 50 回／Run |
| 計画の立て直しの回数 | Run | 10 回／Run |
| 記憶の抽出と検証 | Run・テナント | 20 回／Run |
| 再試行の回数（種類をまとめた合計） | Run | 30 回／Run |
| 総実行時間（経過時間） | Run・実験 | タスクの `timeout`。Run の上限は 2 時間 |
| **すべての操作の合計（作業単位）** | Run | 上の合計の上限とは別に、1つの総数の上限を持つ |

- 個別の上限を守っていても、合計の上限に達したら止める。
- 値はタスクの種類ごとに、事前登録で決める。
- 処理の順序（Safety の判定、予約、Intent、Permit）の統一は、E で行う。

### 11.3 実API を使う前の承認（Phase 3 以降、D1）

- 実API を使う実験は、どれも、実行の前に**オーナーの承認**（`SpendApproval`）が必要。承認する内容は次のとおり。
  - 試行の回数（タスクの数 × 試行の回数 × 構成の数）
  - 費用の見積もり（見積もりの方法と、上乗せの幅）
  - 最大の費用（その実験の、厳密な内部の上限）
  - 月間の上限
- **Phase 3 以降も、費用は自動では承認しない。**
- 承認を超えそうになったら、新しい試行を始めずに止め、オーナーに確認する。

## 12. 費用の評価と照合（D12）

### 12.1 指標

| 指標 | 定義 |
|---|---|
| 1タスクあたりの費用 | 総費用 ÷ 試行の数（無効な試行の費用は、別に報告する） |
| **成功1件あたりの費用** | **失敗したタスクの費用も含めた**総費用 ÷ 成功の件数。**成功が 0 件なら未定義** |
| 品質を保つための費用 | 事前に決めた品質の水準に達するまでの費用（4.2） |
| 失敗したタスクの費用 | 失敗、時間切れ、予算超過の試行の費用の合計と、その分布 |
| 人間の介入の時間 | 承認、確認、手で直したときの分数の合計と、1タスクあたりの値 |
| 長時間の運用での費用 | 連続した作業や、長時間のタスクで、時間あたり、作業単位あたりの費用がどう変わるか |
| 初期の費用と、維持の費用 | 立ち上げ（評価の環境、記憶の作成など）と、続けるための費用（再検証、保存、評価の環境の維持）を分ける |

- 成功と失敗の件数は、必ず一緒に示す。隠さない。

### 12.2 照合（設計A の A09 を引き継ぐ）

- 照合の合格の条件（設計A の4.1）は変えない。
  - `unexplained_diff = 0`
  - 説明できる差額が、許容誤差の範囲内
  - 実際の請求が、承認した上限の範囲内
- **許容誤差の候補（オーナーが承認する。PROVISIONAL）：** 照合の期間（実験ごと、または1日ごと）について、説明できる差額の合計の絶対値を、次の大きいほう以下にする。
  - 1.00 米ドル
  - 照合して確定した額の 2%
- **説明のつかない差額を、許容誤差の中に隠さない。** 説明のつかない差額は、金額にかかわらず、その実験の新しい支出を止めて調べる理由になる。
- 試験の段階（Phase 1〜2）では、`XTU` の仮想の価格表と、偽の利用の実績で、照合の処理を試す。

## 13. 実験の再現性と管理（D13）

### 13.1 実験ごとに記録する項目

- `experiment_id`
- Agent Core のコミットの SHA、構成のハッシュ（`config_hash`）
- モデルの ID と版、`ModelProfile@version`、推論の設定
- タスクの集合の版、採点のプログラムの版、`assurance` の内訳
- Sandbox の構成（`sandbox_profile_hash`）、ポリシーの版（`policy_version`）
- 予算と、承認（`SpendApproval`）、価格表の版
- 実行の順番、乱数の種、試行の回数
- 成功、失敗、無効な試行の件数と理由
- 実行の時間、費用（状態ごと）
- 評価の結果の信頼度（`assurance`、無効な試行の割合、条件の違い（`condition_deviations`））
- 事前登録の仕様のハッシュ（`spec_hash`）と、登録した時刻

### 13.2 固定と、実行の順番

- 評価の条件と採用の基準は、実験を始める前に固定する（`spec_hash` を Journal と Results Store に記録する）。
- 実行の順番は、構成とタスクを無作為に交ぜて決める。こうして、時間の経過による変化（プロバイダーの側の負荷や変更）が、特定の構成に偏らないようにする。乱数の種を記録する。

### 13.3 再現性の限界

- モデルの出力は、同じ条件でも毎回同じになるとは限らない。プロバイダーの側でモデルや設定が変わることもある。
- そのため、完全に同じ結果になるとは限らない。
- 再現性は、「同じ仕様で実行し直したときに、結論（8.6 の分類）が変わらないか」で確かめる。数値が完全に一致することは求めない。
- モデルの ID、版、日付を記録し、変わったことが分かった場合は、比べてよい範囲を限る。

|---|---|
| V1 | 評価の条件、指標、分析の計画、採用の基準は、実行の前に固定し（`spec_hash`）、実行の後に変えない |
| V2 | 標本の単位はタスク（または一連の作業）。同じタスクの繰り返しを、独立した標本として数えない |
| V3 | 安全のために必須の機能は、どの構成でも外さない。Safety Gate を通らない構成は、採用しない |
| V4 | 評価する対象の、自分自身の成功の報告は、正式な採点に使わない |
| V5 | ブラックボックスと `in_process` の結果を、まとめて集計しない。正式な「向上」の主張は、ブラックボックスの集合で成り立つときだけ |
| V6 | 結論は `IMPROVED`、`NON_INFERIOR`、`DEGRADED`、`INCONCLUSIVE` のどれか。有意な差がないことを、同じであることの証明にしない |
| V7 | holdout の結果で、機能を繰り返し調整しない。使った回数を記録し、上限を守る |
| V8 | AI は、評価の基準、採点のプログラム、タスクの集合、分析の計画を変えられない |
| V9 | 成功1件あたりの費用は、失敗の費用を含めた総費用で計算する。成功が 0 件なら未定義。成功と失敗の件数を必ず示す |
| V10 | 予約は、関係するすべての階層の上限を、1つのトランザクションで確かめる。1つの予約を二重に使わない。結果が分からないものは、上限の見積もりで計上し続ける |
| V11 | 金銭以外の上限と、Run 全体の作業単位の上限を持つ。どれかに達したら止める |
| V12 | 実API を使う実験は、事前にオーナーが承認した、試行の回数、見積もり、最大の費用、月間の上限の範囲でだけ行う。自動では承認しない |
| V13 | 説明のつかない差額を、許容誤差の中に隠さない |
| V14 | 試験用の価格表（`XTU`、`status: test`）を、本番のモードで使わない |
| V15 | 判定に使えない比較（Baseline C、条件をそろえられなかったもの）は、参考の値として印を付ける |

## 16. ゲート

**ゲートに合格しても、評価が完全に正しいことの証明にはならない。**

### 16.1 Technical Gate（評価の仕組みそのもの）

| 試験 | 合格の目安 |
|---|---|
| 模擬データ（効果の大きさが分かっているもの）での統計のプログラム | 効果がない設定で、`IMPROVED` と判定する割合が、名目の値（2.5%）程度。決めた効果の大きさで、計画どおりの検出力が出る |
| タスクの単位でのブートストラップの実装 | 繰り返しを独立に数えた場合と比べて、信頼区間が正しく広がることを確かめる |
| 事前登録の固定 | 固定した後に仕様を変えた実行が、拒否される割合 100% |
| 予約の階層 | 同時に実行した場合や、障害が起きた場合でも、どの階層でも上限を超えた件数 0 |
| 金銭以外の上限 | 各上限と、合計の上限で止まる割合 100% |
| 照合 | 偽の利用の実績に、説明できる差額と、説明のつかない差額を入れたとき、正しく分類する割合 100% |
| 再現性 | 同じ仕様と同じ乱数の種で、ScriptedProvider を使ったとき、結果が完全に一致する |

### 16.2 Safety Gate（評価の仕組みに関わる安全）

| 試験 | 合格の目安 |
|---|---|
| 安全のために必須の機能を外した構成を登録しようとする | 拒否される割合 100% |
| AI（評価する対象）が、採点のプログラム、タスク、基準、分析の計画を書き換えようとする | 成功した件数 0 |
| holdout を、開発の側から使おうとする。使う回数の上限を超えようとする | 成功した件数 0 |
| 承認のない実API の実験、承認を超える支出 | 始まった件数 0。上限を超えた件数 0 |
| 試験用の価格表を、本番のモードで読み込もうとする | 拒否される割合 100% |
| 評価する対象の自己申告で、成功にしようとする | 採用された件数 0 |

### 16.3 Performance Gate

- 9.1・9.2 のとおり。判定は、事前登録した実験の結果だけで行う。

## 18. 残存リスク

1. **既存の知識による汚染：** モデルが既に学習している内容による汚染は、完全には確かめられない。
2. **検出力の不足：** 費用の上限のために、十分なタスクの数を確保できず、`INCONCLUSIVE` が続く可能性がある。
3. **Baseline B の妥当性：** 独立審査に頼る。「実用として妥当」の線引きに、主観が残る。
4. **AI による採点の偏り：** 人間の採点との一致度を確かめても、偏りが残りうる。
5. **プロバイダーの側の変更：** モデルや設定が評価の途中で変わると、比べられる範囲が狭くなる。
6. **in_process の方式に頼るタスク：** ブラックボックスにできないタスクが多いと、正式に主張できる範囲が狭くなる。
7. **候補の値の妥当性：** 9.3 などの候補の値は、予備の評価の前の仮の値である。
8. **費用の照合：** 利用の実績の粒度や、反映の遅れは確かめていないので、照合の精度は不明。
9. **初回報告書との照合：** 初回報告書の全文と照合していない。

## 19. 未確認事項（外部調査は行っていない）

- 実際のプロバイダーの価格、課金の単位、キャッシュの料金の体系、失敗したリクエストへの課金。
- プロバイダーの利用の実績の取得の方法、粒度、反映の遅れ。
- プロバイダーの側の支出の上限が、厳密に止まるかどうか。
- Baseline C に使う外部のエージェントの製品、版、条件をどこまでそろえられるか。
- 予備の評価の前の、ばらつきと効果の大きさ。
- 模擬データで確かめる統計の方法の、細かい性質（少ないタスクの数での、ブートストラップの信頼区間の精度など）。
