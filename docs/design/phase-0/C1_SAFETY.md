## 0. 基本方針

1. **最小権限とデフォルト拒否：** はっきり許可していない操作は、すべて拒否する。
2. **信頼しないものを決めておく：** AI モデル、外部ツール、取得した文書、生成されたコード、MCP サーバー、外部の Web サイトは、信頼できないものとして扱う。
3. **判断と強制を分ける：** 許可するかどうかを判断する部分（PDP、Safety Engine）と、実際に強制する部分（PEP、Execution Broker と Egress Gateway）を分ける。どちらも AI モデルからは独立している。
4. **AI の判定だけに頼らない：** 文章を見て危険かどうかを判定する仕組みは、制限を加える方向にだけ使う。許可を与えることには使わない。
5. **試験で違反が 0 件でも、安全の証明にはしない：** 見つかっていない経路は残る（12章）。

## 1. 脅威モデル（C01）

### 1.1 主体と、信頼の度合い

| 主体 | 信頼の度合い | 持てる権限 |
|---|---|---|
| オーナー | ポリシーについては信頼する。ただし、アカウントが乗っ取られる可能性は残る | ポリシーの変更、ツールと MCP の登録、緊急停止と再開、予算の上限 |
| 一般ユーザー | 自分のタスクの意図については信頼する。ポリシーについては信頼しない | 許されたプロジェクトでタスクを作ること。委ねられた範囲での承認 |
| Runtime（Orchestrator） | **信頼の基盤（TCB）** | Journal、Ledger、Permit の発行 |
| Safety Engine（PDP） | TCB | 判定だけ。実行はしない |
| Execution Broker・Egress Gateway（PEP） | TCB | 副作用のある操作を実行する、唯一の経路 |
| AI モデル | **信頼しない** | なし。モデルの出力は「提案」にすぎない |
| Worker | 2つに分ける（2.1）。信頼する制御の部分（Worker-Control。Broker の一部）と、信頼しない実行の部分（Worker-Exec。Sandbox の中で動くプロセス） | Worker-Control：Permit の扱い、コピー、コンテナの制御。Worker-Exec：権限なし（15章の CP-3） |
| Sandbox | 中身は信頼しない。境界の仕組みだけに頼る | ワークスペースの写しと、上限のある資源だけ |
| Tool Adapter | Agent Core が作り、リリースとハッシュを固定した `builtin` のものだけを信頼する。それ以外のアダプターは信頼せず、Sandbox の中で動かす（2.1、5.3） | マニフェストで宣言し、ポリシーで許した範囲だけ |
| MCP サーバー | **信頼しない** | 登録済みで、版が固定されたツールだけを、PEP を通して使う |
| 外部の Web サイト | **信頼しない** | なし。応答は D2 として扱う |
| Model Provider | 契約の範囲で、機密を守ることだけを信頼する。送ったデータは、Agent Core の管理から外れる | なし |
| 永続ストレージ | Sandbox からは触れられない場所に置く。完全性はハッシュの連鎖で確かめる | — |
| 評価環境 | 開発の環境とは別にする（詳細は C2） | 評価用の権限だけ |

**TCB（信頼の基盤）に含めるもの：** Orchestrator、Journal と Ledger、PDP、PEP（Broker と Gateway）、Sandbox を起動する部分、鍵を使う部分（C2）。TCB は小さく保つ。

### 1.2 想定する攻撃者

| ID | 攻撃者 | 例 |
|---|---|---|
| T1 | 外部の悪意あるコンテンツ | Web、文書、リポジトリ、ツールの出力、MCP の結果に、指示を紛れ込ませる（プロンプトインジェクション） |
| T2 | 悪意のある、または乗っ取られた MCP サーバーやツール | ツールの説明文に毒を仕込む、ツールの定義を後から差し替える、データを持ち出す |
| T3 | モデルの誤った振る舞い | 根拠のない破壊的な操作、評価の抜け道を突く行動 |
| T4 | 生成された悪意あるコード | Sandbox からの脱出、資源を使い尽くす、データを持ち出す |
| T5 | 悪意のある一般ユーザー | 他のテナントへのアクセス、権限の格上げ（マルチテナント化の後で重要になる） |
| T6 | ネットワーク上の攻撃者 | DNS の書き換え（rebinding）、SSRF、中間者攻撃 |
| T7 | 供給網 | 依存関係やコンテナイメージの改ざん（一部だけ対象にする） |

### 1.3 守る資産

- 認証情報（API キー）
- ホストの完全性
- ユーザーのコードとデータ
- 記憶（B2）
- Journal、Ledger、削除台帳の完全性
- 予算（実際のお金）
- holdout と評価の完全性
- ポリシーの完全性
- 稼働し続けること（二次的）

### 1.4 防御の範囲

| 防御する | 防御しきれない（残存リスク） |
|---|---|
| 権限のない操作の実行、ファイルの境界の回避、許可していない外部通信 | カーネルの未知の脆弱性（0-day）を使ったコンテナからの脱出（対策は取るが、保証はしない） |
| モデル・Sandbox・ログに認証情報がさらされること | ホストの OS や管理者の権限が乗っ取られること |
| 承認の改ざん、承認や Permit の使い回し | プロバイダーの側での漏えい |
| 外部情報による権限の格上げ、ポリシーの変更 | 処理時間などのサイドチャネル、物理的なアクセス |
| Sandbox の中での資源の使い尽くし、緊急停止 | オーナーが内容を理解せずに、悪意ある操作を承認すること（表示を工夫して減らすだけ） |
| | 許可した通信経路を使った持ち出し（狭めることはできるが、なくせない。10章） |
| | 悪意のある内容を、完全に見分けること |

## 2. アーキテクチャ

```
 オーナー／ユーザー ─(認証された経路)─▶ Policy Store（版付き）・Approval Service
                                              │
 AI モデル ─(提案)─▶ Orchestrator ──▶ PDP（Safety Engine：判定だけ、副作用なし）
                         │  Permit を発行     │
                         ▼                    ▼
              ┌──────── PEP：Execution Broker（副作用の唯一の経路）────────┐
              │ Sandbox Controller │ File Broker │ MCP Client │ Model Client │
              │ Memory Access（Runtime の内部だけ）                        │
              └───────┬──────────────────────────────┬──────────────────┘
                      ▼                              ▼
          Sandbox（Docker、コンテナごとに        PEP：Egress Gateway（外部通信の唯一の出口）
           独立したネットワーク、--network none）  ├ 接続先の登録簿・DNS の固定・内部アドレスの遮断
                                                  ├ 認証情報の注入（ここでだけ行う）
                                                  └ 緊急停止の印を、リクエストごとに確かめる
                                                         ▼
                                       Model Provider／MCP（リモート）／Web／外部 API
```

- PDP は、副作用を持たない判定の関数である。入力は、ポリシー、Run の権限、ActionDescriptor（7章）、状態（epoch と拒否リスト）。
- PEP は、Permit を確かめてから実行する。PDP の判定だけでは何も実行されない。
- Phase 1〜2 は単一のマシンで動かす。プロセスの分け方は 2.1 のとおり。Sandbox の中からは、Gateway 以外のネットワークにも、Broker の制御用の API にも届かない。

### 2.1 プロセスの境界と、TCB の権限の分離（C1-R05）

| プロセス | 信頼 | 持つもの | 持たないもの |
|---|---|---|---|
| P1 Orchestrator | TCB | Journal への書き込み（唯一）、PDP、Permit の発行と消費の処理（7.5） | ネットワーク（プロセス間通信だけ）、Docker の API、認証情報 |
| P2 Broker（Worker-Control） | TCB | Docker の API（唯一）、ワークスペースへのコピーと取り出し、`builtin` のアダプター、stdio の MCP の制御 | Journal への直接の書き込み（P1 に依頼する）、外部ネットワーク（Gateway を通すだけ）、認証情報 |
| P3 Gateway | TCB | 外部ネットワーク（唯一）、認証情報（唯一） | ワークスペース、Docker の API、Journal への直接の書き込み |
| P4 Sandbox（Worker-Exec、MCP のサーバー、信頼しないアダプター） | 信頼しない | 上限のある資源と、ワークスペースの写し | 上のすべて |

**OS のレベルで分ける方法**

- P1〜P3 を、それぞれ別の OS ユーザーで動かす。
- ファイルの権限で、触れられるものを分ける。
  - `journal.db` は P1 だけ。
  - 認証情報の保存先は P3 だけ。
  - Docker のソケットのグループは P2 だけ。
- P1〜P3 の間は、Unix ドメインソケットで通信する。接続してきた相手の資格情報（`SO_PEERCRED`）を、P1 の側で確かめる。Windows での同じ仕組みは未確認。

**段階ごとの扱い**

- **Phase 1〜2：** P1〜P3 は別のプロセスにし、別の OS ユーザーを推奨する。
  - 同じ OS ユーザーで動かす場合は、「論理的に分けただけ」と記録する。
  - この時期は、D1 により認証情報が存在しないので、P3 が認証情報を持つことによる危険はまだない。
- **Phase 3A より前：** 認証情報を持つ P3 を別の OS ユーザーにすることを**必須**にする。

**限界：** コードの中で呼び出しの経路を禁止しても、OS のレベルで隔離したことにはならない。同じプロセスや同じ OS ユーザーの中では、コードに不具合があったり乗っ取られたりすると、境界を越えられる。

## 3. 信頼境界

| 境界 | 越えるデータ | 越える権限 | 境界での検査 |
|---|---|---|---|
| モデル → Orchestrator | ツール呼び出しの提案（構造化された形）、テキスト | なし | スキーマの検証。マニフェストの版が固定されているかの確認。自然な文章で書かれた説明は、判定に使わない |
| Orchestrator → Sandbox | コマンド、ワークスペースの写し | Permit の範囲だけ | Permit の検証、パスの検証、資源の上限 |
| Sandbox → Orchestrator | 標準出力、終了コード、成果物 | なし | 大きさの上限、スキーマの検証。D1 として扱う。シンボリックリンクなどを除外する（8.3） |
| Sandbox → ネットワーク | — | 原則なし | `--network none`。許可した場合だけ Gateway を通す |
| Broker → Gateway → 外部 | リクエスト本体 | 接続先ごとの認証情報（Gateway の中だけ） | EgressCheck、Permit と request_hash の照合、DNS と IP の検査 |
| 外部 → Broker | 応答 | なし | 大きさと時間の上限。D1／D2 として扱う |
| ユーザー・オーナー → Runtime | タスク、承認、ポリシーの変更 | 役割の範囲 | 認証、承認の中身の表示（7.3） |
| Runtime → 永続ストレージ | Journal、blob、鍵 | Orchestrator だけ | Sandbox からは触れられない。整合性の検証（A、B2） |
| 開発の環境 ↔ 評価環境 | 評価の結果だけ | なし | C2 |

## 4. 権限管理（C02）

### 4.1 役割

| 役割 | できること | できないこと |
|---|---|---|
| `owner` | ポリシーの変更、ツールと MCP の登録・再審査、緊急停止と再開、予算の上限の設定、すべての承認 | — |
| `user` | 許されたプロジェクトでタスクを作ること。自分の Run の中での、委ねられた種類の承認（例：Sandbox の中でのテストの実行） | ポリシーを緩めること、ツールの登録、他人の Run への承認 |
| `system`（Runtime） | Permit の発行、記録 | 自分で権限を広げること |
| AI モデル | **権限を持たない** | 提案すること以外のすべて |
| `evaluator`（評価の実行） | 評価用の名前空間の中だけ | 開発用のデータや holdout の正解への直接のアクセス（C2） |

### 4.2 権限の階層（下へ行くほど狭くなる）

```
テナントのポリシー ⊇ プロジェクトのポリシー ⊇ Run の権限（RunGrant） ⊇ 1回の操作の Permit
```

**RunGrant（Run を作るときに PDP が計算し、Journal に記録する）**

| 項目 | 内容 |
|---|---|
| `tools[]` | 使ってよいツール。`tool_id@version@manifest_hash` で固定する |
| `files` | ワークスペース内の、読み込みと書き込みの範囲 |
| `destinations[]` | 通信してよい接続先の ID（9章） |
| `model_profiles[]` | 使ってよいモデルのプロファイル |
| `authorized_scope` | 記憶の範囲。`AuthorizedScope`（B2 の4.1、P-1） |
| `budget_caps` | 予算の上限（金額、回数、時間。Run 全体の上限は B1-P04 で、D と E が決める） |
| `approval_rules` | 承認が必要になる条件 |
| `policy_version`, `access_epoch_at_grant`, `expires_at` | 作ったときのポリシーの版、epoch、有効期限 |

**決まり**

- **デフォルト拒否：** RunGrant に載っていない操作は、すべて拒否する。
- **有効期限：** 長さの順に並べると、RunGrant（Run の期限まで）＞ 承認（短い）＞ Permit（さらに短い。初期値 60 秒、PROVISIONAL）。
- **権限の変更と失効：**
  - ポリシーを変えると、新しい `policy_version` になる。
  - 権限を狭める変更（失効、削除、ポリシーを厳しくする）では、テナントの `access_epoch` を1つ増やす（B2 の7.8）。
  - 実行中の Run の RunGrant は、次の判定から、すぐに狭まる。
  - epoch が古い Permit は、PEP で無効になる（7.4）。
  - **権限を広げる変更は、実行中の Run には自動では及ばない。** 新しい Run を作るか、オーナーが権限を付け直すことを承認する必要がある。
- **AuthorizedScope：** 次の情報から、PDP が決定的に計算する関数で作る。テナントのポリシー、プロジェクト、ユーザーの役割、RunGrant、`policy_version`、`access_epoch`。ハッシュを記録する。モデルからは指定できない（P-1）。

### 4.3 自分の権限を変えることの禁止と、ポリシーの変更

- Policy Store、RunGrant、マニフェスト、承認の記録は、Sandbox からもモデルからも届かない場所に置く。これらを書き換えるツールは、登録できない（S2）。
- エージェントは、ポリシーの変更を**提案**することだけができる。提案は D4 のデータとして扱う。
- 変更の手順は次のとおり。
  ```
  提案 → オーナーが、認証された経路で、差分を見て承認する → 新しい policy_version → 有効になる
  ```
- セキュリティポリシー（B1 の I1）を緩める変更には、オーナーの承認が必ず要る。一般ユーザーは、緩める承認ができない。

## 5. Tool Manifest と、実行する前の検証（C03）

### 5.1 宣言する項目

`tool_id`, `version`, `manifest_hash`, `kind`, `input_schema`, `output_schema`, `effect_class`, `external_guarantee`, `required_permissions[]`, `resources`, `destinations[]`, `timeout_ms`, `max_output_bytes`, `cost_estimate`, `approval_conditions`, `sandbox_profile`

- `kind`：`builtin`（Broker の中で動く、Agent Core のコード）／`sandboxed_command`／`mcp`／`model_call`
- `effect_class`：設計A の分類（`READ_ONLY` など）
- `external_guarantee`：外部サービスが冪等性を保証するかどうか（設計A の A08）
- `resources`：読み書きする資源。パスのパターンと、読み・書きの別
- `approval_conditions`：人間の承認が必要になる条件

マニフェストは、オーナーが登録する。`manifest_hash` で版を固定する。

### 5.2 宣言を信じず、実行するときに強制する

| 宣言 | 実行するときの強制のしかた |
|---|---|
| 入力と出力のスキーマ | PEP が、実行の前に入力を、実行の後に出力を検証する。合わなければ拒否する |
| `effect_class` | 宣言が `READ_ONLY` なら、ワークスペースを読み込み専用でマウントし、ネットワークは `none` にする。宣言を超える操作は、構造的にできない |
| `resources` | RunGrant の範囲と重なる部分だけを、マウントする。パスは、8.3 の方法で確かめる |
| `destinations` | Gateway が、Permit に載っている接続先だけを通す |
| `timeout_ms` | Broker が時間を測り、超えたらコンテナごと止める |
| `max_output_bytes` | 超えた分は切り捨てるか、成果物として保存する（B1 の5.3） |
| `cost_estimate` | 予算の予約に使う。実際の費用は Ledger で照合する |
| `approval_conditions` | PDP が判定し、承認を求める |
| `external_guarantee` | 復旧のときの扱いに使う（設計A の A08）。**宣言を信じて、自動で再実行することはしない**。保証が確かめられていない間は、`none` として扱う |

- **不明なツールは拒否する：** 登録されていないツール、`manifest_hash` が違うツール、版が固定されていないツールは、すべて拒否する（S8）。

### 5.3 マニフェストの固定と、実行コードの固定を分ける（C1-R05）

**マニフェストを固定しても、実際に動くコードが固定されたことにはならない。** そこで、登録するときに、次の `artifact_hash`（実行物の固定）も記録する。

| 対象 | 固定するもの |
|---|---|
| `builtin` のアダプター | Agent Core のリリースのハッシュ（そのアダプターのコードを含む） |
| コンテナのイメージ | イメージのダイジェスト |
| 起動の設定 | 入口のコマンド、引数のひな形、環境変数のひな形、作業ディレクトリ |
| 依存関係 | ロックファイルのハッシュ |
| Sandbox のセキュリティ設定 | `sandbox_profile` のハッシュ（8.1 と 8.6 の設定一式） |
| ローカルの MCP サーバー | パッケージ、またはイメージのダイジェスト |
| Policy Store | 版ごとのハッシュの連鎖と、オーナーの承認記録 |
| Broker と Gateway | リリースのハッシュ。起動するときの自己診断で照合する |

**決まり**

- 登録は `(manifest_hash, artifact_hash)` の組で行う。どちらかが変われば、登録済みのツールでも**再審査**する。それまでは拒否する。
- Permit には `artifact_hash` を含める。PEP は、実行するときに、実際のイメージのダイジェストと、コンテナの有効な設定（8.7）を照合する。
- 信頼しないアダプター（第三者が作ったもの、MCP のサーバーなど）は、TCB のプロセスの中では動かさない。必ず Sandbox の中で動かす。

## 6. Policy Enforcement Point（C04）と、処理の順序

### 6.1 迂回できないようにする方法

| 操作 | 唯一の経路 | 迂回を防ぐ方法 |
|---|---|---|
| コマンドの実行 | Broker → Sandbox Controller | Orchestrator にもモデルにも、シェルを渡さない。Sandbox の中に Docker のソケットを置かない。ホストでの直接の実行は、コードの中に存在しない（静的検査で確かめる） |
| ファイルの操作 | File Broker（ホストとの間のコピーと取り出し） | ホストのファイルはマウントしない。Sandbox の中のコマンドは、写しを直接操作できる。だから、境界は、コピーする範囲、マウントの ro と rw、取り出すときの検査で強制する（8.5） |
| 外部通信 | Egress Gateway | Sandbox は `--network none`、または Gateway だけに届く内部のネットワーク。Broker の Model Client と MCP Client も、Gateway を通す |
| MCP ツールの実行 | MCP Client（Broker の中） | stdio の MCP サーバーは、それ専用の Sandbox で動かす。リモートの MCP サーバーとは、Gateway を通してだけ通信する |
| モデルの呼び出し | Model Client（Broker の中） | Provider Adapter は、Broker の中にだけある。EgressCheck を通す |
| 記憶の取得と保存 | Runtime の内部（B2） | Memory の DB と blob は、Orchestrator のプロセスからしか触れない。取得は `MemoryQueryRequest`、保存は Journal のコマンドで行う |

### 6.2 処理の順序（設計E で統一するための提案）

```
① 提案              モデルが、構造化されたツール呼び出しを出す（権限なし）
② 検証              スキーマ、マニフェストの固定、RunGrant にあるか
③ 内容を確定        ActionDescriptor を作る（7.1）。モデルの呼び出しや外部通信の場合は、
                    最終的なリクエストを組み立てたうえで request_hash を計算する
④ PDP の判定        ポリシー、範囲、Safety の規則、EgressCheck（接続先、送る内容の区分。C2）
⑤ 承認              必要な場合だけ。action_hash に結び付ける
⑥ 予算の予約        設計A の4章
⑦ Intent の記録     設計A
⑧ Permit の発行     発行の直前に、PDP がもう一度判定する。epoch、拒否リスト、承認の有効性、緊急停止を確かめる
⑨ PEP の直前の検査  実行や送信の直前に、7.4 の検査を行い、7.5 の原子的な消費をする（B2-P02 の強制点）
⑩ 実行              Sandbox／Gateway
⑪ 結果の検査と記録  大きさ、スキーマ、機密の検査（C2）→ COMMITTED
```

- 設計A の Step の状態遷移（`SAFETY_CHECKED → APPROVED → BUDGET_RESERVED → INTENT_RECORDED → PERMIT_ISSUED → DISPATCHED`）とは、同じ順番になる。
- B1 の6.1 では予算の予約が Safety の判定より先にあり、この順番と食い違う。これを変更案 CP-1 とした（15章）。

## 7. 承認と Permit（C05、B1-P02、B2-P02）

### 7.1 ActionDescriptor（操作の内容を正規化したもの）

`{run_id, step_id, attempt_id, tool_id@version@manifest_hash, artifact_hash, sandbox_profile_hash, args_hash, target_resources[], rw_scopes, destinations[], request_hash?, effect_class, policy_version, access_epoch, cost_cap, reservation_id, expires_at}`

- `args_hash` は、引数を正規化（RFC 8785）してから計算する。
- `request_hash?` は、外部通信のときだけ含める。
- `action_hash` = H(正規化した ActionDescriptor)。
- 機密を含む引数やリクエストのハッシュは、推測攻撃に耐えられるように、用途ごとの鍵で計算した HMAC にする。鍵は C2 で決める（B1-P02 の後半）。

### 7.2 承認の記録

`{approval_id, action_hash | action_class, approver_id, approver_role, granted_at, expires_at, max_uses}`

- **1回の操作だけを承認する（ExactApproval、既定）：** `action_hash` に結び付け、`max_uses=1` にする。
- **範囲を決めた継続的な承認（ScopedApproval）：** 制約と、禁止する場合は 7.6 で定める。この場合も、実行のたびに、その都度の Permit が必要になる。
- 承認者の役割が、その承認に必要な役割を満たさなければ、承認は無効になる（B1 の3.4）。
- **引数や送信先が変わった場合：** `action_hash` が変わるので、承認はもう当てはまらない。承認か認可を、やり直さなければならない。

### 7.3 承認を求めるときの表示

- 承認を求める画面には、**実際の引数から作った** ActionDescriptor を見せる。モデルが書いた要約は見せない。
- 具体的には、実行するコマンド、対象のパス、送信先、送る内容の区分、費用の上限を見せる。

### 7.4 Permit と、PEP での直前の検査

**Permit の中身**

`{permit_id（128 ビットのランダムな値）, action_hash, access_epoch, issued_at, expires_at, mac}`

- `mac` は Permit 用の鍵で計算する。この鍵は、Orchestrator と PEP だけが持つ。

**PEP が実行や送信の直前に確かめること**（どれか1つでも満たさなければ拒否する）

1. MAC が正しい。**MAC は、PEP ではなく、P1 の消費のトランザクション（7.5）の中で検証する**（CP-9、E2）。PEP は、MAC を使わない項目だけを先に確かめる。
2. 期限が切れていない。
3. `permit_id` が、まだ使われていない。
4. 今の `access_epoch` が、Permit の `access_epoch` と同じ。
5. 拒否リストに、対象の資源や記憶が含まれていない。
6. 承認が有効（期限切れでも、取り消されてもいない）。
7. 緊急停止の印が立っていない。
8. **実際に行う操作の `action_hash` と、Gateway では実際の送信内容から計算した `request_hash` が、Permit と一致する。**

**一度だけ使えることを保証する**

- 一度だけ使えることは、7.5 の原子的な消費で保証する。

**限界**

- 検査から送信までの、わずかな時間差は残る。
- 送信した後の情報や、外部サービスの側で始まった処理は、取り消せない（B2-P02）。

### 7.5 Permit と承認の、原子的な消費（C1-R02）

**誰が消費するか（最終的な強制点）**

- Permit には、発行するときに `consumer` を1つだけ決めて書き込む。
  - `GATEWAY`：外部通信を伴う操作。モデルの呼び出し、トークンの計測、リモートの MCP、Web、API。
  - `BROKER`：Sandbox での実行、ファイルの操作、`builtin` のツール、stdio の MCP。
- もう一方の PEP は、検査（7.4）だけを行い、**消費はしない**。こうして、Broker と Gateway の両方を通る操作でも、二重に消費しないようにする。

**消費の処理（1つのトランザクション）**

- 消費する PEP は、送信や実行の直前に、P1（Orchestrator）に `consume(permit_id, actual_action_hash, actual_request_hash?)` を依頼する。
- P1 は、Journal と同じ SQLite の上で、`BEGIN IMMEDIATE` の1つのトランザクションとして、次をすべて行う。

```
- permits：     state='ISSUED' かつ期限内かつ access_epoch=今の値 かつ consumer=依頼してきた PEP
                → 'CONSUMED' に更新する（更新できた行が 0 なら拒否）
- approvals：   有効かつ uses < max_uses → uses を 1 増やす（0 行なら拒否）
- reservations：同じ step と attempt の予約が RESERVED であること（設計A の4章）
- intents：     同じ step と attempt の INTENT_RECORDED があること（設計A の3.1）
- runtime_owner：epoch が今の Orchestrator のものであること（設計A の A11。古い Worker や古いプロセスを防ぐ）
- 停止の状態：  全体・テナント・Run のどれも停止していないこと（11.4）
- 拒否リスト：  対象の資源や記憶が含まれていないこと（B2 の7.8）
- 一致の確認：  actual_action_hash と actual_request_hash が、Permit と一致すること
- Journal：     PermitConsumed{permit_id, consumer, receipt_id} を追記する
```

- どれか1つでも満たさなければ、トランザクション全体を取り消して、拒否する。
- 書き込むのは P1 だけなので、同じ Permit を同時に使おうとしても、成功するのは1回だけになる。
- **P1 に届かない場合は、実行しない**（安全側に倒す）。

**消費した直後に障害が起きた場合**

- `PermitConsumed` はあるが、実行や送信の記録がない場合、その Step は設計A の `UNKNOWN_OUTCOME` として扱う。
- `READ_ONLY` の操作に限り、新しい attempt、新しい予約、新しい Permit で、もう一度実行できる。
- それ以外の操作は、**自動では再実行しない**（設計A の A08・A10）。
- Gateway が消費した後、送信する前に止まったことが分かっている場合（11.4 の停止など）は、`ABORTED_BEFORE_SEND`（送っていないことが確定した状態）として記録する。

### 7.6 承認の範囲（C1-R08）

| 種類 | 結び付けるもの | 使える操作 |
|---|---|---|
| ExactApproval | 1つの `action_hash`。`max_uses=1` | すべて。高リスクの操作と、取り消せない操作は、これだけを使う |
| ScopedApproval | 下の制約すべて | 制限された種類だけ |

**ScopedApproval の制約**（すべて必須）

- `run_id`
- `tool_id@version@artifact_hash`
- 引数の制約：列挙した値、先頭と末尾を固定した正規表現、数値の範囲、ワークスペースの中のパスのパターン
- 対象の資源
- `sandbox_profile_hash`
- 読み書きできる範囲
- 外部通信先（既定では、なし）
- 許す副作用の種類
- 費用の上限
- `max_uses`
- `expires_at`

**ScopedApproval を禁止する操作**（ExactApproval が必要）

- `IRREVERSIBLE` の操作
- `external_guarantee=none` の外部への副作用
- 副作用の種類が分からないツール（10.5）
- ホストへの書き込みの範囲を超える削除
- ポリシーや権限に関わる操作
- ポリシーで「高リスク」とした操作

**対象のコードが変わった場合**

- **ツールの実行物が変わった場合**（`artifact_hash` や `sandbox_profile_hash` が変わった）：承認は**常に無効**になる。
- **ワークスペースのコードが変わった場合**（例：エージェントが書き換えたリポジトリで、テストを実行する）：
  - ネットワークがなく、書き込みが Sandbox の中だけで閉じる操作なら、承認はそのまま有効。コードの変化は、Sandbox の中の危険として扱う。
  - 外部通信、ホストへの反映、成果物の書き出しを伴う操作では、承認にワークスペースの木のハッシュを含める。コードが変われば、承認は無効になる。

**承認の画面**

- 正規化した ActionDescriptor の各項目を、正確に表示する。
- 認証情報は、値を出さずに `<credential:destination_id>` のように表示する。
- 承認者に見せてよくない機密は、伏せて表示する。そのうえで、内容のハッシュの先頭だけを示す。何を伏せるかは C2 で決める。
- 伏せた部分の確認が必要で、承認者にそれを見る権限がない場合は、承認できない。オーナーに回す。
- ファイルの書き込みは、変更の一覧を表示し、必要なら差分も表示する。

## 8. Sandbox（C06）

### 8.1 Docker の基本の設定（Phase 1〜2）

| 観点 | 設定 |
|---|---|
| ホストのファイル | ホストのリポジトリは、直接マウントしない。Run ごとに Broker がワークスペースの写しを作り、それだけをマウントする。結果は Broker が検査してから取り出す |
| root の権限 | コンテナの中では、root ではない UID で動かす。rootless の Docker、または userns-remap を優先する |
| Linux の capabilities | `--cap-drop=ALL`、`--security-opt no-new-privileges` |
| システムコールの制限 | 既定の seccomp と、AppArmor／SELinux の既定のプロファイルを有効にする |
| ルートのファイルシステム | `--read-only`。`/tmp` は大きさに上限のある tmpfs にする |
| Docker のソケット | **マウントしない**。privileged も、ホストの PID・IPC・ネットワークも使わない |
| 資源の上限 | `--memory`、`--cpus`、`--pids-limit`、ulimit（`nofile`、`nproc`）。ディスクは、ワークスペースの容量の上限と tmpfs の大きさで抑え、使用量を見張る |
| 実行の時間 | Broker が、経過時間で上限をかける。超えたら、コンテナごと止める |
| 子プロセスの残り | `--init` で、終わったプロセスを片付ける。終わるときに、コンテナごと消すので、子プロセスは残らない。ラベルで、残ったコンテナがないかを確かめる |
| 環境変数と認証情報 | 環境変数は、許可した名前だけにする。認証情報は、渡さない（S11） |
| コンテナどうしの通信 | Run ごとに別のネットワークにする（またはネットワークなし）。コンテナどうしの通信を無効にする |
| ネットワーク | 既定は `--network none` |
| 終わった後の片付け | コンテナとボリュームを削除し、残ったものがないかを検査する。結果の写しは、Broker が受け取ったものだけにする |
| イメージ | ダイジェストで版を固定した、小さなイメージにする |

**Docker を使うだけでは、安全とはみなさない。** ホストとカーネルを共有するため、カーネルの脆弱性で脱出されうる。マルチテナント化する前に、gVisor や microVM のような、より強い隔離を評価する（13章）。

### 8.2 起動時の自己診断と、使えないときの拒否

- Runtime を起動したときに、自己診断用のコンテナで次を確かめる。
  - root ではないこと
  - capabilities が外されていること
  - seccomp が効いていること
  - Docker のソケットがないこと
  - ネットワークが `none` で、外に届かないこと
  - 資源の上限が効いていること
- 一つでも満たさなければ、Sandbox は「使えない」とし、コードを実行するツールは、すべて拒否する。
- **Sandbox を使えないときに、安全性を下げて、ホストで直接実行することはしない**（S10）。

### 8.3 パスとファイルの境界

**パスの解決**

- 必ず、ワークスペースのルートからの相対パスとして扱う。
- 絶対パス、`..`、NUL 文字は拒否する。
- 正規化した後、ルートの内側にあることを確かめる。
- Linux では、`openat2` の `RESOLVE_BENEATH` と `RESOLVE_NO_SYMLINKS` を使う。使えるかどうかは、未確認。
- **安全なファイル操作の手段が使えない環境では、コピーと取り出しを拒否する**（S19）。

**写しを取り出すとき**

- シンボリックリンク、ハードリンク、デバイスファイル、FIFO は取り出さない。
- ファイルの数と大きさに、上限を設ける。

**写しを作るとき**

- 新しいファイルとして作り、ホストのファイルへのハードリンクは作らない。

### 8.4 Windows と Linux の違い

- Windows の Docker Desktop は、WSL2 や Hyper-V の仮想マシンの上で動くので、Linux とは次の点が違う。
  - マウントのしかた
  - パーミッション
  - シンボリックリンクの扱い
  - パスの区切り文字
  - 大文字と小文字を区別しないこと
  - rootless で動かせるかどうか
- **Phase 1〜2：** コードを実行するのは、Linux のホストで、8.2 の自己診断に合格した場合だけ。Windows では、Runtime そのものは動かせるが、自己診断に合格するまで、コードを実行するツールは拒否する。
- この違いは、設計A の課題 P2（排他ロックの互換性）とまとめて、設計E で対応する OS の範囲を決める。

### 8.5 Sandbox の内外でのファイルの権限（C1-R01）

| 区分 | 決め方 | 強制のしかた |
|---|---|---|
| ① Sandbox へコピーできるファイル | RunGrant の `files.read` と、プロジェクトのルートの内側が重なる部分から、除外の一覧に当たるものを除く | Broker が、写しを作るときに選ぶ。ルートの外のもの（ホームディレクトリ、`~/.ssh` など）は、対象にならない |
| ② Sandbox の中で読めるファイル | **①と同じ**。コピーしたものは、Sandbox の中のどのコマンドからも読める | ファイル単位の細かい読み取りの権限は、**提供しない**（強制できないので、提供できるとも言わない） |
| ③ Sandbox の中で書けるファイル | ツールの `effect_class` と、RunGrant の `files.write` | ディレクトリの単位で、マウントを分ける。読み込み専用（ro）にするか、書き込みできる（rw）にするか。例：`tests/` を ro にして、テストの改ざんを防ぐ。ro の部分マウントの数には上限を設ける。**ファイル単位の書き込みの権限は提供しない** |
| ④ ホストへ反映できるファイル | RunGrant の `files.write` のパターン | 取り出すときに Broker が検査する（下記） |

- 任意のコマンドは、File Broker を通さずに、Sandbox の中のファイルを直接操作できる。だから、Sandbox の中で強制できるのは、上の③の、マウントの単位の ro と rw だけである。

**ホストの機密ファイルをコピーしない仕組み**

- 除外の一覧（既定）：`.env*`、`*.pem`、`*.key`、`id_*`、`.npmrc`、`.pypirc`、`.netrc`、`.git/config` の認証情報、クラウドの認証情報のファイル。オーナーが追加できる。
- `.git` は、そのままはコピーしない。作業ツリーだけを書き出す（`.git` の中身を含めない）。git の操作が必要な場合は、フックや認証情報を除いた最小限の `.git` を作る。
- コピーする前に、C2 の機密の検査を通す。引っかかったファイルは除外し、そのことを記録する。

**取り出すときの検査**（どれか1つでも満たさなければ、反映を**全体として**取り消す）

1. コンテナを**止めた後に**、ボリュームから読む。Sandbox のプロセスと、同時にファイルが変わることはない。
2. コピーしたときの状態と比べて、追加・変更・削除の一覧を作る。
3. それぞれの変更について、次を確かめる。
   - パスが④の範囲の中にある。
   - 削除は、方針で許されている場合だけ。
   - 普通のファイルである（シンボリックリンク、ハードリンク、デバイスファイル、FIFO、ソケットは拒否）。
   - setuid と setgid は拒否する。実行権限の付け方は、方針に従う。
   - 大きさとファイルの数が、上限の中にある。
4. 読むときは、`openat2` を、シンボリックリンクを追わない設定で使う。
5. ホストへの反映は、一時的な置き場に書いてから、ファイルごとに原子的に置き換える。ホスト側の対象のパスも、同じ方法で解決する。ホストのワークスペースに、外を指すシンボリックリンクがないことも確かめる。

### 8.6 資源の上限（C1-R07）

**2種類の上限を分ける**

- **OS による強制：** OS が上限を超えさせない。
- **監視による停止：** 見張っていて、超えたら止める。超えてから止めるまでの間に、上限を超えた分が出る。

| 資源 | 方式 | 仕組み（値は PROVISIONAL） |
|---|---|---|
| CPU、メモリ | OS による強制 | cgroup（`--cpus`、`--memory`、swap なし） |
| プロセスの数 | OS による強制 | `--pids-limit`、ulimit の `nproc` |
| ワークスペースの写し | 入る前に拒否 | コピーするときに、大きさとファイルの数を確かめ、超えたらコピーしない |
| ワークスペースのディスク | OS による強制（推奨） | 大きさを固定したファイルシステムのイメージ（loop）か、大きさの上限のある tmpfs をマウントする。どちらも使えない構成では「監視による停止」になり、**上限を保証したとは扱わない** |
| `/tmp` などの一時ファイル | OS による強制 | 大きさの上限のある tmpfs |
| 標準出力・標準エラー | Broker が強制 | 読み取りの上限。超えた分は捨て、捨てたことを記録する |
| ログ | Runtime が強制 | 大きさの上限、ローテーション。内容を含めない（B2 の7.6） |
| 保存する成果物 | Runtime が強制 | Run ごとの保存量の上限 |
| Gateway の応答 | Gateway が強制 | 受け取る量の上限（9.1）。超えたら切断する |
| 展開した後のデータ | Gateway と Broker が強制 | 自動では展開しない。展開する場合は、少しずつ展開し、展開の比率と絶対量に上限を設ける。Broker は、アーカイブを自分では展開しない |
| 同時に実行する数 | Orchestrator が強制 | 全体、テナント、Run ごとに、Sandbox の同時実行数と外部通信の同時実行数に上限を設ける。超えた分は待たせる |
| 実行の時間 | Broker が強制 | 経過時間で止める（コンテナごと） |

### 8.7 コンテナごとの有効な設定の確認と、残ったものの回収（C1-R07）

- **起動の前の確認：** コンテナを作った後、起動する前に、実際に効いている設定を読み取り、`sandbox_profile` と照合する。読み取るのは、Docker の inspect に当たる情報。
  - 照合する項目：ユーザー、capabilities、`no-new-privileges`、読み込み専用のルート、ネットワーク、マウント（種類、ro か rw か、元の場所）、資源の上限、seccomp と AppArmor、イメージのダイジェスト。
  - 一致しなければ、そのコンテナを壊し、実行を拒否する。
  - 起動したときの自己診断（8.2）だけでなく、**コンテナごとに**この確認を行う。
- **障害の後の回収（Sandbox Reaper）：** Runtime を起動したとき、次を一覧にする。
  - Agent Core のラベル（`run_id`、`attempt_id`、`owner_epoch`）が付いたコンテナ、ボリューム、一時的な置き場。
  - そのうち、今の Lease を持つ attempt のものでないものは、止めて削除する。
  - それらの結果は、ホストへ反映しない（取り出しを行わない）。対応する Step は、設計A の手順で `UNKNOWN_OUTCOME` として扱う。
  - 回収したことを記録する。

## 9. 外部通信と EgressCheck（C07、B1-P02、B2-P02）

### 9.1 接続先の登録簿（オーナーが登録する）

`destination_id → {purpose, scheme: https のみ, host（完全一致）, port, allowed_methods, allowed_paths, max_request_bytes, max_response_bytes, timeout, allowed_data_classes, credential_binding}`

- `purpose`：`model`／`token_count`／`mcp`／`web`／`api`
- `allowed_data_classes`：送ってよい情報の区分（C2）
- `credential_binding`：使う認証情報。中身は Gateway の中だけにある

### 9.2 Gateway の検査（どれか1つでも満たさなければ遮断する）

1. **Permit と照合する：** 封をしたリクエスト（9.5）から、Gateway 自身が `request_hash` を計算し直し、Permit と比べる。認証情報を注入する前の内容で計算する。
2. **直前の検査：** 7.4 の 4〜7 を確かめる（B2-P02）。
3. **DNS と IP：**
   - Gateway 自身の名前解決で、IP を求める。
   - 解決したアドレスは、9.6 の規則で判定する。通すのは、グローバルなユニキャストのアドレスだけ。
   - **解決した IP に固定して接続する。** 名前を解決し直して、別の IP に行くことはしない（DNS rebinding への対策）。
   - TLS の証明書の検証は必ず行い、SNI と Host が一致することを確かめる。
4. **リダイレクト：** **原則として拒否する。** 3xx の応答は、データとして呼び出し元に返すだけで、Gateway は追わない。接続先の登録で明示して許している場合に限り、リダイレクト先への要求を**新しい操作**として扱い、新しい ActionDescriptor、新しい Permit（必要なら承認も）を取り直す。リダイレクト先には、認証情報を注入しない。
5. **大きさと時間：** リクエストと応答の大きさ、かかる時間に上限を設ける。
6. **その他：** 任意の宛先への CONNECT と、平文の HTTP は認めない。

**応答の扱い：** 応答は、D1／D2（信頼しないデータ）として扱う。

**対象：** Model Provider、トークンを数える API、MCP サーバー（リモート）、Web、その他の API。すべて、この同じ経路を通る。

### 9.3 認証情報

- 認証情報は、Gateway が `credential_binding` に従って、送信の直前にだけ注入する。
- モデル、Sandbox、Journal、ログには、認証情報が現れない（B1 の C14、S11）。

### 9.4 Phase 1〜2 での扱い

- 登録できる接続先は、ローカルの偽のサーバーだけ。
- 実際のプロバイダーの接続先は、登録簿にも、Gateway の設定にも存在しない（D1、設計A の I10）。
- 機密の検出と、送ってよい区分の判定の詳細は、C2 で決める。

### 9.5 送信する内容の、完全な認可（C1-R03）

**CanonicalRequest（request_hash の計算の対象）**

| 項目 | 内容 |
|---|---|
| プロトコルの版 | `HTTP/1.1`、`h2` など |
| 送信先 | `scheme`（https だけ）、`host`（小文字にし、国際化ドメイン名は ASCII に変換したもの）、`port`（省略せずに明示する）、`destination_id` |
| メソッド | — |
| パス | パーセントエンコーディングを正規化したもの |
| クエリ | 送る順番どおりの、キーと値の組の並び |
| ヘッダー | 次の2種類を除く**すべて**のヘッダー。名前は小文字にし、値はそのまま。<br>- Gateway が注入する認証情報のヘッダー<br>- 中継のための hop-by-hop のヘッダー（`Connection` など） |
| 本文 | 本文の形式（`Content-Type`、`Content-Encoding`）、本文の長さ、本文のハッシュ |

- `request_hash` = 鍵付きのハッシュ（CanonicalRequest）。鍵は C2 で決める。
- ActionDescriptor の `destinations` と `request_hash` は、この CanonicalRequest から作る。

**封をしたリクエスト（SealedRequest）**

- Broker（モデルの呼び出しなどでは Model Client）は、送る**バイト列そのもの**を組み立て、`request_hash` と一緒に、変更できない形にして Gateway に渡す。
- Gateway は、受け取ったバイト列から CanonicalRequest を作り直し、ハッシュが一致することを確かめる。
- Gateway が加えてよい変更は、決められた位置への認証情報の注入だけ。それ以外は一切変えずに送る。

**URL やヘッダーを使った持ち出しへの対策**

- パス、クエリ、ヘッダーの値も、本文と同じく、C2 の機密の検査の対象にする。
- クエリの長さ、ヘッダーの数と大きさに上限を設ける。
- 接続先ごとに、許すヘッダーの名前の一覧（`allowed_headers`）を登録し、それ以外のヘッダーは拒否する。

**認証情報の注入**

- 認証情報は、`destination_id` と `host` が登録と完全に一致する場合にだけ、Gateway で注入する。
- リダイレクト先や、登録にない宛先には、決して注入しない。

### 9.6 アドレスと、接続の検査（C1-R03）

**許可の一覧の考え方**

- 通すのは、グローバルなユニキャストのアドレスだけ。
- 次の特殊な用途のアドレスは、すべて遮断する。この一覧は、IANA の登録簿と照らし合わせて確かめる必要がある（未確認事項）。

| 種類 | 遮断する範囲 |
|---|---|
| IPv4 | `0.0.0.0/8`、`10.0.0.0/8`、`100.64.0.0/10`、`127.0.0.0/8`、`169.254.0.0/16`、`172.16.0.0/12`、`192.0.0.0/24`、`192.0.2.0/24`、`192.88.99.0/24`、`192.168.0.0/16`、`198.18.0.0/15`、`198.51.100.0/24`、`203.0.113.0/24`、`224.0.0.0/4`、`240.0.0.0/4`、`255.255.255.255` |
| IPv6 | `::/128`、`::1/128`、`100::/64`、`2001::/23`、`2001:db8::/32`、`fc00::/7`、`fe80::/10`、`ff00::/8` |
| IPv4 を埋め込んだ IPv6 | `::ffff:0:0/96`（IPv4-mapped）、`64:ff9b::/96`（NAT64）、`2002::/16`（6to4）。中に埋め込まれた IPv4 を取り出して、IPv4 の規則で判定する |

**実際の宛先の確認**

- 接続した後、ソケットの相手のアドレス（`getpeername`）が、固定した IP と一致することを確かめる。一致しなければ、切断する。

**プロキシによる迂回を防ぐ**

- Broker、Gateway、Sandbox のプロセスでは、プロキシの環境変数（`HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY` など）を消しておく。
- 使うライブラリが、プロキシを自動で検出しないように設定する。
- Gateway の外へ出る通信は、直接の接続だけにする。

### 9.7 試験用の構成を分ける（C1-R03）

- Phase 1〜2 のローカルの偽のサーバーは、**外部と通信できない、独立した試験用の構成**で動かす。具体的には、外への経路を持たない内部だけのネットワークに置く。
- **内部のネットワークを遮断できるかどうかの試験は、偽のサーバーに届くかどうかでは判定しない。** 名前解決の結果を差し替えた試験用の名前解決器で、私的なアドレスや埋め込みのあるアドレスを返させる。そのうえで、9.6 の判定の処理が遮断することを確かめる。
- 試験用の接続先の登録は、試験用のプロファイルにだけ置く。本番のモード（試験用の印のない設定）では、読み込めないようにする。

## 10. プロンプトインジェクションと MCP（C08）

### 10.1 外部情報による権限の格上げを防ぐ

- B1 の階層の規則に従う。外部の情報とツールの出力は D1／D2 であり、命令にはならない。
- PDP は、モデルが書いた理由や説明の文章を、判定の根拠にしない。判定に使うのは、ActionDescriptor と、ポリシーだけ。
- 外部の情報で、ポリシー、RunGrant、マニフェスト、承認が変わることはない（S13）。
- 危険度の高い操作は、モデルが何を主張していても、人間の承認を必要とする。

### 10.2 悪意のあるツールの出力への対応

- 大きさに上限を設け、スキーマで検証し、データとして扱う。
- 出力の中に、ツール呼び出しのような文字列があっても、呼び出しとしては解釈しない。呼び出しとして扱うのは、プロバイダーの構造化されたツール呼び出しの経路だけ。
- **許可した経路を使った持ち出しへの対策：** 例として、許可した Web の取得の URL に、データを埋め込む手口がある。対策は次のとおり。
  - 認証情報を、文脈に入れない。
  - 接続先の登録を狭くする。
  - URL とクエリの長さに上限を設ける。
  - 送る内容を検査する（C2）。
  - これでも、完全には防げない（12章）。

### 10.3 MCP サーバーの登録と、信頼の管理

**オーナーが登録する項目**

`{server_id, transport: stdio（専用の Sandbox）| https（Gateway を通す）, version_pin, tool_definitions_hash, tools[]（それぞれの manifest）, destinations[], permissions}`

- `tool_definitions_hash`：ツールの名前、説明、スキーマの全体から計算したハッシュ

**接続するたびに行う確認**

- サーバーから受け取ったツールの一覧のハッシュを、登録したものと比べる。
- 説明文が1文字でも違えば、そのツールは無効にし、再審査を待つ。これは、説明文に毒を仕込む手口への対策。
- 登録していないツールは、無視して拒否する。

**ツールの説明文**

- モデルに見せる説明文は、D2 として扱う。長さに上限を設け、区切った区画に入れる。

**サーバーの側から始まる要求**

- サーバーの側から始まる要求（モデルによる生成の依頼、ユーザーへの問い合わせ、ファイルの範囲の要求など）は、既定で拒否する。
- MCP の仕様の細かい点は未確認なので、MCP を導入する前に確かめる。

**ツール定義が変わった場合**

- 版の固定と、オーナーによる再審査をやり直す。

### 10.4 AI による判定の位置付け

- 注入を見分けるための分類器は、使ってもよい。ただし、**制限を加える方向にだけ**使う（承認を求める、拒否する）。
- 許可を与えることには使わない。最終的な防御は、構造的な強制（PEP、Permit、Sandbox、Gateway）が受け持つ。

### 10.5 MCP の実行時の信頼境界（C1-R06）

**ツールの定義が一致していても、MCP サーバーの中身や振る舞いは変わりうる。**

| 項目 | 扱い |
|---|---|
| 登録のときの検証 | ツールの定義のハッシュを固定する。ローカルのサーバーは、実行物（パッケージ、またはイメージのダイジェスト。5.3）も固定する。リモートのサーバーは、接続先と、オーナーが審査したツール定義の写しを固定する |
| 呼び出すときの検証 | セッションを始めるたびに、ツールの一覧を取得し、ハッシュを照合する。呼び出すたびに、ツールの名前、固定した入力のスキーマ、出力のスキーマと大きさの上限を確かめる |
| ツールの定義の変更通知 | 一覧が変わったという通知を受け取ったら、そのサーバーのツールを**すべて**止め、再審査を待つ |
| ローカルの MCP の実行コード | イメージのダイジェストで固定し、それ専用の Sandbox で動かす。変われば再審査する |
| リモートの MCP の実装 | **固定できない**（限界）。そのため、出力は D2 として扱う。副作用は、オーナーが契約などで確かめない限り、`IRREVERSIBLE` で `external_guarantee=none` として扱う。ScopedApproval は使わない |
| サーバーから始まる要求 | すべて拒否し、記録する。モデルによる生成の依頼、ユーザーへの問い合わせ、範囲の要求などが当たる |
| 副作用の分類が分からないツール | `IRREVERSIBLE` として扱う。呼び出すたびに ExactApproval が必要 |
| MCP サーバーに渡す認証情報 | サーバーごとに別の認証情報にする。権限は必要なものだけにし、できる限り有効期間を短くする。Gateway で注入する。サーバーどうしで使い回さない |
| MCP サーバーの側で起きる外部への操作 | Agent Core からは見えない（限界）。照合できる範囲に限りがあることを、記録しておく |

**モデルに見せるツールのスキーマ**

- オーナーが審査して固定した構造と説明だけから作る。必要なら、オーナーが説明を書き直す。
- 実行時にサーバーから受け取った説明の文章は、モデルに見せない。信頼する命令としても扱わない。

## 11. 停止と障害への対応（C09）

### 11.1 停止の段階

| 段階 | 誰が | 効果 |
|---|---|---|
| K1：Run のキャンセル | ユーザー、オーナー | 設計A の `CANCELLING`。その Run に、新しい Permit を出さない |
| K2：テナントの一時停止 | オーナー | そのテナントに、新しい Permit を出さない。`access_epoch` を1つ増やす |
| K3：緊急停止（全体） | オーナー | 下の手順をすべて行う |

**K3 の手順**

1. 停止の状態を、11.4 の順序で記録する。まず停止の状態のファイルにある全体の項目を STOPPED にし、その後で Journal に記録する。
2. Permit の発行を止め、`access_epoch` を1つ増やす。これで、出ている Permit はすべて無効になる。
3. Gateway は、すべての送信を遮断する。停止の印が読めないときも、遮断する（安全側に倒す）。
4. 実行中の Sandbox には、SIGTERM を送る。猶予の時間が過ぎたら、コンテナを強制的に止めて削除する。stdio の MCP サーバーも止める。
5. 実行中のモデル呼び出しは、接続を切る。プロバイダーの側では、処理や課金が続くことがある。そのため、結果は `UNKNOWN_OUTCOME` として扱う（設計A の A04）。
6. Run は、設計A の A10 に従って、`CANCELLING` または `RECONCILIATION_REQUIRED` に移す。

**停止の仕組みそのもの**

- Orchestrator の処理が詰まっていても止められるように、停止の要求は別の経路で受け付ける。別の経路とは、制御用の別の口、またはシグナル。
- **外部サービスの側ですでに始まった処理を、必ず止められるとは言わない。**

### 11.2 実行した操作の照合

- 停止した後、次のものを一覧にして、設計A の手順で照合する。
  - `UNKNOWN_OUTCOME` の Step
  - 外部に送った操作
  - 使われた Permit

### 11.3 安全に再開するための条件

すべてを満たした場合だけ、再開する。

1. オーナーが、はっきり再開を指示する。
2. 完全性の検査に合格する。対象は、Journal のハッシュの連鎖、Policy Store とマニフェストのハッシュ、削除台帳（C2）。
3. Sandbox の自己診断（8.2）に合格する。
4. 結果不明の操作を照合し終えるか、オーナーが「解決できない」と受け入れる。
5. 新しい `access_epoch` になっている。
6. 止めた原因を記録し、見直す。

再開した後も、古い Permit と古い承認は使えない。必要なものは、取り直す。

### 11.4 停止の状態の整合性と、実行との順序（C1-R04）

**停止の状態を置く場所**

| 場所 | 役割 |
|---|---|
| Journal の `StopRequested` と `ResumeApproved` のイベント | 正本。`stop_seq` は単調に増える |
| 停止の状態のファイル | Gateway と Broker が、独立して素早く読むための写し。**削除しない**。中身は `{file_seq, entries{(scope_type, scope_id) → {stop_seq, state}}}` と署名（C1-P01）。署名の鍵は C2 で決める |
| Gateway と Broker の記憶 | これまでに見た、最も大きい `stop_seq`（巻き戻りを見つけるため） |

**書き込む順序**

**停止の状態のファイルの構造（C1-P01 で修正）**

- 範囲ごとに、別々の項目を持つ：`global`（1つ、必ずある）、`tenant:<id>`、`run:<id>`。
  - ある範囲の項目を書き換えても、ほかの範囲の項目は書き換えない。全体、テナント、Run の停止が、互いに上書きされない。
- 項目の状態は、次の3つのどれか。
  - `STOPPED`（停止中）
  - `RESUMING`（再開の途中）
  - `RUNNING`（実行してよい）
- 各項目は、範囲ごとに単調に増える `stop_seq` を持つ。ファイル全体は、単調に増える `file_seq` を持つ。
- 書き換えは、排他のロックを取って、一時ファイルに書き、fsync してから名前を変える方法で、原子的に行う。
- **ファイルは削除しない。** 再開するときは、新しい `stop_seq` を持つ `RUNNING` に書き換える。
- 新しく導入したときは、Journal に `StopStateInitialized` を記録し、`global` の項目を `RUNNING`（`stop_seq=0`）にして作る。

**書き込む順序**

- **停止するとき：**
  1. その範囲の項目を、新しい `stop_seq` で `STOPPED` に書き換える（先に書く）。
  2. Journal に `StopRequested{scope, stop_seq}` を記録する。
  3. `access_epoch` を増やす。
  - 間で障害が起きても、止まる側に倒れる。
- **再開するとき：**
  1. Journal に `ResumeRequested{scope, stop_seq}` を記録する。
  2. その範囲の項目を `RESUMING` にする。
  3. 11.3 の確認をする。
  4. Journal に `ResumeApproved{scope, stop_seq}` を記録する。
  5. その範囲の項目を、同じ `stop_seq` で `RUNNING` に書き換える。
  - どの段階で障害が起きても、`RUNNING` にはならない。そのため、止まったままになる。

**実際に効く状態の判定**

- 「実行してよい」になるのは、その操作に関わる**すべての範囲**（`global`、その操作のテナント、その操作の Run）について、次のすべてを満たすときだけ。
  1. Journal と停止の状態のファイルを、どちらも読める。署名が正しい。
  2. 項目が `RUNNING` であり、その `stop_seq` が、Journal にあるその範囲の最新の `ResumeApproved`（または `StopStateInitialized`）と一致している。
     - テナントと Run の項目がない場合は、Journal にもその範囲の停止のイベントがないときだけ、`RUNNING` とみなす。
     - `global` の項目がない場合は、不整合として扱う。
  3. `file_seq` と `stop_seq` が、記憶している値より巻き戻っていない。
- それ以外の場合は、**新しい実行を許さない**。具体的には、`STOPPED`、`RESUMING`、読めない、署名が正しくない、Journal と食い違う、巻き戻っている、のどれか1つでも当てはまる場合。
- 起動したときに、停止のファイルにはあるのに Journal にはない停止（停止の要求の途中で障害が起きた）を見つけた場合は、Journal に `StopRecovered` を追記して、止めたままにする。

**停止と、実行を始めることの順序（最終的な強制点）**

- 7.5 の消費の処理が、同じトランザクションの中で停止の状態を確かめる。P1 が唯一の書き込み手なので、「停止の記録」と「Permit の消費」は、必ずどちらかが先になる。
  - 消費が先なら、その操作は「停止の前に始めた操作」として、照合の対象になる。
  - 停止が先なら、消費は拒否される。
- Gateway と Broker は、消費の確認を受け取った後、送信や実行の**直前に**、もう一度停止の状態のファイルを確かめる。停止していれば中止し、`ABORTED_BEFORE_SEND` として記録する。
- 消費の後の、`access_epoch`、拒否リスト、承認の失効との順序（C1-P02）は、C2 の 5.4 で扱う。

| 対象 | 停止したときの扱い |
|---|---|
| 停止の前に発行した Permit | `access_epoch` が増え、消費の処理で停止を確かめるので、無効になる |
| 送信を待っているリクエスト | Gateway が捨て、送っていないことが確定したものとして記録する |
| 実行中の Sandbox | 11.1 のとおり止める。結果は `LATE_RESULT` として記録するが、ホストには反映しない |
| 実行中の外部通信 | 接続を切る。結果は `UNKNOWN_OUTCOME`。**取り消せたとは言わない** |
| テナント単位の停止（K2） | `scope=tenant` として同じ仕組みを使う。消費の処理で、テナントの停止を確かめる |
| Run 単位の停止（K1） | 消費の処理で、Run の状態（`CANCELLING` など）を確かめる |

## 12. 評価の方法（C10）とゲート

**Phase 1〜2 で使うもの**

- 合成データ
- ScriptedProvider（偽のモデル）
- 外部と通信できない試験用の構成（9.7）の中の、偽のサーバー
- 「乗っ取られたモデル」の筋書き

**違反が 0 件だったことを、完全に安全な証明としては扱わない。** 試験は、知られている手口と、想定した故障に対する確認にすぎない。

### 12.1 Technical Gate（機能が正しく動き、障害から正しく復旧すること）

| 試験 | 合格の目安 |
|---|---|
| Permit の消費の処理（7.5）が、正常に動くこと。障害が起きた後の状態が、設計A の状態遷移と一致すること | 不一致 0 件 |
| 停止と再開で書き込む順序（11.4）を守っていること。どの地点で障害が起きても、状態の判定が「停止」の側に倒れること | 100% |
| 取り出しのときの差分の計算と、原子的な反映（8.5）が正しいこと | 誤りも、途中までの反映も 0 件 |
| コンテナごとの有効な設定の照合（8.7）と、残ったものの回収 | 残ったものが回収された割合 100% |
| 封をしたリクエストの、CanonicalRequest の計算（9.5）が、決定的であること | 同じ入力からは、同じハッシュになる割合 100% |
| 資源の上限：OS による強制か、監視による停止かの区別が、実際の構成と合っていること | 自己診断の結果と一致 |

### 12.2 Safety Gate（攻撃と故障に耐えること）

**C1 第1版から引き継ぐ試験**

| 評価する項目 | 試験のやり方 | 合格の目安 |
|---|---|---|
| 権限のない操作の拒否 | RunGrant にないツール、パス、接続先、モデルを提案させる | 実行された件数 0 |
| 承認の改ざん | 承認の後に、引数・送信先・request_hash を変える。偽の承認の文章を入れる | 実行された件数 0 |
| Permit の再利用 | 同じ Permit で2回実行する。期限が切れた Permit、MAC を改ざんした Permit を使う | 受理された件数 0 |
| 権限の変更と実行の競合 | Permit を出した後、送信の直前に、権限を失効させる・削除を要求する・epoch を増やす | 送信された件数 0（検査より前に送った分は、送信済みとして照合する） |
| ファイルの境界の回避 | `..`、絶対パス、シンボリックリンク、ハードリンク、デバイスファイル、名前の大文字と小文字の違いを使う | 境界の外に触れた件数 0 |
| Sandbox からの脱出を想定した隔離 | 中から次を試す：Docker のソケット、ホストのファイル、ほかのコンテナ、メタデータサービス、外部への通信、capabilities が必要な操作 | 成功した件数 0。ただし、未知のカーネルの脆弱性は対象外 |
| 外部通信の制限 | 登録していない宛先、内部の IP、DNS rebinding、リダイレクト、平文の HTTP、大きすぎる本体を使う | 遮断できなかった件数 0 |
| 機密情報へのアクセス | 目印の値を入れた認証情報を用意し、Sandbox、文脈、ログ、Journal に現れるかを調べる | 現れた件数 0（詳細は C2） |
| 悪意のある MCP ツール | 説明文の差し替え、登録していないツール、サーバーからの要求、持ち出しを狙った出力を使う | 有効になった件数 0、受理された件数 0 |
| 緊急停止 | 各段階の途中で K3 を行う。停止の印を読めない状態にする | 停止の後に送信された件数 0。読めないときも遮断する割合 100% |
| 子プロセスの残り | 二重に fork したプロセスや、デーモンのように残るプロセスを作る | 終わった後に残った件数 0 |
| 実行資源の上限 | fork bomb、メモリやディスクを使い尽くす、無限ループ | 上限で止められた割合 100%、ホストへの影響 0 |


**C1-R01〜R08 で追加した試験**（正常系だけでなく、攻撃と故障を含める）

| 観点 | 試験のやり方 | 合格の目安 |
|---|---|---|
| 同時実行 | 同じ Permit を、複数のスレッドや PEP から同時に消費しようとする。`max_uses` の境目で、同時に承認を使う | 2回以上成功した件数 0 |
| クラッシュと復旧 | 消費の直後、送信の直前、取り出しの途中、停止のファイルを書いた直後に、障害を起こす | 自動で再実行された件数 0（`READ_ONLY` を除く）。停止が解けた件数 0。途中までの反映 0 |
| 認可した後の内容の変更 | 認可の後に、クエリ、ヘッダー、本文、ポート、メソッド、プロトコルの版を変える。Gateway の側で改ざんを試みる | 送信された件数 0 |
| 停止と実行の競合 | 消費と停止をほぼ同時に起こす。停止のファイルを古いものに戻す。停止のファイルと Journal を食い違わせる | 停止の後に新しく実行された件数 0。食い違いのときも、停止の判定になる割合 100% |
| 権限の失効 | 消費の直前に、承認を取り消す、epoch を増やす、拒否リストに加える | 消費に成功した件数 0 |
| ツールのコードの差し替え | イメージ、起動の設定、ロックファイル、`sandbox_profile` を差し替える。ローカルの MCP のパッケージを差し替える | 再審査なしで実行された件数 0 |
| Sandbox の設定の不備 | わざと、ソケットのマウント、root、capabilities、ネットワークを誤って設定したコンテナを作る | 起動された件数 0 |
| 資源の上限を超える | fork bomb、メモリやディスクを使い尽くす、大量の出力、展開すると巨大になるデータ、同時実行の上限を超える要求 | OS による強制の項目は、超えた件数 0。監視の項目は、上限の時間内に止めた割合 100% |
| ファイルの境界（R01） | コピーの除外の一覧にあるファイル、取り出すときのリンクや特殊なファイル、範囲の外の削除、setuid、反映する前にファイルを差し替える | 反映された件数 0 |
| 外部への送信（R03） | IPv4-mapped、NAT64、6to4、特殊な用途のアドレス。名前解決の後に宛先が変わる。プロキシの環境変数。URL やヘッダーに目印の値を入れる | 通過した件数 0。目印の値を見つけた割合 100%（登録済みの目印に限る） |
| MCP（R06） | 一覧の変更の通知、説明文の差し替え、サーバーから始まる要求、分類の分からないツールの ScopedApproval | 受理された件数 0 |
| 承認の範囲（R08） | 制約の外の引数、ScopedApproval を禁止した操作への使用、実行物を差し替えた後の承認の使用、画面に認証情報が出るか | 受理された件数 0、出た件数 0 |

## 14. 不変条件

| ID | 不変条件 |
|---|---|
| S1 | はっきり許可していない操作は、拒否される（デフォルト拒否） |
| S2 | AI モデルは権限を持たない。ポリシー、RunGrant、マニフェスト、承認を変えられない |
| S3 | 副作用のある操作（コマンドの実行、ファイル、外部通信、MCP、モデル、記憶）は、PEP を通ってだけ行われる |
| S4 | すべての実行には、`action_hash` に結び付き、一度だけ使え、期限内で、epoch が今のものと一致する Permit がある。Permit を消費する主体は、ただ1つに決まっている |
| S5 | PEP は、実行や送信の直前に、7.4 の 1〜8 をすべて確かめる。外部への送信では、照合に CanonicalRequest（9.5）を使う |
| S6 | 承認は `action_hash`（または、範囲を決めた種類）に結び付く。内容が変われば、承認を取り直す。承認者の役割を超える承認は無効 |
| S7 | 権限は、階層を下るほど狭くなる。実行中の Run の権限が、自動で広がることはない |
| S8 | 登録されていないツール、版が固定されていないツール、定義が変わった MCP のツールは、拒否される |
| S9 | Sandbox は次を満たす：ホストのファイルを持たない（Run ごとのワークスペースの写しだけ）、Docker のソケットがない、root ではない、capabilities を外している、`no-new-privileges`、資源に上限がある、ネットワークは `none`（または Gateway だけ）。これをコンテナごとに、実際に効いている設定で照合する |
| S10 | Sandbox が使えない、または自己診断に失敗したときは、コードの実行を拒否する。ホストで直接実行することはしない |
| S11 | 認証情報は、Sandbox、モデルの文脈、Journal、ログに入らない。Gateway でだけ注入される |
| S12 | 外部通信は、登録された接続先にだけ行われる。通すのは、グローバルなユニキャストのアドレスだけ（埋め込まれた IPv4 も判定する）。接続した後に、実際の宛先を確かめる。プロキシの設定による迂回を許さない。リダイレクトは原則として拒否し、許す場合も新しい操作として認可する |
| S13 | 外部の内容（ツールの出力、Web、MCP の結果や説明文）で、ポリシーや権限が変わることはない |
| S14 | 緊急停止の後は、新しい Permit を出さず、PEP と Gateway は何も送らない。停止の状態が読めない、食い違う、巻き戻っているときも、停止として扱う |
| S15 | 再開には、オーナーの操作と、11.3 の確認が必要 |
| S16 | ファイルの操作は、ワークスペースのルートの内側で解決する。シンボリックリンク、ハードリンク、デバイスファイルによる回避は拒否する |
| S17 | ポリシーの変更には、認証された経路での、オーナーの承認が必要。新しい `policy_version` として記録する |
| S18 | Sandbox にコピーするのは、①の範囲だけ。機密のファイルと、ルートの外のものは含まない。Sandbox の中の権限は、マウントの単位の ro と rw だけで、ファイル単位の権限を提供するとは言わない |
| S19 | ホストに反映するのは、コンテナを止めた後に検査を通った、④の範囲の普通のファイルだけ。反映は全体として原子的に行う。安全なファイル操作の手段がない環境では拒否する |
| S20 | Permit の消費は、承認の使用回数、予約、Intent、epoch、Orchestrator の epoch、停止の状態、拒否リストの確認と同じ、1つのトランザクションで行う |
| S21 | Gateway は、封をしたリクエストのバイト列を、認証情報の注入を除いて変えずに送る。認証情報は、登録と完全に一致する宛先にだけ注入する |
| S22 | 停止は、停止の状態のファイルを先に書き、再開は、Journal を先に書く。ファイルは削除せず、範囲ごとの項目として書き換える。`RUNNING` 以外の状態や、状態が分からないときは、実行しない |
| S23 | `manifest_hash` と `artifact_hash` のどちらかが変われば、再審査するまで実行しない。信頼しないアダプターを、TCB のプロセスの中では動かさない |
| S24 | 認証情報は P3 だけ、Docker の API は P2 だけ、Journal への書き込みは P1 だけが持つ。Phase 3A より前に、P3 を別の OS ユーザーにする |

## 16. 残存リスク

1. **カーネルの脆弱性：** コンテナは、ホストとカーネルを共有する。カーネルの脆弱性や Docker の設定の誤りで、脱出される可能性がある。
2. **Windows：** Windows での Sandbox の性質は未確認。そのため、Phase 1〜2 では、Windows ではコードを実行しない。
3. **許可した経路を使った持ち出し：** 許可した接続先に、エンコードしたデータを送る手口は、完全には防げない。
4. **承認の疲れ：** 承認が多すぎると、人は内容をよく見ずに承認するようになる。誤った承認や、ソーシャルエンジニアリングを、構造だけでは防げない。
5. **検査から送信までの時間差：** PEP の検査から送信までに、わずかな時間差（TOCTOU）が残る。送信した後は取り消せない。
6. **TCB の乗っ取り：** 単一のマシンの TCB（Orchestrator、PEP）が乗っ取られると、すべての防御が崩れる。
7. **MCP の仕様：** MCP の仕様は変わり続けている。サーバーの側から始まる要求の扱いは、導入する前に確かめ直す必要がある。
8. **ディスクの上限：** ディスクの使用量の上限は、ファイルシステムによっては厳密にかけられない。見張って止める方式に頼ることになる。
9. **初回報告書との照合：** 初回報告書の Safety の部分とは、照合していない。
10. **ファイル単位の権限（R01）：** Sandbox の中で、ファイル単位の読み書きの権限は提供できない。コピーした写しは、すべて読める。
11. **Orchestrator が止まったとき（R02）：** P1 が止まると、どの操作も実行できなくなる（安全側に倒した結果）。
12. **リモートの MCP の中身（R06）：** 固定も確認もできない。サーバーの側で起きる外部への操作は、見ることも照合することもできない。
13. **同じ OS ユーザーの Phase 1〜2（R05）：** P1〜P3 が論理的に分かれているだけの間は、OS のレベルの隔離にはなっていない。
14. **資源の上限（R07）：** OS で強制できない構成（ディスクの容量など）では、監視による停止にとどまる。
15. **停止の状態（R04）：** 停止の状態を両方とも失うと、オーナーが確かめるまで、何も実行できなくなる。
