## 0. 初回設計からの主な変更

| 初回設計（要約） | B2 での変更 |
|---|---|
| 作業記憶、エピソード記憶、意味記憶、手続き記憶の4種類 | User Memory（ユーザーの記憶）を加えて5種類にする。作業記憶は独立した保存先を持たない。Journal から導いた表示用の状態（投影）として扱い、正本は Journal だけにする |
| status は candidate、active、deprecated、superseded | `validating`、`rejected`、`stale`、`quarantined`、`deleting`、`deleted` を加える（3.2） |
| 検証済みの根拠がある場合、または人間が承認した場合に active へ昇格させる | 記憶の種類ごとに検証の方法を定める。「事実の根拠」と「原因の説明の根拠」を分ける。因果を主張する記憶を確認済みにするには、再現による検証を必須にする。人間の承認は「使ってよい」という意味にとどめ、検証の代わりにはしない（3.4） |
| 検索の順位は、BM25、新しさ、重要度、実測された有用性で決める | 権限による絞り込みを、順位付けより前に、完全に分けて行う。「実測された有用性」は、比較実験で得た値だけを使い、単なる相関は使わない |
| 矛盾した記憶には印を付け、新しく検証された記憶を優先する | 「新しいほうが正しい」とは判断しない。根拠の強さと情報の出どころで判断する。同じ内容が何度書かれても、正しさの証拠にはしない（自己強化の防止） |
| 削除時は tombstone と監査記録を残し、ユーザー単位の削除に対応する | 派生データの系譜（どのデータが、どの記憶から作られたか）を記録する。物理削除と鍵の破棄を組み合わせる。障害から再開しても、削除したデータが復活しないようにする（7章） |

## 1. アーキテクチャ

```
                ┌──────────── Memory Engine（判断の部分は副作用なし）────────────┐
 Runtime ─────▶ │ Scope Resolver（Runtime と Safety が範囲を確定する）             │
 （要求と結果） │ Retriever：権限で絞り込み → FTS5/BM25 → 順位付け → 予算に合わせる │
                │ Candidate Validator：根拠、重複、矛盾、種類ごとの採用判定        │
                │ Quality Manager：古さ、矛盾、統合、再検証の計画                  │
                │ Deletion Planner：系譜をたどって、削除の手順を作る               │
                └───────────────┬───────────────────────────────────────────────┘
                                │ 要求（MemoryRequest[]）
                                ▼
   Runtime が実行する：
   - モデルの呼び出し（Reflector、検証、再検証）→ MODEL_CALL
   - 保存（Memory Store、本文の blob、鍵）     → Journal のコマンドとして記録してから反映
   - 人間による確認の待ち行列                   → WAITING_APPROVAL

   保存先（テナントごとに分ける）
   ├ journal.db（設計A。記憶の本文は入れない）
   ├ memory/<tenant>.db（記憶のレコード、系譜、利用の記録。Journal から導いた投影。本文と内容を表す項目は入れない）
   ├ index/<tenant>/<partition>.db（範囲の区画ごとの FTS5 索引。対象は public と internal の記憶だけ。4.3）
   ├ blobs/（本文と構造化項目。記憶ごとの鍵で暗号化する）
   ├ keys/<tenant>.db（記憶ごとの鍵。テナントの鍵暗号化鍵で包む。バックアップの保管期間は短くする。7.6）
   └ deletion-ledger/（削除記録の独立した写し。7.7）
```

**決めたこと**

1. **B1 と同じ分け方：** Memory Engine の判断の部分（検証、順位付け、削除の計画）は、副作用を持たない計算にする。モデルの呼び出しと保存は、要求として Runtime に返し、Runtime が実行する（B1 の1.1、C16 と同じ）。
2. **Memory Store は Journal から導く投影：** 記憶の作成、昇格、失効、削除は、すべて Journal のコマンドイベントとして先に記録する。その後、`memory/<tenant>.db` に反映する。反映したところまでの `last_applied_seq` を記録しておき、障害の後はそこから続きを反映する。
   - こうすると、ファイルをまたぐトランザクションの問題を避けられる。SQLite の WAL では、複数の DB にまたがる処理は、全体として原子的にならない（未確認事項にも記録）。
3. **Journal には記憶の本文を入れない：** Journal に入れるのは、ID、バージョン、鍵付きのハッシュ、blob への参照だけ（M8）。
4. **検索の範囲は区画ごとに分ける：** テナントごとに DB を分けるだけでは、同じテナントの中で、別のユーザー、プロジェクト、エージェントの間を隔離できない。そこで、アクセス権の単位と同じ区画ごとに、索引を分ける（4.3、B2-R01）。
5. **単一の書き込み主体：** 設計A の A11 と同じ排他の仕組みを使い、書き込むのは Orchestrator だけにする。

## 2. データ構造（B08）

### 2.1 記憶の種類

| 種類 | 内容 | 正本と保存先 | 主な出どころ |
|---|---|---|---|
| Working Memory | 実行中の Run の作業状態 | **Journal だけ**。B1 の ProtectedFact、I4、D4 のメモは、どれも Journal のイベントから導く。Memory Store には保存しない（M1） | Runtime の観測、モデルのメモ（D4） |
| Episodic Memory | 過去の Run で起きたこと（観測した結果、エラーの特徴、環境の版） | Memory Store。過去の Run の Journal を参照する | `runtime_observed` |
| Semantic Memory | プロジェクトについての知識（ビルドの手順、モジュールの役割、規約） | Memory Store。元のファイル（リポジトリ、コミット、パス、ハッシュ）に結び付ける | `runtime_observed`、`human_approved`、`model_hypothesis`（検証の前） |
| Procedural Memory | 手順やスキル（バージョン付き） | Memory Store と、手順の登録簿 | 人間、またはモデルの提案。評価に合格し、承認された後に有効になる |
| User Memory | ユーザーの好みや前提 | Memory Store。ユーザーごとのスコープ。機密の区分は、初めから `personal` | `user_input`（ユーザーがはっきり述べたもの）、またはユーザーが確認したもの |

経験の記録（B11）は、Episodic と Semantic／Procedural にまたがる、結び付いたレコードの組として持つ（5章）。

### 2.2 記憶のレコード（MemoryRecord）

| 項目 | 内容 |
|---|---|
| `memory_id`, `version`, `schema_version` | 識別子とバージョン。書き換えるたびに新しいバージョンにする |
| `type`, `subtype` | 2.1 の種類。経験の記録の場合は `subtype`（観測、原因の仮説、確認済みの原因、実施した対策、検証済みの対策） |
| `content_ref`, `content_keyed_hash` | 本文は blob に置き、記憶ごとの鍵で暗号化する。ハッシュも同じ鍵で計算する |
| `structured_ref`, `blind_tokens` | 機械で照合する部分（例：`{subject, predicate, object}`、エラーの特徴、手順の手がかり）。中身は本文と同じく暗号化した blob に入れる。重複や矛盾を照合するためには、ブラインドインデックス（`blind_tokens`）を使う。これは、テナントの索引用の鍵で計算した HMAC で、Memory Store にだけ置く。Journal には入れない（7.6） |
| `scope` | `{tenant_id, user_id?, project_id?, agent_id?, eval_namespace?}` |
| `evidence[]` | 根拠。`{kind, ref, supports, strength, verified_at}`。<br>`kind` は `journal_ref`（run_id と seq）／`source_ref`（リポジトリ・コミット・パス・ハッシュ）／`test_ref`／`approval_ref`／`artifact_ref`。<br>`supports` は `occurrence`（事実が起きた）／`explanation`（原因の説明）／`applicability`（適用できる条件） |
| `provenance` | B1 の `provenance_class`、作った主体（`reflector@version` と `attempt_id`／人間／Runtime）、`derived_from_chain` |
| `sensitivity` | B1 と同じ区分（public／internal／confidential／personal） |
| `confidence` | `{value, method, computed_at}`。互いに独立した根拠だけから計算する（M4） |
| `verification_status` | 検証の状態。`observed`（観測した事実）／`unverified`（未検証の仮説）／`verified`（独立した根拠で検証した）。3.4 |
| `use_approval` | 利用の承認。`{none｜approved, approver, scope, expires_at}`。検証の状態とは**別の軸**で、承認しても検証済みにはならない（3.4） |
| `partition` | 4.3 の区画（`tenant_shared`／`project:<id>`／`user:<id>`／`agent:<id>`）。1つの記憶は、1つの区画にだけ属する |
| `importance` | 重要度。重要度の高い記憶は、人間による確認の対象にする |
| `applicability` | `{conditions[], exclusions[]}`。言語、リポジトリ、ツールの版、エラーの特徴など、機械で照合できる形で持つ |
| `timestamps` | `created_at`, `last_verified_at`, `last_provided_at`, `review_due_at` |
| `valid_until` | 有効期限。種類ごとの既定値は 6.1 |
| `status` | 3.2 の状態 |
| `lineage` | `derived_from[]`, `derived_to[]`（7.1 の系譜） |
| `relations` | `conflicts_with[]`, `supersedes`, `superseded_by`, `duplicate_of` |
| `key_id` | 暗号化に使った鍵の ID |

**利用の記録**（別の表に持つ）：`memory_id@version`, `run_id`, `step_id`, `context_hash`, `event`（`provided`（文脈に入れた）／`cited`（モデルの出力が参照した））。利用の記録は、効果があったことの証拠にはしない（M16）。

### 2.3 Working Memory と Journal の重複を防ぐ

- 作業記憶は「Journal から導いた、その Run の状態の見え方」であって、別の保存先ではない。
- Run が終わった後に、作業記憶の内容を長期の記憶に残したい場合は、必ず `MemoryCandidateProposed` を経由する。直接は書き込まない。

## 3. 記憶のライフサイクル（B09）

### 3.1 流れ

```
① 候補の抽出    Reflector（MODEL_CALL）、または決定的な抽出器（Runtime の観測から作る）
                → MemoryCandidateProposed（本文は暗号化した blob、Journal には参照とハッシュだけ）
② 根拠の確認    参照先が存在するか、スコープの中か、ハッシュが一致するか、
                根拠の種類（supports）が主張の種類に合っているか
③ 重複と矛盾の検査  構造化キーの照合、FTS の類似度 → 重複なら統合の候補、矛盾なら印を付ける
④ 採用の判定    種類ごとの方針（3.3）。必要なら、独立した検証（MODEL_CALL・テスト）か、人間の確認
⑤ Active       検索の対象になる
⑥ その後        再検証（stale → active／deprecated）、失効（期限切れ）、置換、隔離、削除（7章）
```

### 3.2 状態の遷移

```
candidate → validating → active ─┬→ stale ──→（再検証）→ active | deprecated
          │              │       ├→ superseded（新しい版に置き換わった）
          │              │       ├→ quarantined（汚染の疑い・重要な矛盾）→ active | rejected
          │              │       └→ deprecated（期限切れ・使わなくなった）
          └→ rejected    └→ rejected
いずれの状態からも → deleting → deleted（tombstone）
```

- `deleted` は終わりの状態で、ほかの状態には戻らない（M9）。
- 文脈に渡す（provided）のは、`active` だけ。実験の設定で明示した場合に限り、印を付けて `candidate` も渡せる（B1 の6.4）。

### 3.3 種類ごとの採用の判定

**大原則：テストに合格したことは、「何が起きたか」の根拠にはなるが、「なぜ成功したか」の根拠にはならない。**

| 種類 | 自動で採用してよい条件 | 人間の確認か、独立した検証が必要な場合 |
|---|---|---|
| Episodic（観測） | 根拠が `runtime_observed` で、参照が正しい（起きた事実の記録だけ） | 説明の文を含む場合、その文は D4 として別に持つ |
| Semantic（プロジェクトの事実） | 元のファイルと照合でき、決定的な規則で確かめられる（例：「ビルドの手順は X」→ 設定ファイルに X がある）。または、実際に実行して確かめられる | 外部の情報（D2）だけから得た事実、重要度の高い事実、他の記憶と矛盾する事実、機械では確かめられない規約（プロジェクトの管理者が確認する） |
| 確認済みの原因、検証済みの対策 | **自動では採用しない** | `verified` にするには、再現による検証（反実仮想テスト）が必要。反実仮想テストとは、対策を外すと失敗し、入れると成功することを、繰り返して確かめること。それができない場合、人間は「未検証の仮説として使ってよい」と承認できるだけで、確認済みにはならない（3.4） |
| Procedural（手順） | **自動では採用しない** | 評価用のタスクで合格し（判定の基準は D）、さらに人間が承認すること。バージョンごとに有効にする |
| User Memory | ユーザーがはっきり述べたこと（`user_input`） | 推測した好みは、ユーザーが確認するまで候補のまま |

**独立した検証の決まり**

- 候補を作ったモデル呼び出しと同じ呼び出しで、検証してはならない。別の手段で確かめる。手段は、決定的な検査、テストの実行、別の設定や別のモデルによる確認（MODEL_CALL）、人間による確認のどれか。
- モデルを使う抽出と検証は、どれも `ModelAssistRequest` として、`MODEL_CALL` の手順（予算の予約、Safety の判定、送信の認可、Intent、Permit）を通す。

### 3.4 根拠の強さと、人間の承認を分ける（B2-R06）

**2つの軸**

| 軸 | 値 | 意味 |
|---|---|---|
| `verification_status`（検証の状態） | `observed` | Runtime が観測した事実（何が起きたか） |
| | `unverified` | 未検証の仮説 |
| | `verified` | 独立した根拠で検証した内容 |
| `use_approval`（利用の承認） | `approved` | 人間が「この範囲で使ってよい」と承認した。**検証の状態は変わらない** |

- 人間が承認しただけで、未検証の原因を「技術的に確認済み」として扱うことはしない。
- 承認された仮説は、文脈の中でも「未検証（承認済みの仮説）」と表示する。

**独立した根拠とは**

次の2つを両方満たすものだけを、独立した根拠として数える。

1. **元が違う：** 系譜をたどったときに、元になった資料や観測が、主張の根拠と重ならない。
2. **反証できる：** その確かめ方で、主張が間違っていれば、間違いだと分かる。例：反実仮想テスト、新しく実行した観測。

独立した根拠に**数えないもの**：

- 同じ元資料を読んだ、別のモデルや別のプロンプトによる確認。これは「見直し」であって、根拠は増えない。
- 同じテストを同じ条件で繰り返した結果。これは観測が再現できることの確認にはなるが、原因の説明を独立に支えるものではない。
- こだま（6.4）と、利用の回数。

**種類ごとの検証の方法**

| 種類 | 検証の方法 | 人間の役割 |
|---|---|---|
| ユーザーの好み | ユーザー本人がはっきり述べたこと、またはユーザーの確認。行動から推測した好みは、確認されるまで有効にしない | 情報の出どころそのもの（本人であることが、根拠になる） |
| プロジェクトの事実 | 今の元ファイルとの決定的な照合、または実際の実行 | 機械で確かめられない規約は、プロジェクトの管理者が確認する |
| 技術的な原因と対策 | 反実仮想テストと、繰り返しの試行（回数は D で決める） | 利用の承認だけ。検証の代わりにはならない |

## 4. 検索と関連度の判定（B10）

### 4.1 範囲（スコープ）の確定

- `MemoryQueryRequest` で、モデルが指定できるのは、検索の言葉、ヒント、目的だけ。**スコープはモデルには指定させない。**
- Runtime と Safety が `AuthorizedScope` を決める。中身は、テナント、ユーザー、プロジェクト、エージェント、評価の名前空間、取り出してよい種類と機密の区分、`policy_version`。
- 取り出してよい機密の区分は、送信先が許す区分（B1 の5.6）の範囲に収める。

### 4.2 検索の流れ（順番を固定する）

```
① 区画を選ぶ：AuthorizedScope が許す区画だけを開く（4.3）。許されない区画の索引ファイルには、触れない
② 権限による絞り込み（SQL、許された区画の中だけ）：status=active／機密の区分／有効期限の内側／
   削除中や削除済みでない（7.8 の拒否リストも確かめる）／適用の条件に合う
③ 照合：FTS5 の MATCH を、一致したかどうかの判定だけに使う。bm25() や rank は使わない
   （索引全体の統計を使う計算をしない）。confidential と personal の記憶は索引に入れていないので、
   許された少数の集合を復号し、手元で照合する（4.3）
④ 順位付け：その記憶だけで決まる特徴量で計算する
   score = w1·一致した語の数と位置 ＋ w2·新しさ ＋ w3·根拠の強さ ＋ w4·重要度 ＋ w5·測定した有用性
   - 矛盾の印や、古くなりかけている印がある記憶には、それを示す情報を付ける
⑤ Context Engine から割り当てられたトークン数に合わせて、上から順に詰める（B1 の記憶の区画。最小 0）
```

- **権限と順位付けを分ける：** 権限のない記憶は、①〜⑤のどの段階にも入らない。統計、順位、件数、キャッシュのどこにも影響しない。たとえば「ほかに N 件あります」のような表示も出さない（M6、M19）。
- **`w5`（測定した有用性）：** 比較実験（記憶あり／なしのアブレーション）で得た値だけを使う。単に「使われた回数」や「使ったときの成功率」は使わない（M3）。初期値は 0。
- **検索する時期：**
  - タスクを始めるとき（1回）
  - モデルが要求したとき
  - 失敗を観測したとき（エラーの特徴が似た過去の事例を探す）
- **延期するもの：** ベクトル DB、知識グラフ、高度な検索モデルや並べ替えのモデル。

### 4.3 同じテナントの中での、検索範囲の隔離（B2-R01）

**4つの方式の比較**

| 方式 | 隔離の強さ | 費用・複雑さ | 判断 |
|---|---|---|---|
| (a) 許された範囲ごとに索引を分ける | 区画の単位がアクセス権の単位と同じなら、統計に混ざるのは許された記憶だけになる | 区画の数だけ索引が増える。記憶ごとに細かい ACL があると、区画が増えすぎる | **v1 で採用**（区画の単位を限る） |
| (b) 許された集合だけでスコアを計算する | 完全。許された集合から、手元で統計を作る | 許された記憶の件数に比例して時間がかかる | 性能評価の後に、(a)の上で BM25 が必要になったら追加する |
| (c) 初期段階は単純で決定的な検索にする | 索引全体の統計を使わないので、統計による漏えいがない | 最も単純。順位の質は落ちうる | **v1 で採用**（(a)と組み合わせる） |
| (d) 将来、アクセス制御に対応した検索基盤にする | 基盤による | 依存関係が増え、運用も重くなる | 将来の候補 |

**v1 での実装方法**

- **区画：** `tenant_shared`、`project:<id>`、`user:<id>`、`agent:<id>`。1つの記憶は、1つの区画にだけ属する。
- **区画ごとの索引：** 区画ごとに、別の FTS5 索引ファイル（`index/<tenant>/<partition>.db`）を持つ。
- **細かい共有はしない：** 記憶ごとの細かい共有（特定のユーザーにだけ見せる、など）は、v1 では扱わない。別の区画と共有したい場合は、承認を経て、新しい記憶 ID で写しを作る（系譜で元と結び付ける）。
- **順位付け：** BM25 などの、索引全体の統計を使う計算はしない（4.2 の③④）。順位は、その記憶だけで決まる特徴量だけで決める。
- **索引に入れないもの：** confidential と personal の記憶は、FTS 索引に入れない。許された区画の中から、メタデータで少数に絞り込み、復号して手元で照合する。件数には上限を設け、超えたら、検索の言葉を絞り込むよう求める。
- **キャッシュ：** 検索結果のキャッシュの鍵は、`AuthorizedScope` のハッシュ、`store_seq`、`access_epoch`（7.8）の組にする。範囲をまたいで、キャッシュを共有しない。権限や削除の状態が変わったら、すぐに捨てる。
- **件数：** 返す件数は、許された集合の中だけの件数にする。

**残る限界**

- 照合にかかる時間は、許された区画の大きさによって変わる。それでも、許されない区画の大きさには左右されない。許されない区画の索引ファイルは開かないため。
- ファイルシステムの階層で、区画の存在（ファイルの数や名前）が分かってしまう可能性がある。ファイル名には、推測しにくい ID を使う（C と調整する）。

## 5. 成功と失敗からの学習（B11）

### 5.1 別々に持つ記録

| 記録 | provenance | 自動で active にするか |
|---|---|---|
| 観測した成功・失敗（タスクの特徴、結果、エラーの特徴、環境の版） | `runtime_observed` | する（Episodic） |
| 原因の仮説 | `model_hypothesis`（D4） | しない。`status=candidate` のまま「未検証」として渡すか、渡さない |
| 確認済みの原因 | 仮説を、独立した根拠（再現）で検証した結果。人間が承認しただけの仮説は、「承認済みの仮説」のままにする | 3.3・3.4 に従う |
| 実施した対策 | `runtime_observed`（Journal に記録された差分と操作） | する（Episodic） |
| 検証済みの対策 | 反実仮想テストと、繰り返しの試行。人間の承認は、利用の承認にとどまる | 3.3・3.4 に従う |
| 適用できる条件・適用できない条件 | 観測と検証から作る。うまくいかなかった例も含める | 条件のない対策は「条件不明」と印を付ける |

### 5.2 誤った対策を当てはめないために

- 対策は、D3 として「参考：条件 X のときに有効だった（根拠 …）」という形で渡す。命令にはしない。
- 渡す前に、`applicability` を今の状況と機械的に照合する。条件が分からない対策は、仮説の扱いで注意書きを付けるか、渡さない。
- 対策を当てはめて**新しい失敗**が起きた場合は、うまくいかなかった例として記録する。適用の条件を狭め、確信度を下げ、再検証の対象にする。
- 手順の記憶や対策の記憶を、自動で実行の権限や Safety のポリシーに変えることは**禁止**（M5）。どの操作も、通常の Safety の判定と承認を通る。
- 利用回数や、成功との相関は、因果の証拠として扱わない（M3）。

### 5.3 同じ失敗を繰り返さない仕組み

- 失敗を観測したら、エラーの特徴（種類、正規化したメッセージ、場所）で、過去の事例と検証済みの対策を検索する。
- タスクを始めるときに、似た特徴のタスクで過去につまずいた点（既知の落とし穴）を検索する。
- 評価では、「同じ失敗の再発率」と「記憶が引き起こした新しい失敗の割合」を、両方とも測る（11章）。

## 6. 品質の管理と汚染への対策（B12）

### 6.1 古くなった記憶

- Semantic の記憶は、元のファイル（リポジトリ、パス、ハッシュ、コミット）に結び付ける。
- 元のファイルが変わったら `stale` にし、再検証する。再検証には、まず決定的な照合を使い、必要ならモデルによる確認（MODEL_CALL）を使う。
- ツールの版などの適用条件が変わった場合も、同じく再検証する。
- 種類ごとに有効期限と再検証の期日を持たせる（既定値は PROVISIONAL）。
  - Episodic：期限なし。ただし過去の事実として渡す。
  - Semantic：再検証を 90日ごと。
  - 対策と手順：再検証を 180日ごと。
  - User Memory：ユーザーの同意の方針に従う。
- 期限切れの記憶と `stale` の記憶は、渡さない（M14）。

### 6.2 矛盾、訂正、重複

- **矛盾の検出：**
  - 構造化キーの衝突（同じ `subject` と `predicate` で `object` が違う）
  - FTS の類似度と否定表現の手がかり
  - 評価の後は、モデルによる検出（MODEL_CALL）も加える
- **矛盾の解決：** 「新しいほうが正しい」とはしない。次の順で比べる。
  1. 根拠の強さ（再現できる > 観測した > 人間が述べた > 推測）
  2. provenance
  3. 最後に検証した日
  - それでも決まらない重要な矛盾は、両方を `quarantined` にして人間に確認する（M15）。
- **訂正：** 新しいバージョンを作り、`supersedes` で結ぶ。古いバージョンは監査のために残す（削除の要求があれば消す）。訂正した記憶から派生した記憶には、再検証の印を付ける（系譜をたどる）。
- **重複の統合：** 1つの正規のレコードにまとめ、根拠は合わせて持つ。確信度は、**互いに独立した根拠**（出どころと検証の方法が違うもの）だけから計算する。

### 6.3 悪意のある情報と、他テナントの混入

- 根拠が外部の情報（D2 や `external_extracted`）だけの記憶は、自動で active にしない。
- 命令のような文章（「〜を実行せよ」「権限を付与する」など）を含む候補は、`quarantined` にする。記憶はもともと D3 なので、命令にも権限にもならない（B1 の C13、M5）。
- 他のテナントの記憶が混ざらないように、テナントごとに DB を分ける（M7）。同じテナントの中は、区画ごとに分ける（4.3、M19）。書き込みと読み込みのたびに範囲（scope）を確かめる。

### 6.4 AI が作った情報の自己強化を防ぐ

- 同じ内容が何度書かれても、正しい証拠にはしない。
- 候補の根拠をたどった結果、その候補自身の元になった記憶に行き着く場合（記憶を渡す → モデルが言い直す → Reflector が同じ内容を候補にする）は、**こだま（echo）**と判定する。こだまは、確信度を上げる根拠として数えない（M4）。
  - 判定には、`MemoryUsed`（文脈に入れた記録）と、候補の `derived_from_chain` を使う。
- 確信度を変えられるのは、検証の結果だけ。使われた回数では変わらない。
- 「新しい記憶は正しい」とも判断しない。根拠と情報の性質で判断する。

## 7. 削除とプライバシー（B13、B1-P03）

### 7.1 派生データの系譜（Lineage）

すべての派生データに、元になった記憶の `memory_id@version` を記録する。

| 派生データ | 系譜を記録する場所 |
|---|---|
| Context IR、変換済みの文脈、リクエストの記録 | Manifest の `included[]`（B1 の2.5） |
| モデルの応答 | 応答を生んだリクエストの `context_hash` を経由して |
| 要約 | CompactionRecord の `source_item_hashes` |
| 派生した記憶 | `lineage.derived_from` |
| 評価の結果 | 評価に使った実行の名前空間（D） |
| バックアップ | 世代ごとに、含まれている DB と blob の範囲（7.7） |
| そのほか（B2-R07） | 生成したファイルやコード、ツールへの入力、外部ツールの結果、評価用の成果物、書き出した文書、ログやトレース、何段階も経由した派生データ。7.9 で扱う |

### 7.2 削除の理由を2つに分ける

| 理由 | 例 | 派生データの扱い |
|---|---|---|
| プライバシーや法令による削除 | ユーザーの記憶の削除、ユーザー単位での削除 | 系譜でたどれる派生データを**すべて**消す |
| 品質のための廃止 | 誤った記憶、古い記憶 | 渡すのを止め（`deprecated`／`superseded`）、監査のために残す。派生した記憶には再検証の印を付ける |

### 7.3 3つの方式の比較

| 方式 | 良い点 | 問題 |
|---|---|---|
| A. 物理削除と、派生データの無効化 | 鍵の管理が要らず、仕組みが単純 | すべての複製を探して消す必要がある。バックアップの中身を書き換えにくい。見落としが起きやすい |
| B. 暗号鍵の破棄（crypto-shredding） | 鍵を消すだけで、バックアップを含むすべての暗号文が読めなくなる | 鍵のバックアップが残る。平文のキャッシュが残る。派生データは別の鍵で暗号化されていて残る。複数の記憶をまとめた blob では、記憶ごとに鍵を分けられない |
| **C. 両方を組み合わせる（採用）** | 記憶の本体とそのバックアップは B で、まとめた派生データは系譜をたどって A で消す。両方の弱点を補い合える | 手順が増える。完了したと言えるのは、バックアップの保管期間が過ぎてから |

**C の具体的な中身**

- 記憶の本文は、記憶ごとの鍵で暗号化する。鍵は `keys/<tenant>.db` に分けて置き、その DB のバックアップの保管期間は短くする（期間は設計A の課題 P1 で決める）。
- まとめた派生データ（IR、変換済みの文脈、リクエストの記録、応答、要約）は、系譜で見つけて物理的に削除する。各 blob の鍵を破棄してもよい。
- 平文のキャッシュは、永続化しない（プロセスのメモリの中だけに置き、削除のイベントで消す）。
- SQLite は `secure_delete` を有効にする。FTS5 は、行を削除したうえで索引を最適化する。WAL はチェックポイントで切り詰める。これで削除した内容が空き領域に残る量を減らす。ただし、**ファイルを削除したことを、媒体からの完全な物理消去とはみなさない**（7.6 の保証の範囲）。効き方は未確認なので、検査で確かめる。
- 最初から複雑な鍵管理の仕組みは作らない。v1 では、手元の SQLite に置いた鍵の表で足りる。

### 7.4 保存先ごとの反映

| 保存先 | 削除の反映 |
|---|---|
| Memory Store | 行を削除し、tombstone（ID、削除の日時、理由の区分、要求の参照。本文は入れない）を残す |
| 検索インデックス（FTS5） | 行を削除し、索引を最適化する |
| キャッシュ | 削除のイベントで、すぐに捨てる |
| Journal | もともと本文を持たないので、書き換えない。`MemoryDeletionRequested` などのイベントを追記する。鍵付きのハッシュは、鍵の破棄で照合できなくなる |
| Snapshot（設計A） | Journal の投影なので、本文を持たない。記憶の投影は、Journal のイベントから作り直す |
| Context IR、変換済みの文脈、リクエストの記録 | 系譜でたどって、blob を削除する（または鍵を破棄する）。その Run には「Replay できない」と印を付ける |
| Replay の記録 | 上と同じ。該当する Run は `REPLAY_UNAVAILABLE`（B1 の C24） |
| 要約 | プライバシーによる削除なら削除する。品質のための廃止なら印を付ける |
| 派生した記憶 | プライバシーによる削除なら削除する。同じ内容が独立した別の根拠でも支えられる場合は、通常の候補の経路で**新しい記憶として**作り直してよい。元の記憶を復元するわけではない |
| モデルの応答 | プライバシーによる削除なら、応答の blob を削除する |
| バックアップ | 本文の暗号文は、鍵を破棄すれば読めなくなる。復元したデータは隔離し、最新の削除記録と照合してから使い始める（7.7、M22）。削除が完全に終わるのは、削除の対象を含みうる**すべての**バックアップの世代が期限切れになった時点（7.7） |
| 外部のプロバイダー | **Agent Core の側で消しても、プロバイダーに送ったデータまで消えたとは言わない。** 系譜から「どのリクエストで送ったか」を報告できるようにする。プロバイダー側の保管の扱いは C で確認する |

### 7.5 削除の手順と、障害からの再開

```
REQUESTED  →  直ちに取得を止める（Retriever、get_stored、Replay が削除の印を確かめる）
   ↓          ※ Journal に MemoryDeletionRequested を記録した時点で、取得は止まる
PURGING    →  索引 → Store → 系譜の対象の blob → キャッシュ → 鍵、の順に進める
   ↓          各手順は冪等で、1手順ずつ Journal に記録する。障害の後は、記録の続きから再開する
VERIFYING  →  残っていないかを検査する：目印の値を使った検索、FTS の照会、blob と鍵の有無、系譜の対象がすべて処理済みか
   ↓
COMPLETED_LIVE  →  BACKUP_EXPIRY_PENDING  →  FULLY_COMPLETED
```

- `FULLY_COMPLETED` に進むのは、次の世代がすべて期限切れになるか消され、そのうえで検査を通ったときだけ（M23）。
  - 鍵のバックアップだけでは足りない。
  - 平文を含みうる世代（Memory の DB、FTS の索引、WAL、派生データの blob、ログ）と、復号できる暗号文を含みうる世代の、両方を対象にする。

**削除したデータが復活しないための決まり**

- 投影を作り直す処理（Rebuild を含む）は、tombstone を必ず当てはめる。
- バックアップから復元するときも、tombstone を必ず当てはめる。
- 根拠が削除済みのデータを参照している候補は、却下する。
- ユーザーが「同じことを二度と覚えないで」と求めた場合の扱い：内容の鍵付きハッシュを「再学習しない一覧」に残す方法があるが、ハッシュを残すこと自体が情報を残すことになる。これは C とオーナーが判断する事項として残す。

### 7.6 保存する範囲と暗号化（B2-R02）

**保存先ごとの方針**

| 保存先 | 方針 |
|---|---|
| `structured` の項目 | 内容を表す項目（`subject`/`object`、エラーのメッセージ、パスなど）は、本文と同じく暗号化した blob に入れる。平文で持ってよいのは、内容を含まない項目だけ。ID、種類、状態、時刻、区画の ID、機密の区分、重要度、`key_id`、系譜の ID がこれにあたる。照合には `blind_tokens` を使う |
| `MemoryCandidateProposed` などのイベント | 本文も、`structured` の平文も入れない。参照、`key_id`、記憶ごとの MAC 鍵で計算したハッシュだけを入れる。`blind_tokens` も Journal には入れない（削除の後に、照合できる値を残さないため）。**これで M8 と食い違わない** |
| FTS5 の索引 | FTS が働くには平文が必要なので、索引の中身は平文である。そのため、public と internal の記憶だけを索引に入れ、区画ごとに分ける。削除は 7.3 の手順で行う |
| SQLite の WAL と一時ファイル | `temp_store=MEMORY` にして、一時ファイルを作らない。削除の後には、WAL のチェックポイント（TRUNCATE）を行う。`secure_delete` も有効にする |
| Snapshot（設計A） | Journal の投影で、記憶の内容は持たない。記憶の DB の写しは、バックアップとして扱う |
| ログ | 記憶の本文と `structured` の中身は、ログに出さない。出すのは ID だけ。デバッグ用でも出さない。目印の値を使った検査で確かめる |
| 平文のキャッシュ | プロセスのメモリの中だけに置き、有効期間に上限を設ける。鍵は範囲（scope）ごとに分ける。永続化しない。`access_epoch` が変わったら捨てる |
| バックアップ | 世代を管理する（7.7）。鍵の DB は、データとは別にバックアップし、保管期間を短くする |
| 鍵の DB | 記憶ごとの鍵は、テナントの鍵暗号化鍵（KEK）で包んで保存する。KEK は鍵の DB には置かない（置き場所は C で決める） |

**鍵を用途ごとに分ける**

- 記憶ごとに、元になる鍵を1つ持つ。
- そこから HKDF（鍵導出関数）で、用途を表すラベルを変えて、暗号化の鍵と MAC の鍵を作る。**同じ鍵を、暗号化と HMAC の両方に使うことはしない**（M20）。元の鍵を破棄すれば、両方とも使えなくなる。
- テナントの単位では、用途ごとに別の鍵を持つ。
  - 索引の鍵（`blind_tokens` 用）
  - KEK
  - B1 の context_hash 用の鍵
- アルゴリズムの選び方は、C で決める。

**保証できる範囲**

- 削除が `COMPLETED_LIVE` になった後は、Agent Core の API のどれを使っても、その内容は返らない。
- Agent Core が把握している管理下のファイル（Store、索引、blob、WAL、ログ）に、平文が残っていないことを、目印の値を使った検査で確かめる。
- 鍵を破棄した後は、元の鍵と KEK の写しがすべて消えている限り、暗号文の写しは読めない。

**保証できない範囲**

- 媒体からの物理的な消去。SSD の書き込み分散、ファイルシステムのジャーナル、OS やクラウドのスナップショットなど。
- メモリの内容がディスクに書き出されること（スワップ）。
- Agent Core の外に出た写し。外部のプロバイダー、書き出した文書、push したコード、人が控えたもの。
- FTS の索引が最適化されるまでに、空き領域に残る断片。
- 処理時間などから情報が漏れるサイドチャネル。

**引き継ぎ：** 保存する前の機密の検査は、B1-P01 とまとめて設計C で決める。

### 7.7 削除記録とバックアップからの復元（B2-R03）

**削除記録の正本と、独立した写し**

- **正本：** Journal に記録した、削除のイベント。
- **独立した写し：** 削除台帳（`deletion-ledger/`）。
  - 追記専用で、ハッシュの連鎖にし、台帳用の鍵で MAC を付ける。
  - データのバックアップとは**別の場所**に置く。
  - 保管期間は、削除の対象を含みうるバックアップの、最長の保管期間より長くする。
  - 中身は ID、時刻、理由の区分だけで、内容は入れない。
- **台帳の先頭の目印（anchor）：** 台帳の最新の位置（seq とハッシュ）を、さらに別の場所に置く。これは、台帳が古いものに差し替えられていないかを見分けるため。

**バックアップの世代の管理**

- 世代ごとに、次の情報を目録に記録する。
  - 世代 ID と、作成の時刻
  - 含まれる保存先
  - その時点の `journal_seq` と、削除台帳の先頭の位置
  - 保管期限
- 世代の種類ごとに保管期限を決める。
  - `R_data`：Memory の DB と索引
  - `R_blob`：本文と派生データの blob
  - `R_key`：鍵の DB（最も短くする）
  - `R_ledger`：削除台帳（最も長くする）
  - 具体的な値は、設計A の課題 P1 と設計E で決める。

**復元の手順**

```
① 復元したデータは「隔離区画」に置き、一切渡さない
② 最新の削除台帳を取り出し、連鎖と MAC を検証する。先頭の目印とも照合する
③ バックアップの時点より後の削除記録を、すべて当てはめる
④ 最新の権限の状態（policy_version、区画の権限）を当てはめる
⑤ 安全性を検証する：削除した ID と目印の値の検査、範囲の隔離の試験の一部
⑥ すべて合格したら、隔離を解いて使い始める
```

- **最新の削除の状態を確かめられない場合は、復元した記憶へのアクセスを許さない**（M22）。台帳がない、連鎖が壊れている、目印より古い、などの場合がこれにあたる。隔離したまま、人間に確認する。
- Journal もバックアップから復元した場合、Journal はバックアップの時点のものに戻るので、それより後の削除イベントが含まれていない可能性がある。そのため、③では必ず独立した削除台帳を使う。

### 7.8 削除や権限の変更と、実行中の Run の競合（B2-R04）

**access_epoch（アクセスの世代番号）**

- テナントごとに、単調に増える `access_epoch` を持つ。
- 削除の要求や権限の変更があると、それを Journal に記録すると同時に1つ増やし、拒否リスト（削除中や削除済みの ID、権限を外された区画）を更新する。
- 書き込むのは Orchestrator だけなので、Permit の発行と、epoch の更新は、必ずどちらかが先になる。同時に起きることはない。

| 対象 | 扱い |
|---|---|
| 取得済みの記憶 | 次に文脈を組み立てるときに、拒否リストで外す |
| 組み立て済みの Context | `MODEL_CALL` の Permit を発行する前に、Manifest に含まれる記憶の ID を、今の拒否リストと権限で確かめ直す。外れていれば、そのリクエストを取り消し（予約を解放）、組み立て直す |
| キャッシュ | epoch が変わったら、すぐに捨てる |
| 送信待ちのリクエスト | 上と同じ。Permit の発行の前に確かめ直す |
| 実行中のモデル呼び出し | 取り消せない。応答には「汚染あり」と印を付ける。応答を記憶の候補や要約の材料にしない。応答の blob は、系譜による削除の対象にする。**外部に送った情報を取り消せたとは言わない** |
| 生成途中の要約 | 結果が届いたら、系譜を拒否リストと照合する。対象を含んでいれば、保存せずに捨て、対象を外して作り直す |
| 新しい記憶の候補 | 根拠や派生元の経路に、拒否リストの ID が含まれていれば却下する。対象を含む文脈から作られた候補も却下する（汚染の伝わり、M25）。これで、古い処理から再び保存されることを防ぐ |
| Replay | 始める前と、各 blob を読む前に、拒否リストを確かめる。対象があれば `REPLAY_UNAVAILABLE` |

- **Run の範囲そのものが外された場合：** Run を `WAITING_APPROVAL` に移す。
- **残る限界：** Permit を発行した後、Worker がすでに送信した操作は、設計A の A08 のとおり止められない。

### 7.9 派生データの追跡と、削除の限界（B2-R07）

**系譜は多段階の関係（DAG）として持つ**

- 系譜には、記憶 → 要約 → 別の記憶 → 文脈 → 応答 → ファイル、のような何段階もの関係を記録する。
- 削除の影響の範囲は、この関係をたどって求める。たどる段数と件数には上限を設け、上限を超えたら、その旨を報告する。

| 派生データ | 系譜の記録のしかた | 管理の区分 |
|---|---|---|
| AI が生成したファイルやコード | ファイル変更のイベントに、その Step の `context_hash` を結び付ける | 作業ツリーの中は管理下。commit や push した後は、外部への出力 |
| ツールへの入力 | Step の引数のハッシュと blob を、`context_hash` と結び付ける | 管理下 |
| 外部ツールの結果 | 外部へのリクエストに記憶の内容が含まれていれば、外部へ送ったものとして記録する | 結果は管理下。送った内容は外部 |
| 評価用の成果物 | 評価の名前空間と Run を経由する | 管理下 |
| 書き出した文書 | 書き出しのイベントに、送り先を記録する | 外部への出力 |
| ログやトレース | 内容を含めない方針（7.6）。ID だけを記録する | 管理下 |
| 間接的な派生 | 上の関係をたどって、すべての段階を求める | 各ノードの区分による |

**影響の範囲の報告**

- 削除のときには、Agent Core が消せる管理下のデータと、外部に出たデータを分けて報告する。
- 外部に出たデータについては、送り先と時刻だけを報告し、「削除した」とは言わない。

**関係のない内容も含む、共有された派生データの扱い**

- **v1：** プライバシーによる削除では、その派生データを丸ごと削除する（消しすぎることは受け入れる）。
- **コードや作業の成果物：** 正当な作業の結果でもあるので、自動では消さない。人間の確認に回す。
- **性能評価の後：** 対象を外して作り直せるようにする（MODEL_CALL を使い、新しい成果物として作る）。

**限界**

- 記憶が文脈に入っていた Step から生まれた成果物は、すべて「影響を受けた可能性がある」として扱う（多めに見積もる）。
- モデルの内部で、記憶がどこにどう影響したかまでは追えない。

**削除した情報の再抽出の防止：** 消した内容は、残っている元資料（書き出した文書、ユーザーの再度の発言など）から、もう一度抜き出されることがある。その防止の方針（再学習しない一覧など）は、C と連携して決める。

## 8. Runtime・Context Engine との接続仕様

| イベント・要求 | 意味とスキーマ |
|---|---|
| `MemoryQueryRequest` | Engine が返す要求：`{query_text_ref, task_features, hints, purpose, budget_tokens, k}`。**`scope` は含まない。** Runtime が `AuthorizedScope` を付けて実行する |
| `MemoryQueryResult` | Journal に記録する：`{request_id, authorized_scope_hash, store_seq, results[{memory_id, version, status, score_breakdown, content_ref}]}`。本文は入れない |
| `MemoryUsed` | **記憶を文脈に入れたこと**を記録する：`{memory_id@version, run_id, step_id, context_hash, semantics: "provided_in_context"}`。モデルが実際にその記憶を使ったことの証明ではない（M16）。名前は、承認済みの接続口を変えないためにそのまま残す |
| `MemoryCited`（追加） | モデルの出力が、記憶の ID をはっきり参照したこと。これも効果の証拠にはならない |
| `MemoryCandidateProposed` | `{candidate_id, type, partition, key_id, content_ref, structured_ref, content_mac, evidence_refs[], provenance, proposer, attempt_id, run_id, context_hashes[]}`。`structured` の平文と `blind_tokens` は入れない（7.6） |
| 状態の変化 | `MemoryValidated`, `MemoryPromoted`, `MemoryRejected`, `MemoryMarkedStale`, `MemorySuperseded`, `MemoryQuarantined`, `MemoryDeletionRequested`, `MemoryDeletionStep`, `MemoryDeleted`。どれも本文を含まない |

- **context_hash：** 記憶の項目は、B1 の ContextItem（D3）として IR に入る。`item_content_hash` は、記憶ごとの鍵で計算した鍵付きのハッシュを使う。そのため、鍵を破棄すると照合できなくなり、Replay は `REPLAY_UNAVAILABLE` になる。
- **Rebuild：** Journal を読んで、記憶の状態（状態、系譜、tombstone、拒否リスト）を**メモリの中で**計算するだけ。永続的な保存先には書き込まない（M27）。設計A の2.2、B1 の C9 と同じ意味である。行わないことは次のとおり（M12）。
  - 記憶の作り直し
  - モデルの呼び出し
  - 外部の検索
  - 本文が blob にない場合の作り直し（`unavailable` として扱う）
- **ProjectionRepair（投影の修復）：** Journal のコマンドと、すでにある blob から、`memory/<tenant>.db` と区画の索引を作り直したり、最新の状態まで追いつかせたりする、**保守のための別のモード**（8.1）。
  - 排他のロック（設計A の A11）を持った状態で行う。
  - モデルの呼び出し、外部へのアクセス、内容の作り直しはしない。
- **Replay：** 記録された IR と `MemoryQueryResult` を使う。今の記憶を照会することはない（M11）。
- **順序：** Safety の判定、予算の予約、Intent、Permit の順序を、設計A と B1 の間でそろえる作業は、設計E で行う（B1-P04）。

### 8.1 Journal と Memory Store にまたがる、書き込みと障害からの復旧（B2-R05）

**記憶を作るときの書き込みの手順**

```
W1 鍵を作る：keys/<tenant>.db に、記憶ごとの元の鍵を、状態 PENDING（candidate_id 付き）で保存する
W2 本文と structured を暗号化して、blob に保存する（内容のハッシュで管理。目録の状態は PENDING）
W3 Journal に MemoryCandidateProposed（または状態を変えるコマンド）を記録する ← ここが確定の時点
W4 ProjectionRepair と同じ反映処理を行う。1つの SQLite トランザクションの中で、次をまとめて行う：
   memory/<tenant>.db のレコード、系譜の行、last_applied_seq の更新
W5 区画の索引（index/<tenant>/<partition>.db）に反映する。索引の側にも last_applied_seq を持つ
W6 鍵と blob の状態を COMMITTED にする（後片付け。Journal から参照されていることが、正となる根拠）
```

**クラッシュした地点ごとの復旧**

| クラッシュの地点 | 状態 | 復旧の手順 |
|---|---|---|
| W1〜W2 の間、または W2〜W3 の間 | 鍵や blob が、どこからも参照されていない（孤立） | 猶予の期間が過ぎたら、孤立した鍵は破棄し、blob は削除する。Journal に記録がないので、この記憶は存在しなかったものとして扱う |
| W3〜W4 の間 | Journal にはあるが、投影がまだ | `last_applied_seq` の次から、反映をやり直す |
| W4 の途中 | トランザクションが確定していない | SQLite が巻き戻すので、W3〜W4 の間と同じ扱いになる |
| W4〜W5 の間 | Store は最新だが、索引が古い | 索引の `last_applied_seq` の次から、反映をやり直す。それまで、その区画の検索は止める |
| W5〜W6 の間 | 鍵や blob の状態が PENDING のまま | Journal から参照されていれば COMMITTED にする |
| Journal が参照している blob や鍵がない | 欠けている | そのレコードを `unavailable` にし、渡さない。調査の対象として記録する。**内容は作り直さない** |

**重複して当てはめることを防ぐ**

- 投影の各行に、元になったコマンドの `source_seq` を持たせる。
- 当てはめるのは、届いたコマンドの seq が、行の `source_seq` より大きいときだけ（冪等）。

**古い投影の扱い**

- 投影や索引の `last_applied_seq` が、最新の削除や権限変更のイベントの seq より小さいときは、Memory の検索を止める。結果は `MEMORY_UNAVAILABLE` とし、安全側に倒す（M26）。
  - Run そのものは止めない。記憶の区画は最小 0 なので、記憶なしで続ける。
- 投影が Journal より先に進んでいる場合（Journal を古いバックアップから戻した、など）も、検索を止める。そのうえで、7.7 の照合を行う。

### 8.2 B1 との接続仕様についての変更案（確定していない）

以下は、B2 の側で必要になった変更の**案**である。B1 はすでに条件付き合格になっているので、ここでは確定させない。オーナーと審査者の判断を待つ。

| # | B1 の箇所 | 変更案 | 理由 |
|---|---|---|---|

## 10. 不変条件

| ID | 不変条件 |
|---|---|
| M1 | 作業記憶は独立した正本を持たない。正本は Journal だけ |
| M2 | Reflector の出力は、種類ごとの検証を通らなければ active にならない |
| M3 | 確認済みの原因と検証済みの対策（`verified`）には、独立した根拠による再現が必要。人間の承認、利用の回数、相関は、検証の代わりにならない |
| M4 | 確信度は、互いに独立した根拠（3.4 の定義）だけから計算する。繰り返し、こだま、同じ元資料を読んだ別のモデルによる確認は、根拠に数えない |
| M5 | 記憶は D3 であり、命令、権限、ポリシーにはならない。手順の記憶が実行の権限に変わることはない |
| M6 | 範囲（scope）は Runtime と Safety が決め、モデルは広げられない。権限のない記憶は、同じテナントの中の別のユーザー・プロジェクト・エージェントのものも含めて、候補の選択、索引の統計、順位付け、結果、件数、キャッシュのどこにも影響しない |
| M7 | テナントごとに保存先を分ける。テナントをまたいで読み書きする経路はない |
| M8 | Journal には、記憶の本文も、`structured` の平文も、`blind_tokens` も入れない |
| M9 | 削除を要求した時点で、取得を止める。削除の手順は冪等で、途中から再開できる。再開、Rebuild、ProjectionRepair、バックアップからの復元のどれによっても、削除したデータは復活しない |
| M10 | 派生データには、元になった記憶の ID を記録する。プライバシーによる削除は、多段階の系譜でたどれる管理下のすべてのデータに及ぶ。外部に出たデータは、報告するだけで、削除したとは言わない |
| M11 | Replay は、今の記憶を照会しない。必要なデータや鍵がなければ `REPLAY_UNAVAILABLE` |
| M12 | Rebuild は、記憶の作り直し、モデルの呼び出し、外部の検索をしない |
| M13 | 記憶のためのモデル呼び出し（抽出、検証、再検証、矛盾の検出）は、すべて `MODEL_CALL` |
| M14 | `stale`、期限切れ、`quarantined`、削除中、削除済みの記憶は、渡されない |
| M15 | 「新しいほうが正しい」とはしない。矛盾は根拠と出どころで判断し、重要な矛盾は人間に確認する |
| M16 | `MemoryUsed` と `MemoryCited` は、文脈に入れたことと参照したことの記録であり、効果の証拠ではない |
| M17 | 評価に使う記憶の名前空間は、互いに分ける。事前に決めた連続タスクの範囲の外で、記憶を共有しない。holdout は、開発用の記憶に入らない |
| M18 | User Memory の機密の区分は、初めから `personal`。送信先が許さない場合は送らない（B1 の C23） |
| M19 | 索引の区画の単位は、アクセス権の単位と同じ。区画をまたいで、索引全体の統計を使わない。検索結果のキャッシュの鍵は、`AuthorizedScope`、`store_seq`、`access_epoch` の組 |
| M20 | 暗号化の鍵と MAC の鍵は、用途ごとに分ける。同じ鍵を両方に使わない |
| M21 | confidential と personal の内容は、平文の FTS 索引、ログ、永続化したキャッシュ、一時ファイルに入らない |
| M22 | 削除台帳は、データのバックアップとは別に保護する。復元したデータは、最新の削除台帳と照合し終わるまで隔離する。最新の削除の状態を確かめられなければ、アクセスを許さない |
| M23 | `FULLY_COMPLETED` に進むのは、削除の対象（平文、または復号できる暗号文）を含みうるすべての世代が期限切れになるか消され、検査に合格したときだけ。ファイルの削除を、物理的な消去とは主張しない |
| M24 | `MODEL_CALL` などの外部への送信の Permit を出す前と、派生データを保存する前に、拒否リストと権限を確かめ直す |
| M25 | 拒否リストにある記憶を含む文脈から作られた候補、要約、応答は、記憶の材料として保存しない（汚染の伝わり） |
| M26 | 投影への当てはめは、`source_seq` によって冪等に行う。投影が、最新の削除や権限の状態に追いついていないときは、Memory の検索を止める（安全側に倒す） |
| M27 | Rebuild は、永続的な保存先に書き込まない。ProjectionRepair は別の保守のモードで、モデルの呼び出し、外部へのアクセス、内容の作り直しをしない |
| M28 | 検証の状態と利用の承認は、別の軸である。承認しても、検証済みにはならない |

### Performance Gate（Memory v1 の評価。採用の基準は、設計D で事前登録する）

**比べる構成**

1. 記憶なし
2. 単純な記憶（すべてをそのまま保存し、FTS で検索するだけ）
3. Agent Core の Memory Engine
4. 機能を1つずつ外した構成（アブレーション）

| 指標 | 定義 |
|---|---|
| Retrieval precision@k と recall@k | 関係する記憶に注釈を付けた合成の記憶の集合で測る |
| 記憶あり・なしの成功率 | 同じタスクを、記憶ありとなしで実行し、組にして比べる |
| 同じ失敗の再発率 | 過去に見たエラーの特徴を持つタスクのうち、同じ失敗を繰り返した割合 |
| 記憶が引き起こした新しい失敗の割合 | 記憶にある対策を当てはめた後に起きた失敗のうち、記憶なしの構成では起きなかったものの割合 |
| 古い記憶による悪化 | 古い記憶を混ぜたときの成功率の下がり方 |
| 誤った記憶による悪化 | 誤った記憶を混ぜたときの成功率の下がり方と、誤った記憶を採用した割合 |
| 記憶の汚染への耐性 | 悪意のある候補を混ぜたとき、active になった割合と、振る舞いへの影響 |
| トークンの使用量 | 記憶として加えたトークンと、全体のトークンの増減 |
| 成功1件あたりの費用 | 記憶を作る費用（Reflector と検証）と、維持の費用を含める。成功が 0 件なら未定義 |
| 記憶の維持費用 | 一定期間に行った再検証のモデル呼び出し、保存の量、人間による確認の件数 |
| 検索の時間 | p50 と p95 |
| スコープの違反 | 違反した件数 |
| 削除後のデータの復活 | 復活した件数 |

| 記憶の検証にかかる費用（B2-R08） | 検証のためのモデル呼び出し、テストの実行、再検証の費用 |
| 検索にかかる費用 | 検索の処理と、記憶として加えたトークンの費用 |
| 人間による承認の負担 | 承認の件数、待ち行列に入ってから処理されるまでの時間、件数あたりの推定の作業時間 |

- **公平に比べるための共通条件（B2-R08）：** 比べるすべての構成に、同じものを使う。安全性の制約、プライバシーの方針、アクセス制御、予算の上限、実行環境、タスクの集合。
  - 「単純な記憶」の構成でも、範囲の隔離と削除の方針は守る。
- **記憶を増やせば性能が上がる、とは前提にしない。** 記憶の量（少・中・多）を変えて測り、多すぎて悪くなる点がないかを確かめる。
- **連続した作業の評価：** タスクを1件ずつではなく、**一連の作業（関係するタスクの並び）を単位として**比べる。成功率、費用の累計、再発率を、一連の作業ごとに集計する。統計でも、一連の作業を1つの標本として扱う。同じ作業の中のタスク同士は互いに影響し合うので、独立した標本とはみなさないため。
- **因果の判定：** できる限り、次の方法を使う。単なる相関で、因果があると判断しない。
  - 同じタスクを、特定の記憶を入れた場合と外した場合で実行する（記憶の単位でのアブレーション）。
  - 同じ条件で何度も試行する。
  - タスクの順番を無作為に変える。
- 詳しい統計的な合格条件は、設計D で事前登録する。
- **評価の汚染を防ぐ：** 評価の実行ごとに、記憶の名前空間を分け、毎回空にする。連続タスクの評価では、共有してよい範囲（どのタスクの列で、どの種類の記憶を共有するか）を事前に決めて登録する。holdout のタスクに由来する記憶は、開発の側に入れない（D3）。

## 12. 残存リスク

1. **原因の検証が限られる：** 反実仮想テストができない失敗では、確認済みの原因や対策を作れない。人間の確認に頼るため、学べる範囲が狭くなる。
2. **構造化されていない矛盾：** 構造化キーで照合できない矛盾は、v1 では見つけにくい（言い回しが違う重複も同じ）。
3. **削除が完全に終わるまでの時間：** 鍵のバックアップの保管期間が過ぎるまで、削除は完全には終わらない。外部のプロバイダーに送ったデータは、Agent Core の側では消せない。
4. **削除した内容の残り：** SQLite の `secure_delete` と FTS5 の最適化が、削除した内容を空き領域にどれだけ残すかは、確認していない。
5. **適用条件の書き漏れ：** 対策の適用条件が書き漏れていると、誤った当てはめが起きる。
6. **人間による確認の負担：** 重要な記憶や手順の記憶では、人間による確認が多くなる。確認が溜まると、記憶の効果が出るのが遅れる。
7. **原文との照合：** 初回報告書の全文とは、直接照合していない。
8. **索引の区画の粒度（B2-R01）：** v1 では、記憶ごとの細かい共有ができない。共有するには写しを作る必要があり、写しの数と、削除の範囲が増える。
9. **機密を含む記憶の検索（B2-R01、R02）：** confidential と personal の記憶は、FTS の索引に入れず、手元で照合する。そのため、件数が多いと遅くなり、上限を超えると取りこぼしが起きる。
10. **物理的な消去（B2-R02、R03）：** 媒体レベルでの消去（SSD、ファイルシステム、クラウドのスナップショット）は保証できない。KEK と鍵の写しをすべて管理しきれることが前提になる。
11. **削除台帳への依存（B2-R03）：** 削除台帳とその目印を両方とも失うと、復元したデータをいつまでも使えなくなる。安全側に倒すため、使えなくなることは受け入れる。
12. **送信済みの情報（B2-R04）：** Permit を出した後や、実行中のモデル呼び出しで、すでに外部に送った情報は取り消せない。
13. **系譜の多めの見積もり（B2-R07）：** 成果物の単位で追うので、影響の範囲を多めに見積もる（消しすぎや、人間の確認の増加）。モデルの内部で何に影響したかは追えない。
14. **原因の検証の範囲（B2-R06）：** 反実仮想テストができない原因は、承認済みの仮説のままになる。

## 13. 未確認事項（外部調査は行っていない）

- SQLite の WAL で、ATTACH した複数の DB にまたがるトランザクションが、全体として原子的にならないこと（そのため、投影の方式を選んだ）。
- `secure_delete` と FTS5 を最適化したときに、削除した内容がファイルから完全に消えるか。
- 外部のプロバイダーが、送られたデータをどれだけの期間、どう保管するか。削除を依頼できるか。
- 暫定値（再検証の周期、検索の時間の目標、各種の上限）の妥当性。
- FTS5 の MATCH の処理時間が、索引の大きさによってどう変わるか（区画を分ける方式の、サイドチャネルとしての評価）。
- `temp_store=MEMORY` と WAL の TRUNCATE で、一時ファイルと削除した内容の残りを、どこまで防げるか。
