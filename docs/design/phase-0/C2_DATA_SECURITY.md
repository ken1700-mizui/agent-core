## 0. 基本方針

1. **保存と送信は、別々に認可する。** 保存してよいことと、外に送ってよいことは、別の判断である。
2. **認証情報は、どこにも保存しない。** Gateway の認証情報の保管庫だけに置く（C1 の S11）。
3. **分類が分からなければ、厳しい側に倒す。**
4. **機密の検出は、補助の防御にすぎない。** 主な防御は、構造的な仕組みである。具体的には、分類の継承、送信先の方針、データを最小限にすること、暗号化。検出だけで安全を保証したとは言わない。
5. **独自の暗号方式は作らない。** 実績のある暗号ライブラリの、高水準な API だけを使う。
6. **管理下にないデータの削除は、保証しない。**

## 1. アーキテクチャ

```
                  ┌────────────── P1 Orchestrator（TCB）──────────────┐
 書き込みの要求 ──▶ │ Data Classifier → Storage Authorization Gate（SAG）│──▶ journal.db / blobs / memory / logs
                  │ Key Service（P1 の中のライブラリ）                  │     （書き込むのは P1 だけ）
                  │ Deletion Coordinator・Backup Manager・Audit Writer  │
                  └───────────┬────────────────────────────────────────┘
                              │ 消費の確認、失効の通知（同期）
 送信の要求 ──▶ PDP（EgressCheck）──▶ P3 Gateway（Final Egress Inspector、認証情報の保管庫）──▶ 外部

 独立した保管場所：削除台帳・anchor・監査のチェックポイント（7.4、9.3）
 評価の側（開発の側とは別のホスト、または別の VM）：Eval Controller・Test Vault・Untrusted Execution Sandbox・Verifier・Signer・Aggregator（10章）
```

| 部品 | 役割 |
|---|---|
| Data Classifier | データに分類のラベルを付け、派生したデータにもラベルを引き継がせる（3章） |
| Storage Authorization Gate（SAG） | 永続化するすべての書き込みの入口。保存の認可と、保存する前の検査を行う（4章） |
| EgressCheck | 送信の認可。PDP の中にある（5章） |
| Final Egress Inspector | 最終的なリクエストを検査する。Gateway の中にある（5章） |
| Key Service | 鍵の生成、ラップ（鍵を別の鍵で暗号化すること）、導出、破棄（6章） |
| Deletion Coordinator | 削除の手順、系譜をたどること、隔離（7・8章） |
| Audit Writer | 監査ログ（9章） |

## 2. 信頼境界（データの観点）

| 境界 | 越えるデータ | 認可 |
|---|---|---|
| 処理 → 永続ストレージ | Journal、blob、記憶、ログ、キャッシュ、バックアップ | 保存の認可（SAG） |
| Agent Core → 外部の送信先 | 最終的なリクエスト | 送信の認可（EgressCheck と Final Egress Inspector） |
| 外部 → Agent Core | 応答 | ラベルを付け、D1/D2 として扱い、保存の認可を通す |
| 管理下 → 管理の外（書き出し、push、外部ツール） | 成果物 | 送信の認可と同じ扱い。系譜に `exported` と記録する（B2 の7.9） |
| 開発の側 ↔ 評価の側 | 開発 → 評価：評価する版（コミット）、構成。評価 → 開発：制限した結果だけ | 10章・11章 |
| P1 ↔ P2 ↔ P3 | Permit、消費の確認、封をしたリクエスト | C1 の2.1。OS のレベルの強制は 5.5 |

## 3. データの分類（C11）

### 3.1 分類

| 分類 | 例 | 保存 | 外部への送信 |
|---|---|---|---|
| `public` | 公開されている文書 | 可 | 方針に従う |
| `internal` | プロジェクトのコード、設定（機密の指定がないもの） | 可（暗号化を推奨） | 送信先の方針が確認済みであることが必要 |
| `confidential` | 機密に指定したコード、内部の資料 | 暗号化が必須 | 確認済みで、かつ機密を許す送信先だけ |
| `personal` | ユーザーの記憶、個人に関する情報 | 暗号化と系譜の記録が必須。削除に応じられる保存先だけ | 確認済みで、かつ個人情報を許す送信先だけ。オーナーの方針による |
| `credential` | API キー、トークン、パスワード、秘密鍵 | **Gateway の認証情報の保管庫だけ**。それ以外はすべて拒否 | 注入の経路でだけ（C1 の9.3） |

### 3.2 規則

- **複数の分類に当たる場合：** データは、ラベルの**集合**を持つ。扱い（保存、送信、表示、保管の期間、削除）は、それぞれの観点で最も厳しいラベルに従う。
  - たとえば `confidential` と `personal` の両方に当たるデータでは、両方の制約を満たさなければならない。
- **分類が分からない場合：** `confidential` として扱い、`unclassified` の印を付ける。クラウドへ送る前には、人間の確認が必要。
- **派生したデータへの継承：** 派生したデータのラベルは、元のデータすべてのラベルの和集合になる（B1 の `derived_from_chain`）。
  - モデルの応答は、その文脈に含めたラベルの和集合を引き継ぐ。モデルが文脈をそのまま出力しうるため。
- **格下げ：** ラベルを外せるのは、権限を持つ人間が理由を付けて記録した場合だけ。モデルや自動の処理では外せない。
- **ラベルの初期値（入ってきた経路による）：**
  - User Memory：`personal`
  - リポジトリのファイル：`internal`。プロジェクトの方針で `confidential` にしたパスは `confidential`
  - 外部の公開情報：`public`（ただし信頼はしない）
  - ツールの出力：入力のラベルと、読んだファイルのラベルの和集合
  - 環境変数と認証情報のファイル：`credential`
- **`credential` を見つけた場合：** どの書き込みや送信の中で見つかっても、その書き込みや送信を止める。止めたことを監査に記録する（本文は残さない）。

## 4. 保存の認可（C11、B1-P01、B2-R02、CP-2）

### 4.1 Storage Authorization Gate（SAG）

**入口：** `store(target, data, labels, purpose, lineage)`。永続化する書き込みは、すべてここを通る。書き込むのは P1 だけ（設計A の A11）。

**検査の順序**

1. **ラベルの確認：** データにラベルが付いているか。なければ 3.2 の規則で付ける。
2. **認証情報の検査：** 次を組み合わせて確かめる。
   - 認証情報のパターン
   - 登録済みの認証情報のハッシュとの照合
   - 目印の値（canary）
   - エントロピー（文字のランダムさ）による検査
   - 見つかれば拒否する。元の場所で伏せ字にすることを求め、監査に記録する。
3. **保存先とラベルの照合：** 4.2 の表と照らし合わせる。
4. **暗号化と系譜：** `confidential` と `personal` のデータは、暗号化した blob と系譜の記録がそろっていること。
5. **大きさと保管の期間：** それぞれ上限の範囲内であること。
6. **監査の記録：** 本文を含めずに記録する（9章）。

**拒否した場合**

- 監査には、`action_hash`、理由の区分、ラベル、大きさ、鍵付きのハッシュだけを残す。**本文は残さない**（B1-P01）。

### 4.2 保存先ごとの規則

| 保存先 | 保存してよいもの | 条件 |
|---|---|---|
| Journal | ID、ハッシュ（鍵付き）、参照、ラベル、状態 | **本文は、どの分類でも入れない**（B2 の M8 を Journal 全体に広げたもの） |
| Context IR、変換済みの文脈、リクエストの記録、モデルの応答、ツールの出力 | 暗号化した blob（Run ごとの鍵。6章） | `personal` を含む場合は、系譜の記録が必須。`credential` は拒否する |
| 記憶 | B2 の7.6 のとおり | 記憶ごとの鍵 |
| 成果物 | 暗号化した blob、またはワークスペース | ラベルを引き継ぐ。書き出すときは送信と同じ扱い |
| ログとトレース | ID、大きさ、時間、ラベル、理由の区分 | **本文と引数の値は入れない** |
| キャッシュ | `public` と `internal` は、暗号化した永続のキャッシュでも可 | `confidential` と `personal` は、プロセスのメモリの中だけ |
| バックアップ | 上の保存先の、暗号化した写し | 世代を管理する（7.5） |

### 4.3 リクエストの記録を保存する順序（CP-2 を確定する案）

```
組み立て → リクエストの記録を保存してよいかの認可（SAG）→ 送信の認可（EgressCheck）
→ リクエストの記録を暗号化して保存 → Permit の消費 → 最終の検査 → 送信
```

- 保存の認可で拒否された場合は、送信もしない（安全側に倒す）。
  - 理由：記録のない送信は、設計A の照合と Replay ができないため。
  - 「記録を残さない送信」は、初期の段階では認めない。

### 4.4 SAG で強制できる範囲（C2-R02）

**X2 の範囲をはっきりさせる：** SAG を必ず通るのは、**信頼するプロセス（P1〜P3）が、正式な保存領域に書き込むとき**である。信頼しないコードが直接書き込む領域は、SAG では止められない。そこで、そうした領域は「隔離した一時領域」として扱い、正式な保存領域に移す前に SAG を通す。

| 対象 | SAG で強制できるか | 扱い |
|---|---|---|
| Sandbox の中の書き込み | **できない**（信頼しないコードが直接書く） | 隔離した一時領域として扱う（大きさに上限のある tmpfs、または loop。C1 の8.6）。Run が終わったら破棄する。正式な領域へ移せるのは、取り出しのときに SAG を通ったものだけ |
| Docker のログ | 設定で止める | コンテナは `--log-driver none` にする。標準出力は、Broker が上限を付けて受け取り、SAG を通す |
| 一時ファイル | 方針で止める | P1〜P3 では `temp_store=MEMORY` にし、プロセスごとに権限を絞った一時ディレクトリを使う。起動するときに空にする。本文を一時ファイルに書かない、というコードの決まりを設け、試験で確かめる |
| 作業フォルダ（ワークスペースの写し） | 写しは隔離した一時領域。ホストへの反映は強制できる | ホストのワークスペースへの反映は、取り出しの検査（C1 の8.5）と SAG を通す |
| クラッシュダンプ | 設定で止める（一部だけ） | P1〜P3 とコンテナで、コアダンプを無効にする（`ulimit -c 0`、ダンプできない設定）。OS のクラッシュ報告の仕組みは、Agent Core では止めきれない（残存リスク） |
| スワップ | **強制できない** | 暗号化したスワップか、スワップなしを推奨する。起動するときの自己診断で警告する。ホストの設定なので、保証の範囲の外 |
| SQLite の WAL | 間接的に強制できる | DB に入れる内容そのものを SAG で決めるので、WAL も同じ内容しか持たない。削除した後は、チェックポイントで切り詰める（B2 の7.6） |
| OS のログ（journald、syslog など） | 方針で止める（一部だけ） | P1〜P3 は、本文を標準出力やシステムのログに出さない。カーネルや OS のログは、保証の範囲の外 |
| 成果物の取り出し | **できる** | ファイルごとに、ラベルの付与、認証情報の検査、SAG を行ってから反映する |
| バックアップ | **できる**（Agent Core が作るもの） | Backup Manager は、SAG を通った保存領域だけを、暗号化して写す。OS やクラウドが取るディスクのスナップショットは、保証の範囲の外 |

### 4.5 監査の再帰と、検査が漏えいの経路にならないこと（C2-R02）

**監査の書き込みを再帰させない**

- Audit Writer は、SAG を**呼び出さない**、専用の追記の経路を持つ。
- 監査の記録の形（9.2）は、決まった項目だけを許し、本文を入れる項目を持たない。そのため、本文の検査は要らない。検査するのは、形が正しいかどうかだけ。
- SAG の判定は、Audit Writer に記録する。Audit Writer の側の失敗は、SAG に戻さない。Audit Writer が書き込めないときは、操作そのものを止める（監査なしでは進めない）。

**検査の処理が、新しい漏えいの経路にならないようにする**

- 機密の検査は、P1 と P3 のメモリの中だけで行う。外部には何も送らない。
- 見つけた値そのものは、保存も、ログへの出力もしない。出力するのは、規則の ID、位置の範囲、鍵付きのフィンガープリントだけ。
- 照合のために登録する認証情報は、平文ではなく、検査用の鍵で計算した HMAC として保存する（6.2）。
- 検査のエラーメッセージにも、入力の一部を含めない。

## 5. 外部送信の認可（C12）

### 5.1 送信先の情報（C1 の9.1 を広げたもの）

`destination_id → {provider, region, deployment: local|cloud, data_policy: {status: verified|unverified, verified_at, evidence_ref, reviewer}, retention, training_use: {status, opt_out}, allowed_labels[], allowed_headers[], ...}`

- **`data_policy` が `unverified` の送信先には、`public` だけを送れる。** `internal` 以上の分類は送らない。
- 確認済みにできるのは、オーナーだけ。確認した根拠への参照を残す。プロバイダーの方針は変わりうるので、確認には期限を設ける。
- **Phase 3B で Anthropic の API に送る前に、** オーナーが次を確かめ、確認済みとして登録する必要がある。
  - データの扱いの方針
  - 保管の期間
  - 学習への利用
  - 地域
  - これらは、この設計では**確認していない**（16章）。
- **ローカルのモデル：** 外部へ送ることにはならないが、保存の規則は同じく当てはまる。ローカルのモデルを動かす実行環境は、信頼しないコードとして Sandbox で動かす（C1）。

### 5.2 送信の認可の判定（EgressCheck）

送ってよいのは、次をすべて満たすときだけ。

1. 送信先が登録されていて、`data_policy` がまだ有効である。
2. 送る内容のラベルが、すべて `allowed_labels` に含まれている。
3. 記憶の削除の状態に当たらない（拒否リスト）。`access_epoch` が今のものである。
4. 承認がある場合は、承認が `action_hash` と `request_hash` に一致している。
5. 内容を組み立てた結果が、構造として許される（ラベルの付いた項目だけで組み立てている）。

### 5.3 最終的なリクエストの検査（Final Egress Inspector）

- Gateway が、**封をしたリクエストそのもの**を検査する。対象は、URL、クエリ、ヘッダー（注入する認証情報は除く）、本文。
- 検査の内容は 4.1 の 2 と同じで、さらに既知の機密項目の鍵付きのフィンガープリント（内容から作った識別値）と照合する。
- 主な防御は、構造（ラベルと送信先）である。検査は、それを補うものとして扱う。

### 5.4 消費の後の失効と、送信開始の順序（C1-P02、C2-R06）

**receipt（消費の確認）の状態遷移**

```
ISSUED（P1 の消費の処理で作る。permit_id、consumer、pep_boot_id、revocation_gen、期限付き）
  → CLAIMED（PEP が送信の直前に、原子的に自分のものにする）
  → SEND_STARTED（最初のバイトを書いた）
  → COMPLETED | FAILED | UNKNOWN_OUTCOME
ISSUED または CLAIMED（送信を始める前）→ REVOKED（失効）| EXPIRED（期限切れ）
```

- receipt に含めるもの：`pep_boot_id`（PEP のプロセスが起動するたびに変わる値）と、`revocation_gen`（失効の世代番号）。

**失効の、2つの時点を分ける**

| 時点 | 意味 |
|---|---|
| `REVOCATION_RECORDED` | P1 が、失効をトランザクションで記録した。`access_epoch` を増やす、拒否リストに加える、承認を取り消す、のどれか。`revocation_gen` を1つ増やし、まだ送られていない receipt を `REVOKED` にする |
| `REVOCATION_ENFORCED` | Gateway と Broker の**すべて**が、新しい `revocation_gen` を当てはめ終えたと ack を返した |

- `RECORDED` から `ENFORCED` までの間、P1 は、対象の範囲に新しい Permit も receipt も出さない。

**PEP の中での排他（失効と送信開始の順序付け）**

- PEP は、送信開始の判定に、読み書きのロックを使う。
- **送信の側（読みのロック）：** ロックを持っている間に、次をすべて確かめる。
  1. receipt が `ISSUED` である。
  2. receipt の `revocation_gen` が、PEP の現在の値と同じ。
  3. `pep_boot_id` が自分のもの。
  4. 承認の `expires_at` が「今の時刻＋送信にかかる時間の余裕」より後である。
  5. 停止の状態が `RUNNING`（C1 の11.4）。
  - すべて満たせば、receipt を `CLAIMED` から `SEND_STARTED` にしてからロックを放し、バイト列を書く。
- **失効の側（書きのロック）：** 失効の通知を受け取ったら、次を行う。
  1. 書きのロックを取る。
  2. `revocation_gen` を新しい値に更新する。
  3. `ISSUED` と `CLAIMED` の receipt を、すべて `REVOKED` にする。
  4. ロックを放す。
  5. P1 に ack を返す。
- これで、どの送信も「失効の前に始まった」か「失効によって止められた」かの、どちらかになる。
- **通知を受け取っても、すでに `SEND_STARTED` になった送信は止まらない。** 接続を切ることはできるが、送ったデータは取り消せない。そうした送信は「失効より前の送信」として、照合の対象にする。

**ack が届かない場合と、IPC が切れた場合**

- P1 は、決めた時間（暫定で 2 秒）のうちに ack が届かなければ、その PEP を「不健全」とする。そのうえで、対象の範囲を停止にする（C1 の11.4）。強制が確かめられないので、範囲ごと止める。
- PEP は、P1 とのプロセス間通信が切れたら、新しい送信を始めない。持っている receipt は、すべて自分の側で `REVOKED` にする。

**Gateway や Broker が再起動した場合**

- `pep_boot_id` が変わるので、再起動する前の receipt は、すべて無効になる。
- 再起動した PEP は、P1 に登録し直して、今の `revocation_gen` を受け取るまで、送信しない。
- 再起動したときに送信の途中だったものは、`UNKNOWN_OUTCOME` として扱う（設計A）。

**使い回しの禁止**

- receipt は、1回の接続の試みにだけ使える。PEP は、`SEND_STARTED` になった receipt を、二度と受け付けない。
- P1 は、送信の開始と終了の通知を受けて、記録する。通知が届かないまま PEP が止まった場合は、`UNKNOWN_OUTCOME` にする。

**限界**

- すでに送った内容は、取り消せない。

### 5.5 OS のレベルでの強制（C1-P04）

| 対象 | Phase 1〜2 | Phase 3A より前に必須にする条件（実API に接続する前の隔離の条件） |
|---|---|---|
| 外部ネットワーク | 認証情報は存在しない（D1）。P1 と P2 にネットワークがないことは、論理的な分離だけでもよい | P1 と P2 を、外へ出る経路のないネットワークの名前空間で動かす。または、OS ユーザーごとのファイアウォールで、外への通信を P3 にだけ許す |
| プロセス間通信 | ソケットのディレクトリの権限を、`0700` 相当にする | ソケットのファイルの権限と、`SO_PEERCRED` による相手の確認。許可した UID 以外は拒否する |
| Docker のソケット | rootful の Docker のソケットを持つプロセスは、**実質的にホストの root と同じ**。このことを前提にして扱う | **rootless の Docker（専用のユーザー）を必須にする。** rootful しか使えない場合は、認証情報を持つ P3 を、別のホストまたは別の VM に置く。そのどちらもできなければ、実API には接続しない |
| 認証情報へのアクセス | 認証情報は存在しない | 認証情報の保管庫を読めるのは、P3 の OS ユーザーだけ。P2 の権限の強さ（rootful の場合）によっては、それでも守れない。そのため、上の条件が前提になる |

- 実現できるかどうか（rootless の Docker で、必要な設定がすべて動くか）は、未確認である。

### 5.6 送信内容の正規化（C1-P05）

**組み立ての方式：Gateway が自分で組み立てる**

- Gateway は、**CanonicalRequest から、HTTP のリクエストを自分で組み立てる**。受け取ったバイト列をそのまま送ることはしない。意味が一致することを、組み立ての方式で保証するため。
- ハッシュは CanonicalRequest に対して計算する。組み立ては決定的に行う。

**HTTP のクライアントについて**

- 自動の処理はすべて無効にした、最小限の HTTP/1.1 のクライアントを使う。無効にする処理は次のとおり。
  - 自動のリダイレクト
  - Cookie
  - プロキシ
  - 自動の展開と、展開のためのヘッダーの付加
  - 既定のヘッダー
  - 接続の使い回しによるヘッダーの付加

**拒否するもの**

- 名前が重複したヘッダー（初期の段階）
- 改行の文字（CR、LF）
- 古い形式の、折り返したヘッダー
- 制御文字
- 認可していない Host のヘッダー

**パスの扱い**

- パスはバイト列のまま扱う。
- `.` や `..` の区切りと、あいまいなエンコーディング（`%2e`、`%2f` など）は、送信先が許可していなければ拒否する。

**ヘッダーと本文の扱い**

- 認証のヘッダーは、決めた名前でだけ注入する。同じ名前のヘッダーが、すでにあれば拒否する。
- `Content-Length` は Gateway が計算する。リクエストを分割して送る方式（chunked）は使わない。

**HTTP/2**

- 正規化のしかたを確かめるまで、使わない。プロバイダーが HTTP/2 を必須にしているかどうかは、未確認。

**ハッシュの鍵**

- `request_hash` の HMAC の鍵は 6章で扱う。

## 6. 暗号化と鍵の管理（C13）

### 6.1 アルゴリズムとライブラリ（方針。具体的な選定は未確認）

| 用途 | 方式 |
|---|---|
| 認証付き暗号化（AEAD） | XChaCha20-Poly1305（ランダムな nonce を安全に使えるため）、または AES-256-GCM（nonce を重複させない管理が必要） |
| MAC | HMAC-SHA-256 |
| 鍵の導出 | HKDF-SHA-256（用途のラベルを必ず付ける） |
| 署名（検証する側が鍵を偽造できないようにするため） | Ed25519 |
| ハッシュ | SHA-256 |

- **ライブラリ：** 実績のある、広く使われている暗号ライブラリの、高水準な API を使う（候補は libsodium の系統、OpenSSL を使うもの）。どれを使うか、その版、使える関数は、**確認していない**。依存関係を入れることになるので、オーナーの承認が必要（AGENTS.md）。
- **独自の方式は作らない：** 低水準の部品を、自分で組み合わせることもしない。

### 6.2 鍵の用途と、置き場所

| 鍵 | 種類・範囲 | 持つプロセス | 置き場所 | 導出のラベル、または生成の方法 |
|---|---|---|---|---|
| 記憶の元の鍵 | 記憶ごと、ランダム 256 ビット | P1 | `keys/<tenant>.db`（KEK でラップ） | 生成する |
| 記憶の本文の暗号化の鍵 | 記憶ごと | P1 | 保存しない（毎回導出する） | HKDF(元の鍵, `"agent-core/v1/memory/enc"`) |
| 記憶ごとの MAC の鍵 | 記憶ごと | P1 | 保存しない | HKDF(元の鍵, `"agent-core/v1/memory/mac"`) |
| テナントの KEK | テナントごと | P1 | P1 の OS ユーザーだけが読めるファイル（Phase 1〜2）。Phase 3A より前に、OS の鍵の保管の仕組みを使うかを決める | 生成する |
| Context の HMAC の鍵 | テナントごと | P1 | `keys/<tenant>.db`（KEK でラップ） | 生成する |
| rendering_hash の HMAC の鍵 | テナントごと | P1 | `keys/<tenant>.db`（KEK でラップ） | 生成する |
| request_hash の HMAC の鍵 | テナントごと | P1、P3（検証のため） | 同じ場所。P3 には、この鍵だけの写しを渡す | 生成する（rendering_hash の鍵とは別の鍵） |
| Permit の MAC の鍵 | 全体 | **P1 だけ** | P1 のファイル | 生成する。PEP は MAC を検証しない。MAC の検証は、P1 の消費の処理（C1 の7.5）の中で行う（6.4、CP-9） |
| 削除台帳の署名の鍵 | 全体（Ed25519） | 秘密鍵は P1、公開鍵は復元する側 | 秘密鍵は P1、公開鍵はオーナーの控え | 生成する |
| 停止の状態の署名の鍵 | 全体（Ed25519） | 秘密鍵は P1、公開鍵は P2 と P3 | 同じ方式 | 生成する |
| 監査のチェックポイントの署名の鍵 | 全体（Ed25519） | 秘密鍵は P1 | 同じ方式 | 生成する |
| 検索のキャッシュの HMAC の鍵 | テナントごと | P1 | メモリの中だけ。起動のたびに作り直してよい | 生成する |
| ブラインドインデックスの鍵 | テナントごと | P1 | `keys/<tenant>.db`（KEK でラップ） | 生成する |
| Run の KEK | Run ごと | P1 | `keys/<tenant>.db`（テナントの KEK でラップ） | 生成する。blob ごとの鍵をラップするためだけに使う |
| blob ごとの鍵（DEK） | blob ごと | P1 | Run の KEK でラップして保存する | 生成する。削除のときに、対象の blob の鍵だけを破棄できる（8.2） |
| 抑止の一覧の鍵 | テナントごと | P1 | `keys/<tenant>.db`（KEK でラップ） | 生成する（8.3） |
| 機密の検査の照合用の鍵 | 全体 | P1、P3 | 持つプロセスの OS ユーザーだけが読めるファイル | 生成する（4.5） |
| 評価の結果の署名の鍵（Ed25519） | 評価の側 | 評価の側の Signer だけ（10章） | 評価の側。開発の側には置かない | 生成する |
| バックアップの鍵 | 世代ごと | Backup Manager（P1） | バックアップ用の KEK でラップ。バックアップ用の KEK はオーナーが別に保管する | 生成する |
| 外部への認証情報 | 送信先ごと | **P3 だけ** | 認証情報の保管庫（5.5） | オーナーが登録する |

**鍵の版**

- `key_id = (用途, 範囲, 版)`。データの側に `key_id` を記録する。

**平文の鍵を、無制限に保存しない**

- 平文の鍵をファイルに置くのは、KEK と、少数の全体の鍵だけ。それぞれ、持つプロセスの OS ユーザーだけが読める。
- それ以外の鍵は、KEK でラップして保存する。

### 6.3 鍵の更新、失効、破棄、バックアップ、障害からの復旧

| 操作 | 方法 |
|---|---|
| 更新（定期的な切り替え） | 新しい版の鍵で、新しく書き込む。古い版は、そのデータを再暗号化するか期限切れになるまで、復号と検証のためにだけ残す。KEK を切り替えるときは、データの鍵をラップし直す |
| 失効（漏えいの疑い） | `COMPROMISED` の印を付けて、使うのをやめる。<br>- 暗号化の鍵の場合：データを再暗号化する。<br>- MAC や署名の鍵の場合：鍵を切り替えたうえで、台帳、anchor、チェックポイントの署名をやり直す。<br>失効したことを監査に記録する |
| 破棄 | ラップした鍵の行を削除し（`secure_delete`）、鍵の DB のバックアップが期限切れになるのを待つ（`R_key`）。<br>KEK を長く保管していても、記憶ごとの鍵が残っていなければ、記憶は戻せない。記憶ごとの鍵は、保管の期間が短い鍵の DB にだけあるため |
| バックアップ | 鍵の DB は、データとは別にバックアップし、保管の期間を短くする。KEK とバックアップ用の KEK は、オーナーが別の場所に保管する |
| 障害からの復旧 | 鍵をなくしたデータは、戻せないものとして扱う（安全側に倒す）。データは `unavailable` にし、作り直さない |

**限界**

- 鍵の種類を分けても、それだけで安全にはならない。P1 が乗っ取られると、P1 が持つすべての鍵が漏れる。

### 6.4 鍵の用途の分離と、鍵の信頼の確かめ方（C2-R05）

**用途の分離**

- HKDF の `info`（導出のラベル）は、`"agent-core/<版>/<用途>/<テナント>/<範囲>"` の形にし、用途ごとに異なる文字列にする。
- 同じ鍵を、別の用途（暗号化と MAC、rendering と request など）に使わない。

**鍵の信頼を確かめる方法**

- 署名の鍵（停止の状態、削除台帳、監査、評価の結果）を作ったときは、その公開鍵のフィンガープリントを、次の3か所に記録する。
  - Journal の `KeyCreated` のイベント
  - 外部の証人（7.3）
  - オーナーが持つ公開鍵の一覧
- 検証する側は、公開鍵を固定して持つ。
- 鍵を替えるときは、次のどちらかが必要。
  - 通常の更新：古い鍵で署名した `KeyRotated`
  - 漏えいした場合：オーナーが承認した `KeyCompromised` と `KeyReplaced`

**Permit の MAC と、C1 の PEP の検証との整合**

- C1 の7.4 の「1. MAC が正しい」は、PEP で検証するのではなく、P1 の消費のトランザクション（C1 の7.5）の中で検証する、と改める（CP-9）。
- PEP が受け取った Permit を先に確かめたい場合は、Permit ID、期限、`action_hash` の形式など、MAC を使わない項目だけを確かめる。最終的な判断は P1 の消費で行う。

### 6.5 通常の更新と、漏えいしたときの失効の違い（C2-R05）

| | 通常の更新 | 漏えいしたときの失効 |
|---|---|---|
| 古い鍵で作った記録 | 引き続き信頼する（古い鍵で検証できる） | **漏えいしたかもしれない期間**に作った記録を、`SUSPECT`（疑わしい）として隔離する。期間の始まりが分からなければ、その鍵を作った時点から |
| 署名をやり直すこと | 不要 | **新しい鍵で署名し直しても、信頼は回復しない**。独立した根拠で検証し直したものだけを、信頼を戻す |
| 独立した根拠の例 | — | 漏えいの期間より前に、外部の証人に写した、台帳・監査のチェックポイント・anchor。その期間より前のバックアップ。外部のサービスの側の記録（請求の記録など） |
| 検証し直せなかった記録 | — | `SUSPECT` のままにする。安全な側に倒して扱う。<br>- 削除の記録：削除したものとして扱う。<br>- 権限、承認、評価の結果：無効として扱う |
| 実行中のもの | — | Permit の MAC の鍵が漏えいした場合は、出ているすべての Permit と receipt を無効にする。漏えいの期間に実行した操作を、照合の対象にする |

### 6.6 AEAD の nonce と AAD、鍵の更新の途中の障害（C2-R05）

**nonce の管理**

- XChaCha20-Poly1305 を使う場合は、暗号化するたびに、192 ビットのランダムな nonce を使う。
- AES-256-GCM を使う場合は、96 ビットのランダムな nonce を使い、1つの鍵で暗号化する回数に上限を設ける（上限の値は、選ぶライブラリの資料で確かめる。未確認）。上限に近づいたら、鍵を替える。
  - 数を数えて nonce を作る方式は、障害の後に同じ値を繰り返す危険があるので、使わない。
- 同じ鍵と nonce の組を、二度と使わない。blob ごとの鍵は、1つの内容（の1つの版）だけを暗号化するので、重なる危険はさらに小さくなる。

**AAD（暗号化しないが、改ざんを検知できるように結び付ける情報）**

- AAD に入れるもの：`{tenant_id, purpose, object_id（memory_id／run_id／blob_id）, version, key_id, schema_version, labels のハッシュ}`。
- 復号するときは、期待する値で AAD を組み立てる。暗号文を別のテナント、別のデータ、別の版、別の用途に差し替えても、復号に失敗する。

**鍵の更新の途中で障害が起きた場合**

```
① 新しい鍵を作る（状態は PENDING）→ Journal に KeyCreated を記録する
② データを順に、新しい鍵でラップし直すか、暗号化し直す
   - データごとに key_id を更新する。冪等にする
③ Journal に KeyActivated を記録する（新しく書き込むときは、新しい鍵を使う）
④ すべて移し終えたら、KeyRetired を記録する
⑤ 保管の期間が過ぎたら、古い鍵を破棄する
```

- データごとに `key_id` を持っているので、古い鍵と新しい鍵のデータが混ざっていても、読める。
- 障害の後は、古い `key_id` のデータを探して、②から続ける。

## 7. 削除の受付と、削除台帳の整合性（C14、B2-P01、C2-R03、C2-R04）

### 7.1 削除要求の状態と、利用者への応答（C2-R03）

| 状態 | 起きたこと | 取得 | 利用者への応答 |
|---|---|---|---|
| `RECEIVED`（受信） | 要求を受け取った（まだ永続化していない） | 止めていない | まだ返さない |
| `LOCALLY_ACCEPTED`（ローカルでの受付） | D1：P1 の1つのトランザクションで、`MemoryDeletionRequested` の記録、拒否リストへの追加、`access_epoch` の増加を行った | **ここから止める** | 「受け付けました。確定の処理中です」。**ディスクを失うと、この要求は消えうる**。利用者の側（またはその代理の仕組み）は、`deletion_id` で冪等に要求をし直せるようにしておく |
| `LEDGER_PERSISTED`（独立した台帳への永続化） | D2：独立した台帳に追記し、fsync した | 止めたまま | （内部の状態） |
| `DURABLY_ACCEPTED`（永続的な受付の確定） | D3：anchor を書き換え、**外部の証人（7.3）が受け取ったことを確かめた** | 止めたまま | 「受付が確定しました」。ここで初めて、障害の後も要求が残ると言える |
| `PURGING` → `COMPLETED_LIVE` → `FULLY_COMPLETED`（削除の処理と完了） | 8章 | 止めたまま | 進み具合と、`DeletionReport`（8.4） |

- **D1 の記録だけで、障害の後も削除の要求が残るとは保証しない。** 保証するのは `DURABLY_ACCEPTED` から。
- **確定したかどうか分からない場合は、対象のデータを使えないようにする。** 例：Journal を失って復元したが、その後の要求が台帳や証人にあるかどうか確かめられない。
  - 対象が分からなければ、そのテナントの記憶全体を使えないようにする（7.2）。

### 7.2 障害が起きた場合の復旧（起動するたび、および復元したときに照合する）

| 状況 | 判定 | 動作 |
|---|---|---|
| D1 より前に障害 | 要求は存在しない | 応答を返していないので、利用者がもう一度要求する |
| D1 の後、D2 の前に、プロセスが止まった（ディスクは無事） | 正常な途中の状態 | Journal にあって台帳にない削除を、台帳に追記する（自動でよい） |
| D1 の後、D2 の前に、**ディスクを失った** | 要求は失われうる | 利用者には `LOCALLY_ACCEPTED` までしか返していない。そのため、利用者の側から、もう一度要求してもらう。<br>復元した後、そのテナントの記憶は、照合期間（暫定値。E で決める）が終わり、オーナーが確かめるまで、使えないようにする |
| D2 の後、D3 の前 | 正常な途中の状態（7.3 の自動修復の条件を満たす場合） | anchor を台帳の先頭まで進め、証人に送る |
| 証人が受け取ったかどうか分からない | 確定していない | 証人に送り直す（冪等）。受け取ったと確かめられるまで、`DURABLY_ACCEPTED` とは言わない |
| 台帳が Journal より先に進んでいる | Journal が古い（復元など） | 台帳の削除を正とする。足りない削除を Journal に取り込む（削除の方向は安全な側）。終わるまで、記憶へのアクセスを止める |
| 7.3 の「不整合として止める条件」に当たる | 巻き戻り、または改ざんの疑い | 記憶へのアクセスを止める。自動では直さず、オーナーに確認する |
| 台帳、anchor、証人のどれかが読めない、または署名が正しくない | 最新かどうか確かめられない | 記憶へのアクセスを止める（隔離） |

### 7.3 最新であることの証明と、巻き戻りの検知（C2-R04）

**署名が正しい台帳が、最新の台帳であるとは限らない。** 古い台帳にも、正しい署名が付いているからである。最新であることを示せるのは、信頼できる、単調に増える外部の記録と照らし合わせた場合だけ。

**前提：外部の証人（witness）**

- 削除の記録が確定するたびに（D3）、`{ledger_seq, head_hash, 署名}` を、外部の追記専用の保存先に書く。
- 外部の保存先の条件は次のとおり。
  - Agent Core のホストとは別の場所にある。
  - 書き込みに使う認証情報が、Agent Core の台帳とは別。
  - 過去の記録を書き換えたり、消したりできない設定にする（追記専用、またはそれと同等）。
  - `ledger_seq` が単調に増えることを、保存先の側でも確かめられる。
  - 保管の期間は `R_ledger` 以上。
  - 複製されている、または十分に耐久性がある。
- 具体的にどのサービスを使うかは、未確認（16章）。
- オーナーが定期的に取る控えは、**補助**にとどめる。すべての削除の要求について、最新であることを保証するものではない。

**正常な途中の状態と、不正な巻き戻りの区別**

| 区分 | 条件 | 動作 |
|---|---|---|
| **自動で修復してよい**（前へ進めるだけ） | 次をすべて満たす：<br>1. 台帳、anchor、証人の、共通する範囲の `seq` でのハッシュが一致する。<br>2. `anchor.seq ≤ ledger.seq` である。<br>3. `witness.seq ≤ ledger.seq` である。<br>4. 台帳で anchor より先に進んでいる記録が、Journal の削除の記録と対応している（または、Journal が古いことが分かっている）。 | 台帳に記録を足すか、anchor を台帳の先頭まで進めて、証人に送る |
| **不整合として止める** | 次のどれか：<br>1. `ledger.seq < witness.seq` である（台帳が証人より古い）。<br>2. `anchor.seq < witness.seq` であり、かつ台帳もそこまで進んでいない。<br>3. `anchor.seq > ledger.seq` である。<br>4. 共通する `seq` でハッシュが一致しない。<br>5. `seq` が飛んでいる、または重複している。 | 記憶へのアクセスを止め、自動では直さない。オーナーに確認する |
| **最新であることを確かめられない** | 証人に届かない、または証人の応答を検証できない | 記憶へのアクセスを止める（隔離）。新しい削除の要求は `LOCALLY_ACCEPTED` まで受け付けるが、確定したとは言わない |

**限界**

- 台帳、anchor、外部の証人（とオーナーの控え）を、**まとめて**古い状態に戻されると、巻き戻りは見つけられない。
- 外部の証人そのものが乗っ取られた場合も、同じく見つけられない。
- ローカルの台帳で、P1 による切り詰めを OS で禁止できるかどうかは、未確認。

## 8. 派生データの削除（C15、B1-P03、B2-P03）

### 8.1 手順

1. **系譜をたどる：** Journal の Manifest と系譜の表から、多段階の関係を求める。たどる範囲は、記憶 → 文脈 → リクエスト → 応答 → 要約と候補 → 派生した記憶 → 成果物とファイル → 書き出し。深さ N、件数 M の上限を設ける（暫定値。D と E で決める）。
2. **対象ごとの状態を決める：**

| 対象の状態 | 意味 |
|---|---|
| `PURGED` | 物理的に削除した（7.5 の保証の範囲で） |
| `SHREDDED` | 鍵を破棄した |
| `QUARANTINED` | 隔離して、取得、送信、取り出しを止めている |
| `PENDING_REVIEW` | 人間の確認を待っている（コードなどの成果物。B2 の7.9） |
| `EXTERNAL` | 管理の外に出ている。送り先と時刻を報告する |
| `TRACE_LIMIT` | 上限のため、その先をたどれていない |

3. **削除の全体の状態：**
   - `COMPLETED_LIVE` になるのは、管理下のすべての対象が `PURGED` か `SHREDDED` になり、`QUARANTINED`（未解決）、`PENDING_REVIEW`、`TRACE_LIMIT` が 0 件のときだけ（B2-P03）。
   - 上限に達した場合は、`TRACE_LIMIT_REACHED` にして、**削除が完了したとは扱わない**。削除の対象を完全には特定できていないからである。扱いは 8.1.1 のとおり。

#### 8.1.1 影響の範囲が分からない場合の隔離（C2-R07）

- **境界の記録：** たどるのを止めた位置（境界のノード）の一覧と、たどりかけの状態を、Journal に `DeletionTraceState` として記録する。上限を引き上げた後や、人間が確認した後に、そこから再開できるようにする。
- **範囲を広げた隔離：** 境界から先は、何があるか分からない。そこで、次をまとめて一時的に止める。
  - 境界のノードに、その作成より後に触れた Run と、それらの Run の保存領域（blob）。取得、送信、書き出しを止める。
  - そのテナントの記憶のうち、境界のノードに触れた後に作られ、無関係であることを系譜で示せないもの。文脈に入れない。
  - 止める範囲が特定できない場合は、そのテナントの、記憶の取得と書き出しの全体を、一時的に止める。
- **新しい派生データを作らせない：** 隔離したノードと、削除の対象は、拒否リストに入れる。
  - Context Engine は、それらを文脈に入れない（B1 の C22）。
  - Reflector は、系譜がそれらに触れる候補を却下する（B2 の M25）。
- **人間の確認待ちの成果物：** `PENDING_REVIEW` の間も隔離したままにする。確認した結果は、削除・残す・作り直しのどれかとして、理由と一緒に記録する。

### 8.2 実行中の Run と、遅れて届くデータ

| 対象 | 扱い |
|---|---|
| 実行中の Run | B2 の7.8（`access_epoch` と拒否リスト）と、5.4 の失効の順序に従う |
| 削除の後に届いた応答 | 汚染されたものとして扱う。記憶や要約の材料にはしない。照合のために、結果の要約の情報（成功か失敗か、大きさ、ハッシュ）は記録する。本文は、その応答の blob ごとの鍵で暗号化して隔離し、削除が完了したら、**その blob の鍵だけ**を破棄する |
| 生成の途中の要約 | 届いたら捨てる。対象を外して作り直す（B2 の7.8） |

**Run の単位で鍵を破棄することの副作用（C2-R07）**

- Run の鍵を丸ごと破棄すると、同じ Run の中の、削除の対象と関係のない成果物も失われる。照合や復旧に必要なリクエストの記録も失われる。
- そこで、blob ごとの鍵（6.2）を使い、**削除の対象を含む blob の鍵だけを破棄する**。
- Run の鍵を丸ごと破棄してよいのは、次の場合だけ。
  - Run 全体が削除の対象である。
  - かつ、その Run に、`UNKNOWN_OUTCOME` や `RECONCILIATION_REQUIRED` の Step が残っていない。
  - 残っている場合は、照合を済ませてから破棄する。

### 8.3 削除した記憶の再抽出

- 消した内容は、残っている元の資料から、もう一度抜き出されることがある。
- ユーザーがはっきり求めた場合（「二度と覚えないで」）に限り、**抑止の一覧**を作る。
  - 内容を正規化し、テナントの抑止用の鍵で計算したブラインドトークンを、別の保存先に置く。
  - 新しい候補が同じトークンに当たれば、却下する。
- **限界：**
  - 言い回しを変えたものは、見つけられない。
  - トークンを残すこと自体が、照合できる情報を残すことになる。このことを、ユーザーに説明する。
- 抑止の一覧の既定は「作らない」。作るかどうかは、オーナーの方針と、ユーザーの同意による。

### 8.4 削除できないデータの報告

`DeletionReport{deletion_id, 対象ごとの状態, 削除できない理由（EXTERNAL／PENDING_REVIEW／TRACE_LIMIT／鍵のバックアップの保管中）, 外部の送り先と時刻, 完全に完了する見込みの日}`

- 管理の外に出たデータについては、「削除した」とは言わない。

### 8.5 バックアップの保管期限と、完全な完了

- B2 の7.7 の世代の管理（`R_data`、`R_blob`、`R_key`、`R_ledger`）に従う。
- `FULLY_COMPLETED` になるのは、次の**両方**を満たしたときだけ（C2-R07）。
  1. 管理下の未解決の対象が 0 件である。`QUARANTINED`（未解決）、`PENDING_REVIEW`、`TRACE_LIMIT` のどれも残っていない。
  2. 削除の対象を含みうるすべてのバックアップの世代で、期限切れか消去の処理が終わっている（B2 の M23）。
- 期間の値は、E で決める（設計A の P1）。

## 9. 監査ログ（C16）

### 9.1 監査の対象

- 権限の変更、ポリシーの変更
- 承認（作成、使用、期限切れ、取り消し）
- Permit の発行と消費
- 外部への送信（許可したもの、拒否したもの）
- 機密情報へのアクセス（`confidential`、`personal`、鍵）
- 記憶の昇格と削除の各段階
- 鍵の生成、更新、失効、破棄
- バックアップと復元
- 緊急停止と再開
- 評価環境へのアクセス（評価の側の監査ログに記録する）

### 9.2 記録の形（本文と認証情報は入れない）

`{audit_seq, ts, actor, action, target_ids, decision, reason_code, labels, sizes, keyed_hashes, policy_version, access_epoch, prev_hash}`

- 監査ログを読めるのは、オーナーだけ。
- 監査ログそのものも、SAG を通して保存する。

### 9.3 改ざん、削除、巻き戻りを見つける方法

- **ハッシュの連鎖：** 各記録に、直前の記録のハッシュを含める。
- **署名付きのチェックポイント：** 一定の件数ごと、または一定の時間ごとに、`{audit_seq, head_hash}` に Ed25519 で署名する。それを、独立した場所（7.3 の anchor の場所）に書き、オーナーの控えにも写す。
- **限界：**
  - ハッシュの連鎖だけでは、鍵を持つ管理者がログ全体を書き換えることや、末尾を削除することを、必ず見つけられるわけではない。
  - 見つけられるのは、外部に写した最後のチェックポイントより前の改ざんだけ。
  - 最後のチェックポイントより後の、末尾の削除は見つけられない。
  - チェックポイントの間隔を短くし、オーナーの控えに頻繁に写すほど、見つけられない範囲は狭くなる。

## 10. 評価環境の隔離（C17、D3、C2-R01）

**初回報告書の既存の方針**（独立審査者が整理したもの）

- 開発用のタスクと、評価用のタスクを分ける。
- dev、validation、test／holdout を区別する。
- holdout は、別の非公開リポジトリに置く。
- 開発中のエージェントからは、アクセスできないようにする。
- 隠しテストは、作業が終わった後に、評価の側で実行する。
- 同じモデルと条件で比べる。
- 最終評価の問題と正解を、開発の側に漏らさない。

この設計は、これらを引き継いで、具体的にする。

### 10.1 構成と分離

評価の側は、開発の側とは別のホスト、または別の VM に置く。その中を、信頼するものと信頼しないものに分ける。

| 構成要素 | 信頼 | 持つもの | 持たないもの | ネットワーク |
|---|---|---|---|---|
| Eval Controller（評価の管理） | 信頼する | 評価の実行の計画、`eval_run_id` の発行、評価の側の Gateway を通した holdout の読み取り専用の認証情報 | 署名の秘密鍵 | holdout のリポジトリと、評価の側の Gateway だけ |
| Test Vault（隠しテストと正解の保管） | 信頼する | 隠しテスト、正解、採点のプログラム（固定したコミットとハッシュ） | 外部への経路 | なし |
| Untrusted Execution Sandbox（信頼しないコードの実行） | **信頼しない** | タスクの入力。評価するエージェント、またはその成果物。ブラックボックスで採点できない場合だけ、隠しテストの写し（10.2） | **署名の秘密鍵、holdout の認証情報、評価の管理用の認証情報** | エージェントが作業している間は、評価の側の Gateway を通してモデルの提供元にだけ。採点の実行の間は、なし |
| Result Collector／Verifier（結果の収集と検証） | 信頼する | Sandbox の外から観測した結果、採点の基準 | 署名の秘密鍵 | なし |
| Signer（評価の結果への署名） | 信頼する。別のプロセス、別の OS ユーザー | 署名の秘密鍵だけ | ほかの入力。署名するのは、Verifier から受け取った検証済みの記録だけ | なし |
| Aggregator（集計） | 信頼する | 署名の公開鍵、集計の規則 | 秘密鍵、holdout の認証情報 | 開発の側へ、制限した報告だけを渡す一方向の経路 |
| Holdout リポジトリ `ken1700-mizui/agent-core-holdout` | — | 書き込めるのはオーナーだけ | 開発の側からの接続 | — |
| 開発の側（開発用の Claude Code のセッションを含む） | — | 制限した報告だけ | holdout の認証情報、評価の側への書き込み | — |

**読み取り専用でマウントしても、読まれることは防げない。** そのため、信頼しない Sandbox に何を入れるかで、隠せるかどうかが決まる（10.2）。

### 10.2 採点の方式：隠せる場合と、隠せない場合

| 方式 | 内容 | 隠しテストを、評価するコードから隠せるか | 優先する順 |
|---|---|---|---|
| **ブラックボックス** | 成果物を Sandbox の中で動かす（コマンドやサービスとして）。Verifier が外から入力を与え、出力を観測して判定する | **隠せる**。隠しテストは Sandbox に入らない | 1（可能な限り、これを使う） |
| **同じプロセスでの実行** | 単体テストのように、テストのコードが成果物のコードを読み込んで、同じプロセスで動く | **隠せない**。成果物のコードは、実行中にテストを読める。結果を書き換えることもできる | 2（ブラックボックスにできない場合だけ） |

**同じプロセスで実行する場合の対策**

- 隠しテストは、エージェントの作業が**終わった後に**、新しい Sandbox に入れる。エージェントは作業の間、テストを見ていない。
- テストを動かす仕組みは、評価の側のものを使う。成果物に含まれるテストの設定ファイル、プラグイン、フックは、取り除くか無効にする。
- それでも信頼の度合いは低いものとして扱い、結果の記録に `assurance: in_process` と書く。ブラックボックスで採点したものは `assurance: blackbox` と書く。

**想定する攻撃と対策**

| 攻撃 | 対策 |
|---|---|
| 偽のテスト結果 | 正式な結果は、Verifier が観測したものから計算する。成果物が自分で報告した結果は、使わない |
| 終了コードの偽装 | 終了コードだけで判定しない。テストごとの結果を Verifier が確かめる。ブラックボックスでは、出力そのものを判定する |
| 採点のプログラムへの干渉 | 採点のプログラムは Sandbox の外（Verifier）にある。同じプロセスで実行する場合も、判定の処理は外に置く |
| テストの実行環境の改ざん | 実行のたびに、ダイジェストで固定した新しい Sandbox のイメージを使う。成果物はワークスペースにだけ置き、実行環境はその都度入れ直す |
| 成果物を読み込む処理への攻撃 | 巨大な圧縮ファイル、シンボリックリンク、パスの悪用などへの対策として、C1 の8.5 の検査と、大きさの上限を使う。成果物を開いたり解析したりするのは Sandbox の中だけで、信頼するプロセスの中では行わない |
| 評価の結果の使い回し | `eval_run_id` は Controller が発行する、1回だけ使える値。Aggregator は、重複した ID と、発行されていない ID を拒否する |
| 他のタスクの結果とのすり替え | 署名の対象に、`task_id`、成果物のハッシュ、`eval_run_id` を含める。これらは Controller が実行を割り当てたときに結び付ける |

### 10.3 署名の対象と、署名の限界

**Signer が署名する記録**

`{eval_run_id, task_id, eval_set_version（holdout のコミット）, grader_version（コミットとハッシュ）, agent_under_test_commit, config_hash（モデルの ID とプロファイル、Runtime の設定）, sandbox_profile_hash, artifact_hash, assurance, 結果（テストごとの合否のまとめ）, started_at, finished_at, controller_id}`

- **署名されていることは、評価の結果が正しいことを保証しない。** 署名が示すのは、「信頼する Verifier が、この記録を出した」ということだけ。
  - Verifier や採点のプログラムに誤りがあれば、誤った結果にも署名が付く。
  - 同じプロセスで実行した場合は、観測そのものが改ざんされうる。

### 10.4 流れ

```
① Controller が eval_run_id を発行する。holdout を固定したコミットで取得し、採点のプログラムのハッシュを検証する
② Test Vault が、タスクの入力と、隠しテスト・正解を分ける
③ Sandbox に、タスクの入力だけを入れる。評価するエージェントの版を固定する。記憶は、新しい評価用の名前空間にする
④ エージェントが作業を終える → 成果物を取り出す（C1 の8.5 の検査）
⑤ 採点する
   - ブラックボックスの場合：新しい Sandbox で成果物を動かし、Verifier が外から確かめる
   - 同じプロセスで実行する場合：新しい Sandbox に、成果物と隠しテストを入れて動かす
⑥ Verifier が、観測した結果から判定する → Signer が署名する
⑦ Aggregator が、署名を検証して集計する → 開発の側へ、制限した報告だけを渡す（11章）
```

**開発の側から変えられないようにすること**

- 採点のプログラム、正解、隠しテストは、holdout のリポジトリ（書き込めるのはオーナーだけ）と、Test Vault にある。
- 評価の記録は、評価の側の保存先に置き、署名とハッシュの連鎖でつなぐ。
- 開発の側には、これらへの書き込みの権限がない。

**リポジトリの分離だけでは足りない**

- リポジトリを分けることや CODEOWNERS だけでは、完全な隔離にならない。実行するときの隔離（別のホストや VM、別の認証情報、別のネットワークの方針、プロセスの分離）があって、はじめて隔離になる。

**評価の側にも、C1 と同じ仕組みを使う**

- 評価の側も、C1 の PDP と PEP、Sandbox、Gateway を使う。ただし、開発の側とは別の、独立した設置にする。

## 11. 評価の汚染と、不正への対策（C18）

| 脅威 | 対策 |
|---|---|
| 開発の側への正解の漏えい | 開発の側への報告は、全体の点数、信頼区間、分類ごとの件数（件数が少なすぎる分類はまとめる）だけにする。holdout の各タスクの ID、入力、出力、失敗の詳細は渡さない。詳しい結果を返すのは、dev と validation の集合だけ |
| モデルによる採点プログラムの改ざん | 採点の判定は、Sandbox の外の Verifier が行う（10.1・10.2）。エージェントには、採点のプログラムのファイルが見えない |
| 隠しテストへのアクセス | エージェントが作業している間の Sandbox には、隠しテストを入れない。ブラックボックスで採点する場合は、採点の間も入れない（10.2） |
| テストを意図して削除すること | 採点には、Test Vault のテストの写しを使う。エージェントのワークスペースにあるテストの変更は、使わない。テストに関わるファイルを変えていれば、印を付ける |
| 評価記録の改ざん | Signer が署名する（10.3）。評価の側の保存先に置き、ハッシュの連鎖でつなぐ |
| 不正な成功の判定 | 成功かどうかは Verifier が決める。エージェントの主張は使わない。きれいな環境で実行する。テストを動かす仕組みの改ざんや、テストを飛ばす仕掛けを、型に当てはめて見つける |
| 外部通信で正解を取りに行くこと | エージェントが作業している間の Sandbox の通信先は、モデルの提供元だけ。Web と、その他の API は通さない |
| Memory Engine への holdout の混入 | 評価の実行ごとに、記憶の名前空間を新しくする。開発の側の記憶には、書き戻さない（B2 の M17） |
| 同じ holdout を繰り返し使うことによる過学習 | holdout は、ゲートの判定にだけ使う。使う回数と予算に上限を設け、使った回数を記録する。定期的に holdout を入れ替える。基準は D で決める |

- 正式な評価の方法と、統計的な合格の条件は、設計D で決める。

### 11.1 評価のデータの、外部への送信の方針（C2-R08）

**評価のデータを2つに分ける**

| ラベル | 中身 |
|---|---|
| `eval_input` | エージェントに渡すタスクの入力 |
| `eval_secret` | 隠しテスト、正解、採点のプログラムの中身、評価の管理用の認証情報、採点のログ |

- どちらも、少なくとも `confidential` として扱う。

| 対象 | 方針 |
|---|---|
| モデルの提供元への入力 | 送ってよいのは、`eval_input` と、エージェント自身の文脈だけ。送信先の `data_policy` が確認済みで、`confidential` を許し、かつオーナーが「holdout をその提供元に送ってよい」と承認した場合に限る。それまでは、holdout での評価を、その提供元では行わない。`eval_secret` は**決して送らない** |
| モデルの応答 | `eval_input` から派生したデータとして、評価の側にだけ保存する。開発の側には渡さない |
| トークンを数える API | モデルの提供元と同じ方針。外に送る量を減らすため、評価では手元での推定を優先する |
| 採点のログ | `eval_secret`。評価の側の外に出さない |
| エラーメッセージ | 隠しテストの中身を含みうるので、`eval_secret` として扱う。開発の側へは、大まかな分類のコードだけを渡す。メッセージそのものは渡さない |
| 評価の成果物 | 評価の側にだけ置く。開発の側に渡すのは、dev と validation の集合の分だけ |
| トレース | 評価の側にだけ置く。本文は入れない（X4） |
| 評価の結果の集計 | 制限する（下記） |
| 評価用の Memory | 評価の実行ごとに、新しい名前空間にする。実行が終わったら破棄する。開発の側の記憶とは、同期しない |

**隠しテストが漏れていないかの確認**

- 評価の側の Gateway の Final Egress Inspector は、外へのリクエストに、隠しテストや正解のフィンガープリント（鍵付き）が含まれていないかを確かめる。含まれていれば遮断し、その評価を無効にする。

**開発の側へ返す集計の、情報の漏えいへの対策**

- **少数の分類：** 件数が下限（暫定値。D で決める）より少ない分類は、まとめるか、出さない。
- **繰り返しの評価による比較：** 少しずつ変えて何度も評価し、結果の差から個別のタスクを推測されることがある。これを防ぐため、holdout を使う回数に上限を設け、使った回数を記録する。分類ごとの差分を、細かく出さない。D で、集計にノイズを加えるかどうかも含めて決める。
- **エラーの詳細：** 渡さない（上の表）。
- 公開する情報の上限の値と、holdout を使う回数は、設計D で決める。

## 13. 不変条件

| ID | 不変条件 |
|---|---|
| X1 | すべてのデータは、分類のラベルの集合を持つ。分類が分からなければ、`confidential` として扱う。派生したデータは、元のデータのラベルの和集合を引き継ぐ。ラベルを外せるのは、権限を持つ人間だけ |
| X2 | 信頼するプロセス（P1〜P3）が正式な保存領域に書き込むときは、すべて SAG を通る。信頼しないコードが直接書く領域は、隔離した一時領域として扱い、正式な領域に移す前に SAG を通す（4.4） |
| X3 | `credential` は、Gateway の認証情報の保管庫の外には、保存されない |
| X4 | Journal、ログ、監査ログには、どの分類の本文も入らない |
| X5 | 拒否した書き込みや送信の監査には、本文を残さない |
| X6 | 保存の認可と、送信の認可は別々に行う。リクエストの記録の保存が認可されなければ、送信もしない |
| X7 | `data_policy` が `unverified` の送信先には、`public` だけを送る |
| X8 | 最終的なリクエストの検査は、Gateway が組み立てた実際の内容に対して行う |
| X9 | `REVOCATION_ENFORCED`（すべての PEP から ack を受け取った時点）より後に、失効した receipt で送信を始めることはない。PEP の中では、失効の処理と送信の開始を、ロックで順序付ける。receipt は、1回の接続の試みにだけ使える。ack が届かない、IPC が切れた、再起動した、のどの場合も、送信しない側に倒す |
| X10 | Phase 3A より前に、認証情報を持つ P3 が、rootful の Docker の権限を持つプロセスから守られていること（rootless の Docker、または別のホストか VM） |
| X11 | Gateway は、CanonicalRequest から決定的に組み立てたものだけを送る。認可していない意味の変更（重複したヘッダー、パスの書き換え、自動で付くヘッダー）は拒否する |
| X12 | 鍵は用途ごとに分け（rendering_hash と request_hash の鍵も分ける）、`key_id` に版を持つ。平文で置く鍵は、限られた少数のものだけ。AEAD は、ランダムな nonce と、テナント・用途・データの ID・版を結び付けた AAD を使う |
| X13 | 独自の暗号方式は使わない |
| X14 | 取得を止めるのは `LOCALLY_ACCEPTED`（D1）から。永続的に確定したと言うのは `DURABLY_ACCEPTED`（外部の証人が受け取ったことを確かめた後）から。利用者への応答は、7.1 の状態に合わせる。確定したかどうか分からなければ、対象のデータを使えないようにする |
| X15 | 台帳、anchor、外部の証人、Journal を検証でき、7.3 の自動修復の条件を満たすときだけ、記憶へのアクセスを許す。署名が正しいだけでは、最新とはみなさない |
| X16 | `TRACE_LIMIT`、`PENDING_REVIEW`、未解決の `QUARANTINED` が残っている削除は、完了として扱わない。削除の対象を完全に特定できない間は、範囲を広げて隔離し、新しい派生データを作らせない。`FULLY_COMPLETED` には、未解決が 0 件であることと、バックアップの処理が終わったことの両方が必要 |
| X17 | 管理の外に出たデータについて、「削除した」とは言わない |
| X18 | 監査ログはハッシュの連鎖でつなぎ、署名付きのチェックポイントを、独立した場所に写す |
| X19 | 開発の側（開発用の Claude Code のセッションを含む）は、holdout の認証情報を持たず、holdout のリポジトリに接続しない |
| X20 | 信頼しない実行の Sandbox には、タスクの入力（と、ブラックボックスにできない場合だけ、作業が終わった後の隠しテスト）だけを入れる。署名の秘密鍵、holdout の認証情報、評価の管理用の認証情報は入れない |
| X21 | 開発の側は、採点のプログラム、正解、隠しテスト、評価の記録を書き換えられない |
| X22 | 開発の側への評価の報告は、11章で制限した情報だけにする |
| X23 | 正式な評価の結果は、信頼する Verifier が観測したものから計算する。成果物が自分で報告した結果や、終了コードだけでは決めない。採点の方式（`assurance`）を記録する |
| X24 | 署名の対象には、10.3 の項目をすべて含める。Aggregator は、重複した `eval_run_id` と、発行されていない `eval_run_id` を拒否する。署名されていることを、結果が正しいことの証明とはみなさない |
| X25 | Audit Writer は SAG を呼び出さない。監査の記録の形には、本文を入れる項目がない。機密の検査の処理は、見つけた値を保存もログへの出力もしない |
| X26 | 漏えいした鍵で、漏えいしたかもしれない期間に作った記録は、独立した根拠で検証し直すまで `SUSPECT` として扱う。署名し直しても、信頼は回復しない |
| X27 | 削除のために鍵を破棄するときは、blob ごとの鍵を使う。Run の鍵を丸ごと破棄するのは、Run 全体が対象で、照合の済んでいない Step がないときだけ |
| X28 | `eval_secret` は、評価の側の信頼する領域から出さない。モデル、トークンを数える API、開発の側には送らない。`eval_input` を送るのは、確認済みの送信先に、オーナーの承認がある場合だけ |

## 14. ゲート

**合格は、完全な安全の証明ではない。**

### 14.1 Technical Gate

| 試験 | 合格の目安 |
|---|---|
| ラベルの継承 | 合成の系譜で、派生したデータのラベルが和集合になっている割合 100% |
| 削除の D0〜D3 の各地点での障害 | 7.2 の復旧の後、整合性が回復した割合 100%。取得が再び始まった件数 0（確定するまで） |
| 鍵の更新、失効、破棄 | 古い版で検証できる割合、新しい版で書き込む割合、破棄した後に復号できない割合が、それぞれ 100% |
| 監査ログ | 連鎖とチェックポイントを検証できる割合 100% |
| Gateway の組み立て | 同じ CanonicalRequest から、同じバイト列になる割合 100% |
| 評価の流れ | Controller → Sandbox → Verifier → Signer → Aggregator の各段階で、署名と固定したハッシュを検証できる割合 100% |
| receipt の状態遷移（5.4） | 合成の筋書きで、状態遷移が設計どおりになる割合 100% |
| 鍵の更新の途中の障害（6.6） | ①〜⑤の各地点で障害を起こした後、すべてのデータを読める割合 100%。移し替えを再開できる割合 100% |
| 削除の状態と、利用者への応答（7.1） | 状態と応答が一致する割合 100% |
| 系譜の状態の保存と再開（8.1.1） | `DeletionTraceState` から再開できる割合 100% |

### 14.2 Safety Gate（攻撃と故障を含む）

| 試験 | 合格の目安 |
|---|---|
| 目印の値を入れた認証情報を、すべての保存先に書こうとする | 保存された件数 0 |
| 目印の値を入れた `personal` や `confidential` のデータで、Journal、ログ、監査、拒否した送信の記録を調べる | 本文が見つかった件数 0 |
| `unverified` の送信先に `internal` 以上を送ろうとする | 送信された件数 0 |
| URL、クエリ、ヘッダーに目印の値を入れる | 見つけた割合 100%（登録済みの目印に限る） |
| 失効と送信の競合（ack の前後、P1 との接続を切る、receipt の使い回し） | ack の後に送信を始めた件数 0。使い回しを受け付けた件数 0 |
| **失効済みの receipt で、新しく送信しようとする**。失効と送信開始を同時に起こす。ack を止める。IPC を切る。Gateway を再起動して、古い receipt を使う | 新しく送信した件数 0 |
| 承認の期限の直前に送信する | 期限を過ぎて送信を始めた件数 0 |
| **漏えいした鍵で作った記録**（漏えいの期間内の、台帳・監査・評価の結果・Permit）を与える | 無条件に信頼した件数 0。独立した根拠で検証し直すまで `SUSPECT` だった割合 100% |
| 暗号文を、別のテナント、別のデータ、別の版に差し替える | 復号に成功した件数 0 |
| Docker のログ、コアダンプ、一時ファイル、監査、検査のエラーメッセージに、目印の値が現れるか | 現れた件数 0（スワップと OS のログは、保証の範囲の外として記録する） |
| 重複したヘッダー、CR と LF、あいまいなパス、自動で付くヘッダー | 送信された件数 0 |
| 古い台帳と古い anchor の組み合わせを戻す（外部の証人は新しいまま） | 見つけられた割合 100%。アクセスを許した件数 0。**署名が正しい古い台帳が、最新として受け入れられた件数 0** |
| 台帳と anchor の正常な更新の途中（7.3 の自動修復の条件を満たす）と、巻き戻り（止める条件）を作る | 正しく区別した割合 100% |
| 台帳と anchor と外部の証人を、すべて古くする | 限界として記録する（見つけられないことを確かめる） |
| 削除を受け付けた後に障害を起こす。D1 の後でプロセスを止める、D1 の後でディスクを失う、D2・D3 の途中で止める | **データが復活した件数 0**（ディスクを失った場合は、`DURABLY_ACCEPTED` と応答していないこと、復元の後に隔離されていることを確かめる） |
| 確定したかどうか分からない状態を作る（証人に届かない、Journal を失う） | 対象のデータを使えた件数 0 |
| 系譜の追跡の上限に達する。確認待ちを残す。**削除の対象が分からない状態を作る** | 完了とした件数 0。範囲を広げた隔離の外で、境界から先のデータが使われた件数 0。新しい派生データが作られた件数 0 |
| 削除の後に届いた応答 | 記憶の材料にされた件数 0。対象と関係のない blob を失った件数 0 |
| 監査ログの途中の書き換え、チェックポイントより前の末尾の削除 | 見つけた割合 100%。チェックポイントより後の削除は、限界として記録する |
| 開発の側から holdout、採点のプログラム、評価の記録に触れようとする | 成功した件数 0 |
| **評価の実行環境（信頼しない Sandbox）から、署名の秘密鍵、holdout の認証情報、評価の管理用の認証情報に触れようとする** | 成功した件数 0 |
| **偽のテスト結果**：成果物が、合格を装う出力を出す。終了コードを偽る。テストの結果のファイルを書き換える。同じプロセスで、テストを動かす仕組みを書き換える | 正式な結果として採用された件数 0（ブラックボックス）。同じプロセスで実行した場合に見つけられなかったものは、`assurance: in_process` の限界として記録する |
| 評価の結果の使い回しと、すり替え（同じ `eval_run_id` を出し直す、別のタスクの結果を渡す） | 受け入れた件数 0 |
| 成果物を読み込む処理への攻撃（巨大な圧縮ファイル、シンボリックリンク、パスの悪用） | 信頼するプロセスに影響した件数 0 |
| `eval_secret` のフィンガープリントを含むリクエストを、外へ送ろうとする | 送信された件数 0 |
| 作業中の Sandbox から、隠しテストや Web に触れようとする。テストを削除する。採点の仕組みを改ざんする | 成功した件数 0。不正な成功の判定 0 |
| 評価用の記憶の名前空間をまたぐ | 混ざった件数 0 |

## 15. 残存リスク

1. **機密の検出の限界：** 機密の検出は完全ではない。特に、言い換えたものや、エンコードしたものは見逃しうる。
2. **P1 の乗っ取り：** P1 が乗っ取られると、P1 の鍵がすべて漏れる。鍵の種類を分けても、それだけでは防げない。
3. **rootless の Docker の可否：** rootless の Docker が使えない場合、実API に接続するには、別のホストや VM が必要になる。費用と手間が増える。
4. **巻き戻り：** 台帳と anchor と控えを、まとめて古い状態に戻されると、巻き戻りは見つけられない。
5. **監査ログの末尾：** 最後のチェックポイントより後の、末尾の削除は見つけられない。
6. **プロバイダーの方針：** プロバイダーの方針の確認は、オーナーの手作業に頼る。方針が変わったことに気づくのが、遅れることがある。
7. **評価の分離の費用：** 評価の側を別のホストか VM に置くには、費用と運用の手間がかかる。用意できるまでは、実API で評価できない。
8. **再抽出：** 言い換えた内容の再抽出は、防げない。
9. **初回報告書との照合：** 初回報告書の全文と照合していない。評価については、審査者が整理した方針だけを使った。
10. **同じプロセスでの採点：** 同じプロセスで採点する場合、成果物のコードから隠しテストを隠せない。結果を改ざんされることも、完全には防げない（`assurance: in_process`）。
11. **SAG の外：** スワップ、OS のログ、OS のクラッシュ報告、ホストやクラウドのディスクのスナップショットは、SAG の外にある。
12. **ディスクを失ったとき：** D1 の後、D2 の前にディスクを失うと、削除の要求は失われうる。利用者の側で、もう一度要求してもらう必要がある。
13. **外部の証人への依存：** 外部の証人が使えない間は、記憶を使えず、削除の要求も確定しない。外部の証人そのものが乗っ取られると、巻き戻りを見つけられない。
14. **漏えいした鍵：** 独立した根拠がない記録は、`SUSPECT` のまま残る。安全な側に倒して扱うので、使えるものが減る。
15. **失効の確認待ちの間：** `REVOCATION_ENFORCED` になるまでの間は、対象の範囲が止まる。ack が届かなければ、範囲ごと止まる。
16. **範囲を広げた隔離の影響：** 削除の対象が分からないときに隔離を広げると、関係のない Run や記憶も、一時的に使えなくなる。
