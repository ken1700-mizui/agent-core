# Agent Core ロードマップ

> 文書の状態：**DRAFT**（E4 で作成。Phase 0 の最終審査を待っている）　作成日：2026-11-26
>
> この文書の位置付けと前提
> - 予定の正本はこの文書、進捗の正本は `docs/STATUS.md` である。設計の正本の決まりは、`E_INTEGRATION.md` の28章。
> - Agent Core は、オーナー自身が使うための、専用の AI の基盤である。
> - 優先する順は、品質、安全性、信頼性、検証可能性、性能、費用の効率、自律性、拡張性。
> - 商用化、課金の仕組み、一般への販売、企業向けの大規模な仕組みは、必須の目標ではない。
> - 初期の構成は、単一のホスト、単一のオーナー、単一のエージェント、モジュラーモノリス。安全のために必要なプロセスの分離（C1 の2.1）と、独立した評価の環境（C2 の10章）は保つ。
> - 数値は、どれも未承認の候補の値である。

## 0. Phase の一覧と依存関係

```
0 → 0.5 → 1 → 2 → 3A → 3B → 3C → 3D ─┬→ 4 → 5 → 6 → 7 → 8 →（本体の完成）→ Service Harness など
                                       └→（性能の改善が確かめられなければ）原因の分析と、計画の立て直し（3D → 3C）
```

| Phase | 名前 | 実API の費用 |
|---|---|---|
| 0 | 基本の設計、E1〜E4 の統合 | $0 |
| 0.5 | 設計資料の確定、Codex による独立した監査 | $0 |
| 1 | Runtime、Journal、基本のツール、Fake と Replay、CLI | $0 |
| 2 | 無料の評価の基盤、Baseline、統計、契約テスト（Sandbox を含む） | $0 |
| 3A | 実API に接続する前の Technical Gate と Safety Gate | $0 |
| 3B | 承認した、小さな規模の実API の接続の試験 | 承認した額だけ |
| 3C | 実モデルでの正式な性能の比較 | 承認した額だけ |
| 3D | 統計の解析と、性能の改善の判定 | 承認した額だけ |
| 4 | 長時間の稼働、障害からの復旧、必要に応じて MCP、最小限の遠隔操作 | 承認した額だけ |
| 5 | Memory Engine | 承認した額だけ |
| 6 | Improvement Engine | 承認した額だけ |
| 7 | Orchestration、複数のエージェント | 承認した額だけ |
| 8 | 個人向けの管理画面、API、遠隔操作 | 承認した額だけ |

**共通の決まり**

- **Phase 3 で性能の改善を確かめられなかった場合は、無条件には次の Phase へ進まない。**
  - 3D の判定が `INCONCLUSIVE` か `DEGRADED` なら、原因を分析し、計画を立て直す。そのうえで、新しく事前登録して、3C をやり直す（holdout の使用の上限を守る）。
  - 進むかどうかは、オーナーが判断する。
- **ロールバック：** Phase のゲートの後で問題が見つかった場合は、その Phase の前の、ゲートに合格した構成に戻す。根拠は Decision に記録する。
- **どの Phase でも、安全のために必須の機能は外さない**（`E_INTEGRATION.md` の11章）。

## 性能の追跡（すべての Phase）

**Phase ごとに記録する項目**（Results Store と Decision に記録する）

- モデルとその版、コミットの SHA、構成のハッシュ
- 成功率、品質、トークン、費用、実行の時間
- 人間の介入、安全性、障害からの復旧

**Owner Workflow Suite の位置付け**

- 個人での利用で、実際に役に立つかを測る評価として使う（D の9.6）。

**実測していない性能について**

- 改善したとは言わない。
- Phase 1〜2 は Fake で動かすので、機能が正しく動くかどうかだけを記録する。性能が上がったとは主張しない。
