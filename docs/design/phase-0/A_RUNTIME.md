## 0. 範囲と前提

- 対象：アーキテクチャ全体の構成、Runtime の状態管理、障害からの復旧。レビュー指摘 R01 と R05 が中心。
- 他の作業単位との接続口：Context／Memory（B）、Safety／隔離（C）、Evaluation／Cost（D）、ロードマップ（E）。
- 守る確定事項：`docs/decisions/OWNER_DECISIONS.md` の D1〜D4。

## 1. 全体の構成

```
┌──────── 制御側（状態を書き込むのはここだけ）─────────┐
│ Run Orchestrator                                     │
│   ├─▶ Journal（追記専用、SQLite）◀─ Budget Ledger    │
│   │    └─ Snapshot / Materialized State              │
│   └─ 各 Engine の接続口：Context(B) Memory(B)         │
│                        Safety(C) Eval/Cost(D)         │
└──────────────┬───────────────────────────────────────┘
               │ Permit（実行許可）付きで Step を発行
┌──────── 実行側 ▼ ────────────────────────────────────┐
│ Worker ── Tool 実行（Sandbox 内、C）                   │
│        └─ Model Provider ポート                        │
│            ├ ScriptedProvider（決定的な偽応答）  Phase 1〜 │
│            ├ ReplayProvider（記録の再生）        Phase 1〜 │
│            └ LiveProvider（Anthropic）  Phase 3B ゲート後のみ │
└──────────────────────────────────────────────────────┘
```

- 制御側と実行側を分ける。Journal と Ledger に書き込めるのは Orchestrator だけ。Worker は結果を返すだけで、状態を直接変えない。
- Safety は迂回できない関門として、Step を発行する経路に必ず挟む。判定は Journal に記録してから実行する。
- `LiveProvider` は Phase 3B のゲートを通るまで、ビルドにも CI にも含めない。認証情報も注入しない。「設定で無効にする」のではなく、「起動に必要な物がそもそも存在しない」状態にする（R01、D1）。

### 1.1 Replay の段階導入（A01）

| 時期 | 記録の種類 | 内容 |
|---|---|---|
| Phase 1〜 | `origin=synthetic` | 人工的に作った記録で Replay を実装する |
| Phase 3B〜 | `origin=live_approved` | 承認を受けた実API 応答の記録を追加する。承認ID、マスキング（伏せ字処理）済みの印、取得日を付ける |

- 該当する記録がない場合は失敗として止める。Live へ切り替えて続けることは禁止。

### 1.2 初期に作る範囲と延期する範囲（A06）

| 区分 | 内容 |
|---|---|
| Phase 1〜2 で作る | 単一 Worker（同じプロセス内）、単純なループの Orchestrator、SQLite の Journal と Ledger、プロセスの排他（A11）、データ形式上の `epoch`（フェンシングトークン）項目 |
| 延期する | Scheduler、キュー、並列 Worker、Heartbeat 付きの Lease Manager、分散ストレージ |
| 延期分を導入するきっかけ | Phase 3C で並列評価が必要だと判明したとき（R06／D と調整）。そのとき差し替えられるよう、接続口（ポート）の定義だけは先に固める |

## 2. 状態の持ち方

- 正本は Journal（イベントソーシング）。現在の状態は、Journal を先頭から順に適用した結果（`fold(Journal)`）として導く。Materialized State（現在状態の表）はその計算結果のキャッシュにすぎない。
- 保存先は SQLite（WAL モード）。保存処理は Storage ポートの裏に隠す。
- 各イベントに付ける項目：
  - `run_id`, `seq`（Run ごとに隙間なく増える番号）, `prev_hash`（直前イベントのハッシュ）, `schema_version`, `epoch`, `ts`
- 各 Step のイベントには、さらに次を付ける：
  - `runtime_version`, `provider_kind`, `model_id`, `context_hash`, `tool_id@version`, `policy_version`

### 2.1 整合性（A07）

- **状態ハッシュは、必ず同じ `seq` 同士で比べる。** Snapshot と COMMIT イベントに `state_hash@seq` を記録し、状態を作り直すときは各 `seq` 時点で照合する。
- **Snapshot は `journal_head_hash@seq` を持つ。** Journal のハッシュ連鎖と一致しない Snapshot は捨て、さらに古い Snapshot か Journal 全体から作り直す。
- **予算の増減は Journal のイベントとして記録する。** Ledger の表は、同じ SQLite トランザクションの中でそのイベントから導く。イベントと台帳がずれることはない。

### 2.2 3つの実行モードの分離（A07）

| モード | 目的 | 外部への副作用 |
|---|---|---|
| `Rebuild` | Journal を**メモリの中で** fold して、状態を計算する（永続的な保存先には書き込まない。P-5、E の2.4） | **構造的に不可能**。Provider や Tool への接続口を渡さず、通信も遮断する |
| `ProjectionRepair` | Materialized State などの、永続化した投影を、Journal から作り直す（保守のモード。A11 の排他のロックを持って行う。E の2.4） | モデルの呼び出し、外部への通信、内容の作り直しはしない |
| `Replay` | 記録を使った再実行（評価・再現用） | 新しい `run_id` で、外部とは切り離して動かす。ReplayProvider と偽の Tool だけを使う |
| `Live` | 新規実行 | 通常の Step 手順（3章）に従う |

モードは型として区別する。別のモードの接続口を誤って受け取れないようにする。

## 3. Step の手順と副作用の分類

### 3.1 Step の状態遷移

```
PLANNED
 → SAFETY_CHECKED    判定と policy_version を記録。拒否なら Run を ABORTED_SAFETY へ
 → APPROVED          承認が必要な Step のみ（3.4）
 → BUDGET_RESERVED   費用のかかる Step のみ（4章）
 → INTENT_RECORDED   冪等キーと引数ハッシュを記録。ここより前では外部に何も起きない
 → PERMIT_ISSUED     実行許可を発行（A02）
 → DISPATCHED
 → SUCCEEDED | FAILED_RETRYABLE | FAILED_FATAL | UNKNOWN_OUTCOME
 → COMMITTED  または  RECONCILIATION_REQUIRED（A10）
```

### 3.2 副作用の分類

Tool Manifest（ツール定義書）で、各ツールに分類と `external_guarantee`（外部サービス側の保証）の宣言を必須にする。

| 分類 | 結果不明時の扱い |
|---|---|
| `READ_ONLY` | 自動で再実行 |
| `IDEMPOTENT` | 外部サービスが冪等キーを保証する場合に限り、同じキーで再実行 |
| `COMPENSATABLE` | 照会（Probe）するだけ。取り消しも再実行も自動では行わない（A03） |
| `IRREVERSIBLE` | 自動再実行は禁止。照会するか、`RECONCILIATION_REQUIRED` に移す |
| `MODEL_CALL` | 専用の扱い（4章、A04） |

**A08：** `external_guarantee=none`（外部サービスが冪等性も条件付き操作も保証しない）のツールは、宣言上の分類にかかわらず、復旧時には `IRREVERSIBLE` として扱う。結果不明のときに自動で再実行してはならない。

### 3.3 取り消し操作（A03）

- 取り消しは、元の操作とは別の独立した Step である。通常の Step と同じく、Intent 記録・Safety 判定・認可・結果確認・復旧処理をすべて通す。
- 取り消しを検討してよいのは、元の操作が実行されたと照会で確定した場合だけ。結果不明のときは、取り消しも再実行もしない。
- 取り消しが失敗した場合や、取り消しをさらに取り消す必要が出た場合は、自動では処理せず `RECONCILIATION_REQUIRED` に移す。

### 3.4 承認と引数の紐付け（A07）

- **承認記録に含める項目：** `step_id`、`tool@version`、正規化した引数のハッシュ、`policy_version`、費用上限、承認者、`expires_at`。
- **一致の確認：** Permit を発行するとき、これらが一つでも違えば承認を取り直す。
- **期限切れ：** `APPROVAL_EXPIRED` になり、Step は `WAITING_APPROVAL` に戻る。期限が切れても自動では承認しない。
- **取り消し：** 承認の取り消しはイベントとして記録し、即座に無効になる。

## 4. モデル呼び出しと費用（A04、A09）

- モデル呼び出しは `IDEMPOTENT` に入れない。専用の分類 `MODEL_CALL` にする。
- 呼び出しの試行ごとに `attempt_id` と新しい予算予約を作る。予約の使い回しはしない。
- 結果が分からない試行は「未確定費用」として残し、上限見積額（`max_tokens` と価格表から計算）で計上し続ける。プロバイダー側の実績と照合して確定するまで、解放しない。
- 再試行するには新しい予約が必要。予算が足りなければ `PAUSED_BUDGET` に移る。

### 4.1 内部予算と実際の請求の区別（A09）

| 項目 | 意味 |
|---|---|
| `estimated_cost` | 内部の見積もり（usage×価格表。`price_table_version` 付き） |
| `safety_margin` | 価格表のずれに備えて、予約に上乗せする余裕 |
| `pending_cost` | 未確定費用（上限見積額で計上） |
| `reconciled_cost` | プロバイダー側の利用実績・請求と照合して確定した額 |
| `unexplained_diff` | 説明のつかない差額 |

- 内部台帳はあくまで**見積もり**であり、請求額そのものとして扱わない。
- プロバイダー側の支出上限は、**厳密な強制停止として機能するか未確認**。予備の防御としてだけ扱い、主な制御は内部上限で行う。内部上限はプロバイダー側の上限より低く設定する。
- 内部見積もりと実請求がずれる要因（あらかじめ分類しておく）：価格の改定・価格表の誤り、キャッシュ割引、失敗したリクエストへの課金、端数処理、税金、集計の時差。
- **費用照合の合格条件（Phase 3B 以降）：**
  1. 許容誤差（金額での絶対値と割合）を、**実API を使う前に**オーナーが決めて記録しておく。値は未定（TBD）。
  2. すべての差額を上の要因のどれかで説明でき、`unexplained_diff = 0` であること。
  3. 説明できる差額の合計が、許容誤差の範囲内であること。
  4. 実際の請求額が、オーナーの承認した上限以内であること。
  - 「差額が内部予算上限以内」であるだけでは合格としない。

## 5. Worker の制御（A02、A08、A11）

### 5.1 実行の許可と停止（A02）

1. **実行直前の認可：** Worker は Step ごとに、使い捨ての実行許可（Permit）を受け取る。Permit は `step_id`・`epoch`・引数ハッシュに紐付き、有効期限は短い。Orchestrator は、実行権（Lease）が有効なときだけ Permit を発行する。
2. **Worker 側の確認：** 実行の直前に、Permit の残り時間が安全マージン以上あるかを確かめる。足りなければ実行しない。
3. **停止の徹底：** 実行権を失った Worker は、プロセスと Sandbox ごと強制終了する。次の実行権は「有効期限＋時計ずれ分の猶予」が過ぎるまで発行しない。
4. **外部サービス側での防止：** 外部サービスが条件付き書き込みや冪等キーに対応していれば、トークンやキーを渡して、そちら側でも二重実行を防ぐ。

### 5.2 Worker 制御の限界（A08）

- Lease、Permit、フェンシングトークンを使っても、**すでに外部へ発行した操作を止められるとは限らない。** 発行後に Worker を止めても、外部サービス側の処理は進むことがある。
- 確認を通過した直後に止まった Worker が、実行権が切れた後に実行してしまうことも、外部サービス側で防げない限り完全には防止できない。
- そこで、外部サービス側で冪等性や条件付き操作を保証できない処理は、安全側に倒して次のように運用する。
  - 結果不明のときの自動再実行は禁止（3.2）。
  - 単一 Worker でのみ実行する。
  - 実行の前に人間が承認する。
  - 実行の後に照合し、解決できなければ `RECONCILIATION_REQUIRED` に移す。

### 5.3 単一 Worker の排他制御（A11）

ロックファイルが存在するかどうかの確認には頼らない。次の3層で、複数プロセスが同時に動くことを防ぐ。

1. **OS レベルの排他ロック：** 起動時に、専用のロックファイルへ OS の排他ロック（`flock`／`fcntl`）を、待たずに取得を試みる。取れなければ、すぐに終了する。ロックはプロセスが生きている間ずっと持ち続ける。プロセスが異常終了しても、OS（カーネル）が自動で解放する。ファイルに書いた PID は表示用で、判定には使わない。
2. **SQLite 上の所有者記録：** ロックを取った後、`BEGIN IMMEDIATE` のトランザクションで `runtime_owner` 行の `epoch` を1増やし、自分のインスタンスIDを記録する。以後すべての書き込みトランザクションは、`epoch` が自分の値と一致することを条件にする。一致しなければ中止して、自分を終了する。
3. **SQLite の設定：** WAL モード、`busy_timeout` を設定する。書き込みは必ず `BEGIN IMMEDIATE` で始め、トランザクションの外での書き込みは禁止する。

**限界：**
- OS の排他ロックは、同じマシン（同じカーネル）の上でしか効かない。
- ネットワークファイルシステム（NFS など）の上では信頼できない。
- そのため、DB とロックファイルはローカルのファイルシステムに置く。複数のマシンで同じ DB を共有する運用は、並列化の導入（1.2）まで禁止する。

## 6. Run の状態遷移

```
CREATED → QUEUED → RUNNING ──▶ VERIFYING ──▶ COMPLETED
             ▲       │  ▲          │（検証に失敗）→ RUNNING または FAILED
             │       ▼  │
             │  WAITING_TOOL / WAITING_APPROVAL / PAUSED_BUDGET
             │
             └── RECOVERING（再起動時の一時状態）

RUNNING / WAITING_* ──（キャンセル要求）──▶ CANCELLING ──▶ CANCELLED
RUNNING / CANCELLING / RECOVERING ──（未解決の外部操作）──▶ RECONCILIATION_REQUIRED
RECONCILIATION_REQUIRED ──（人間が解決）──▶ RUNNING | CANCELLED | FAILED
いずれの状態からも ──▶ FAILED / ABORTED_SAFETY
```

- **終了状態：** `COMPLETED`, `CANCELLED`, `FAILED`, `ABORTED_SAFETY`。いったん入ったら、どこへも遷移しない。
- **VERIFYING（A07）：** 次をすべて満たして初めて `COMPLETED` になる。
  - 成果物のハッシュが、宣言された出力と一致する。
  - 合格チェックをすべて通過している。
  - 未確定の予約・未確定費用・結果不明の Step が 0 件。
- **CANCELLING（A07）：** 実行中の Step から遅れて届いた結果は、`LATE_RESULT` として記録だけ残し、処理の進行には使わない。結果不明の Step が残っているうちは `CANCELLED` にしない。

### 6.1 RECONCILIATION_REQUIRED（A10）

- **入る条件：** 次のどれかに当てはまったとき。
  - 照会の回数上限、または照会の期限（`reconciliation_deadline`）を過ぎても、外部操作の結果が確定しない。
  - 取り消しに失敗した。
  - `external_guarantee=none` の操作の結果が分からない。
  - `CANCELLING` のまま、期限内に照合が終わらない。
- **期限の役割：** `CANCELLING` や `RECOVERING` が無期限に止まり続けないよう、各状態に期限を設ける。期限を過ぎたら必ずこの状態に移す。
- **停止と通知：** この状態は終了状態ではない。人間の解決を待つ待ち状態で、Run はここで止まり、オーナーに通知する。
- **人間による解決：** 次のどれかを、証拠（外部サービスの記録など）を添えてイベントとして記録する。
  - 「実行された」と確定 → 照合を続け、`RUNNING` に戻るか、`CANCELLING` から `CANCELLED` へ進む。
  - 「実行されていない」と確定 → 同上。
  - 「永久に確認できない」と受け入れる → Run は `FAILED`（理由 `UNRESOLVED_EXTERNAL_EFFECT`）で終わる。
- **禁止事項：**
  - 結果不明を、成功（`COMPLETED`）や正常なキャンセル（`CANCELLED`）として扱ってはならない。
  - 未確定費用は、プロバイダー側の実績と照合するまで上限見積額のまま残す。

## 7. 復旧の動作（クラッシュ地点ごと）

| クラッシュ地点 | 判定 | 動作 |
|---|---|---|
| `INTENT_RECORDED` より前 | 副作用なし | Step を最初からやり直す。予約は解放する |
| `INTENT_RECORDED`〜`DISPATCHED` | 未発行の可能性が高い | Permit が未発行なら安全にやり直せる。発行済みなら `UNKNOWN_OUTCOME` と同じ扱い |
| `DISPATCHED` のまま結果なし | `UNKNOWN_OUTCOME` | 分類表（3.2）に従う。`MODEL_CALL` は4章に従う |
| 結果を受け取った後、`COMMITTED` の前 | Journal に結果が未記録 | 冪等キーで照会する。取得できなければ `UNKNOWN_OUTCOME` |
| Snapshot の作成中 | 壊れた Snapshot | 2.1 の手順で作り直す |

復旧処理は `Rebuild` モードで状態を作り直してから始める（2.2）。作り直しの最中に副作用は起こらない。

## 8. 不変条件

| ID | 不変条件 |
|---|---|
| I1 | Journal は追記のみ。`seq` は隙間なく単調増加し、`prev_hash` の連鎖が途切れない |
| I2 | `INTENT_RECORDED` が永続化されていない副作用は、発行されない |
| I3 | 書き込めるのは、有効な `epoch` を持つ1つの実行主体だけ |
| I4 | `IRREVERSIBLE` と `external_guarantee=none` の Step は、結果不明の後に自動で再実行されない |
| I5 | どの時点でも「確定額＋予約額＋未確定費用 ≤ 内部予算上限」が成り立つ |
| I6 | 同じ `seq` での `fold(Journal)` の状態ハッシュが、Snapshot と Materialized State のハッシュに一致する |
| I7 | 終了状態からはどこへも遷移しない |
| I8 | Safety の判定記録がない Step は発行されない。`policy_version` が変わったら判定をやり直す |
| I9 | 復旧処理は冪等。2回続けて実行しても、結果の状態は同じ |
| I10 | Phase 3B のゲートを通るまで、`LiveProvider` に到達する経路（コード・認証情報・通信許可）が存在しない |

## 9. 合格条件

### Technical Gate（Phase 1〜2、3A）

- **障害注入テスト：** 7章の全クラッシュ地点 × 全分類（取り消し、`MODEL_CALL`、キャンセル、承認の期限切れを含む）で、ランダムに1,000回以上実行する。
  - I1〜I18 の違反が 0 件。
  - 偽の外部サービス側で数えた二重実行が、`IDEMPOTENT`（効果の重複なし）、`IRREVERSIBLE` とも 0 件。
- **再生の一致：** 完了したすべての Run で、同じ `seq` での状態ハッシュが 100% 一致する。
- **排他：** 次の3つの試験で、2つ目のプロセスの書き込み受理が 0 件（A11）。
  - 2つ目のプロセスを起動する。
  - 1つ目のプロセスを強制終了した後に、新しいプロセスを起動する。
  - 古い `epoch` のプロセスから書き込む。
- **形式の互換性：** スキーマ v(n) の Journal を v(n+1) で読める。
- **復旧時間：** イベント1万件以下の Run で、p95 5秒以内（PROVISIONAL）。

### Safety Gate（設計A の担当分）

- I8、I12〜I17 の違反が 0 件。
- 復旧時に Safety の判定を飛ばす経路が、コード上に存在しない（静的検査とテストの両方で確認）。

### 費用ルール（Phase 1〜3A 共通）

- CI と実行環境で、Anthropic API ホストへの通信が 0 回（通信ログで確認）。
- `LiveProvider` がビルドに含まれておらず、認証情報も注入されていない。
- 各 Phase の終了時に、課金がないことを人間がコンソールで確認する。

### Live Integration Gate（Phase 3B）

- 4.1 の費用照合の合格条件を満たす。
- 安全面の違反が 0 件。

### Performance Gate（Phase 3D）

- 設計A では定めない。D と E で定める。

## 11. 残存リスク

1. **外部操作の二重実行：** 冪等性にもフェンシングにも対応しない外部サービスでは、二重実行を完全には防げない。照合と人間の判断に頼ることになる（A08）。
2. **費用の上限：** プロバイダー側の支出上限が厳密に止まるか分からない。内部上限が主な防御になる（A09）。
3. **自律実行の停止：** `RECONCILIATION_REQUIRED` は人間の対応を待つため、その間は自律実行が止まる（A10）。
4. **単一マシン構成：** ディスクが故障して Journal を失うと復旧できない。バックアップの方針は未定。
5. **排他の前提：** 単一 Worker の排他は、ローカルのファイルシステムであることが前提（A11）。
6. **偽応答と実モデルの差：** Phase 3B で初めて分かる不具合がありうる。
7. **記録の機密性：** Replay の記録や Journal の機密性は、C で決める。
8. **原文との未照合：** 初回報告書の原文と、この文書を直接照合したことはない。照合は審査者を通してのみ行われている。
