# WP2-08 Cost Engine：複数のホームにまたがる実験の予算（実装の記録）

> 文書の状態：**DRAFT**（審査待ち）　作成：2026-11-28　承認：D18・D19　正本：D（10・11章）、`PHASE_2_EVALUATION_CONTRACT.md` の7章（7.1〜7.8）
> 合成の XTU だけで、実 API は使わない。単位はすべて台帳と同じマイクロ XTU。

## 1. どこで予算を強制するか

| 強制の手段 | 内容 | 迂回できるか |
|---|---|---|
| **各ホームの台帳**の、予約の1つのトランザクション（D.V10） | **実験の XTU の上限**（既存の EXPERIMENT の範囲の `SetBudgetCap`）。**実験の作業単位の上限**（WP2-08 で加えた。EXPERIMENT の範囲の `SetCounterCap`、WORK_UNITS） | 実験の Run の予約は、どれも両方の上限を通る。作業単位の上限がない実験の予約は `BudgetCapMissingError`（安全側） |
| 試行の Run の上限（`trial_ops`） | `trial_cap_xtu` を Run の XTU の上限に、`trial_event_cap` を Run の作業単位の上限にする | Phase 1 の階層のまま |
| 開始の前の確認（`admit_trial`） | 連鎖が正しい・このホームが開いている先端・台帳の上限が連鎖から計算した値と**完全に一致**・残りが試行の上限以上 | 一致しなければ新しい試行を拒否（`LEDGER_CAP_MISMATCH` など） |
| Results Store | **写しとして比べるだけ**（`check_chain`）。強制の手段にしない | — |

**作業単位の上限を加えた理由：**
- 締めたホームの XTU の上限を「使用済み ＋ 保留」に下げても、0 XTU の試行は通ってしまう。
- そこで、締めるときに作業単位の上限を「使った数」に下げる。こうすると、**0 XTU の試行も拒否**される。
- 開くときの作業単位の上限は `events_per_home`。

**形式の変更：**
- 台帳と Journal の保存の形式は変えていない。`JOURNAL_SCHEMA_VERSION` は 8 のまま。
- 変えたのは次の3点だけで、旧版の DB はそのまま開ける。
  - `SetCounterCap` の範囲に EXPERIMENT を加えた（拡張）。
  - 読み取り（`held_reservations`）を加えた。
  - 実験の予約で作業単位を数えるようにした。

## 2. ホームの連鎖（`adapters/sqlite_home_chain.py`）

| 記録 | 内容 |
|---|---|
| 開始の記録（`OpeningStatement`） | 実験、仕様のハッシュ、ホーム、順番、前の締めのハッシュ、前までの確定の合計、引き継いだ保留（**元のホーム**の ID 付き）、上限、不足、作業単位の上限。**前までの確定 ＋ 引き継いだ保留 ＋ 上限 − 不足 ＝ 実験の上限** |
| 締めの記録（`ClosingStatement`） | このホームの確定の合計、このホームの保留、未解決の引き継ぎ、無効な試行の費用、やり直しの費用（どちらも確定の合計の内）、Journal の head、**後継のホームの ID**（締めの本文のハッシュから決まる） |
| 解決の記録（`CarriedHoldResolved`） | 元のホームで確定した保留の、確定の額と、元の台帳の記録のハッシュ。**(元のホーム, 予約) ごとに1回** |

**一意と排他（署名だけに頼らない）：**
- 一意性は SQLite の UNIQUE で保つ。対象は次のとおり。
  - ホームごとに開始と締めは1つ。
  - 締めごとに開始は1つ（`prev_closing_hash`）。
  - 後継の ID は1つ。
  - 解決は1つ。
- 排他は、実験ごとの `flock` で保つ。走らせる者は1つだけ（`ChainBusyError`）。
- オーナーの鍵の MAC は、変更と偽造を見つけるためだけに使う（`ChainIntegrityError`）。
- ファイルは 0600 で、それ以外の権限は拒否する。

**上限は常に絶対の値：** 開いている先端の上限は、連鎖から次の式で計算し、台帳にその値を書く。

> 実験の上限 − 前までの確定 − 開始時の引き継ぎ ＋ Σ(この先端で解決した保留 − その確定の額)

増分では書かないので、やり直しても予算は増えない。

## 3. 手順と、異常終了の後

| 手順 | 順序 | 異常終了の後 |
|---|---|---|
| `start` | 開始の記録 → 上限を書く | `repair` か `start` のやり直しで、同じ値を書く |
| `close` | **先に上限を下げる**（XTU は使用済み＋保留、作業単位は使った数）→ 締めの記録 | 下げた後の異常終了：新しい作業はもう拒否される。やり直すと同じ締めになる（すでに同じ値なら書かないので、Journal の head も同じ） |
| `open_successor` | 前のホームが台帳でも締められていることを確かめる → 開始の記録 → 上限を書く | 記録の前：何も与えていない。記録の後：`admit_trial` が `LEDGER_CAP_MISMATCH` で拒否し、`repair` が値を書く。後継は締めの中に固定されているので、別のホームは開けない |
| `resolve` | 元のホームで予約が確定していることを確かめる → 解決の記録 → 上限を上げる | 記録の後：拒否 → `repair`。2回目の解決は何もしない（同じ内容）か、`ChainConflictError`（違う内容） |
| `check_chain` | すべてのホームの台帳から、確定と保留を計算し直す | 連鎖と食い違えば完了にしない。Results Store の写しと食い違っても完了にしない |

**ホームの数：** 開始の記録の数は `max_homes` を超えない（`MAX_HOMES`）。`max_homes` は、仕様を固定するときに、イベントの数から計算した必要な数以上であることを確かめる（WP2-01）。

## 4. 試験（`tests/unit/test_wp2_08_experiment_budget.py`、27 件）

| 求められた項目 | 試験 |
|---|---|
| 実験全体の予算の上限 | 台帳が上限で拒否する（受け付けの確認とは別に）。残りが試行の上限より少なければ受け付けない |
| 試行ごとの予算の上限 | Run の上限で台帳が拒否する |
| 複数のホームの間の費用の引き継ぎ、確定済みの費用、未確定の保留 | 切り替えで上限が増えない（300 ＋ 1,000 ＋ 8,700 ＝ 10,000）。保留は新しいホームの予約にならない |
| 無効な試行とやり直し | 費用は確定の合計に残る。確定の合計を超える申告は拒否する |
| 二重の計上の防止 | 解決で、解放した分だけ上限が上がる（600）。2回目は変えない。異なる内容は衝突 |
| ホームの切り替えの途中の異常終了 | 4つの地点（下げた後、締めと開始の間、開始の記録の後、解決の記録の後） |
| 複数の後継の防止 | 別のホームを開けない。同じ開始はやり直しても同じ。違う開始は衝突 |
| 複数回の移行の後の照合 | H1 の保留が H2 を経て H3 に、元のホーム H1 の ID のまま渡る。H3 で解決し、計算し直した値が一致する |
| XTU が 0 の試行 | 締めたホームでは作業単位の上限で拒否する。作業単位の上限で止まる |
| 金銭以外の上限 | 実験の作業単位の上限 |
| 安全側 | 連鎖の外で上げた上限、作業単位の上限、改ざん、2つ目の走らせる者、権限、元のホームでの記録されない確定 |
| Phase 1 との互換 | 実験のない Run は変わらない。保存の形式の版は 8 のまま。既存の全試験が成功 |

## 5. 保証しないこと（未解決として残す）

- **連鎖の記録の削除と巻き戻しは見つけられない。** 先端のホームの台帳は、連鎖と食い違えば拒否する。
- **新しいホームでの新しい連鎖は防げない。** 新しい連鎖の始まりを新しいホームで作られると、二重の割り当てになる。独立の証人は Phase 3A（E の21章）。
- 台帳を直接書き換えられる者（root、オーナーの鍵）は対象の外（Phase 1 と同じ）。
- `trial_event_cap` は Run の作業単位の上限で近似している。作業単位はイベントの数と同じではない。
- Benchmark Runner（WP2-12）への組み込み、Results Store の写しの作成、`PAUSED_BUDGET` での再開は、範囲の外。

## 6. WP2-12 の統合の条件（D20。解決済みとしない）

| # | 条件 |
|---|---|
| 1 | 実験の ID と、実際の予算の範囲の対応。Run の grant の `experiment_id` が、必ずその実験の連鎖の先端のホームの EXPERIMENT の範囲になること |
| 2 | 実験全体の、ただ1つの管理の経路。試行の開始は必ず `admit_trial` を通る。Runner のほかに、実験の Run を作る経路がない |
| 3 | ホームの連鎖の排他。実験ごとの `flock` を、Runner の寿命の全体で持つ |
| 4 | 閉じたホームへの新しい割り当ての拒否。台帳の作業単位の上限と、`admit_trial` の両方 |
| 5 | 保留の照合と再開。結果不明の Attempt を、元のホームで照合してから `resolve` する。照合の前に実験を完了にしない |
| 6 | 連鎖と台帳が一致しない場合の拒否（`LEDGER_CAP_MISMATCH` など）。`repair` は連鎖からの値だけを書く |
| 7 | XTU が 0 の試行の扱い。作業単位とイベントの上限で必ず止まる |
| 8 | **WORK_UNITS と、実際の Journal のイベントの数は違う。** `trial_event_cap` を Run の WORK_UNITS の上限で近似しているのは、**イベントの数の強制ではない**。イベントの数の強制は、WP2-12 で別に実装し、試験する |
| 9 | ホームのイベントの数、バイトの数、起動の時間の上限（P-2）による、ホームの切り替えの判断 |

- **Phase 3A の条件として保つもの：** 連鎖の全体の巻き戻しと、別の連鎖の作成に対する独立の証人。
- **実 API の接続の前に必須：** 正式な予算の強制（上の 1〜9 と、独立の証人）を確かめること。
