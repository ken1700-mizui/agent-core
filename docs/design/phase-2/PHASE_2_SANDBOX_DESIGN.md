## 1. 目的と範囲

- Phase 2 では、Sandbox の中でシェルとテストを実行する（信頼しないコード）。
- **信頼しないコードを実行する前に**、隔離、自己診断、時間の上限（P-5）を試験で確かめる（ROADMAP の0.2、D11）。
- ホストでの直接の実行へのフォールバックは、どの場合も禁止する（C1 の8.2、S10）。
- 対象は Linux のホストだけ（Phase 1 の承認：案 1）。

## 2. プロセスと責任の分離（C1 の2.1）

| プロセス | 信頼 | 持つもの | 持たないもの |
|---|---|---|---|
| **P1 Runtime**（今の `agent_core` と CLI） | TCB | Journal への唯一の書き込み、PDP、Permit の発行と消費、A.I17 の監視（7章）、P2 への要求（IPC） | Docker の API、ネットワーク、認証情報、プロセスの起動 |
| **P2 Broker**（新しい別のプロセス。Phase 2 で作る） | TCB | Docker の API（唯一）、写しの作成と取り出し（ファイルの4区分）、Sandbox の時間の上限の強制、自己診断、コンテナごとの設定の照合、回収（Reaper） | Journal への直接の書き込み（結果は P1 に返す）、外部ネットワーク、認証情報 |
| **P3 Gateway** | — | Phase 2 では作らない（D1：認証情報なし、外部通信なし） | — |
| **P4 Sandbox**（コンテナ） | 信頼しない | 上限のある資源と、ワークスペースの写し | 上のすべて。Docker のソケット、ホストのファイル、ネットワーク |

- **P1 と P2 の間：** Unix ドメインソケット。P1 の側で相手の資格情報（`SO_PEERCRED`）を確かめる。要求と応答は型付きのメッセージで、Permit の ID と結び付ける（P2 は有効な消費の記録のない実行を拒否する）。
- **OS の利用者：** Phase 2 では P1 と P2 を**別のプロセス、別の OS 利用者**にする（オーナーの承認、D15）。Docker のソケットに触れるグループは P2 の利用者だけにする。P1 の利用者は Docker のソケットに触れられない。
- **import の契約：** 今の `phase1-no-network-or-process`（通信とプロセスの起動の経路なし）を、次のとおり狭く変える（**オーナーの承認が要る**）。
  - `agent_core`：AF_UNIX のソケットの client だけを、新しいアダプター（例：`agent_core.adapters.broker_client`）に限って許す。AF_INET、AF_INET6、DNS、`subprocess`、`os.exec*` は、引き続き禁止する。
  - 新しいパッケージ `agent_core_broker`（P2）：Docker の Engine API の client（AF_UNIX）だけを許す。`subprocess` は使わない（Docker の CLI を呼ばない。7.5 の案）。
  - 試験：AF_INET などを開こうとした場合に失敗すること（今のネットワークの遮断の試験を広げる）。

## 3. Docker の基本の設定（C1 の8.1、8.6）

| 観点 | 設定（値は PROVISIONAL） | 確かめ方 |
|---|---|---|
| 利用者 | コンテナの中は root ではない UID（例：10001）。daemon は `userns-remap` か rootless を優先（6章で環境ごとに決める） | 自己診断、inspect の照合 |
| capabilities | `--cap-drop=ALL`、`--security-opt no-new-privileges` | 自己診断（`CapEff` が 0）、inspect |
| システムコール | Docker の既定の seccomp。AppArmor／SELinux の既定のプロファイル（**この環境では AppArmor がない**。6章） | 自己診断（`Seccomp: 2`）、inspect |
| ルートのファイルシステム | `--read-only`。`/tmp` は大きさの上限のある tmpfs（例：64 MiB、`noexec,nosuid,nodev`） | inspect |
| Docker のソケット | マウントしない。privileged、ホストの PID・IPC・ネットワークは使わない | 自己診断（ソケットがない）、inspect |
| ネットワーク | `--network none` | 自己診断（外に届かない、インターフェースは `lo` だけ） |
| 資源 | `--cpus 1`、`--memory 1g`（swap なし）、`--pids-limit 256`、ulimit `nofile=1024`、`nproc=256` | 自己診断（fork の上限、メモリの上限） |
| 書き込みの量 | ワークスペースは大きさを固定した領域（loop のファイルシステムか、大きさの上限のある tmpfs。例：256 MiB）。使えない構成では「監視による停止」と記録し、**上限を保証したとは扱わない**（C1 の8.6） | 自己診断（上限で書き込みが失敗する） |
| 標準出力・標準エラー | P2 が読み取りの上限（例：1 MiB）で読む。超えた分は捨て、捨てたことを記録 | 試験 |
| 子プロセス | `--init`（PID 1 は小さな init）。終わったらコンテナごと消す。ラベル（`run_id`、`attempt_id`、`owner_epoch`） | 回収の試験 |
| 環境変数 | 許可した名前だけ（例：`PATH`、`HOME`、`LANG`）。認証情報は渡さない | inspect |
| イメージ | **ダイジェストで固定**した小さなイメージ（7.4） | inspect のイメージのダイジェスト |
| 時間 | 7章（P-4 の確定案） | P-5 の受入の試験 |

## 4. 自己診断と、コンテナごとの照合（C1 の8.2、8.7）

### 4.1 起動のときの自己診断（P2 が行い、結果を P1 に返す）

自己診断用のコンテナ（固定のイメージと、固定の診断のプログラム。信頼しないコードではない）で、次の**すべて**を確かめる。

1. root ではない（`id -u` が 0 でない）。
2. capabilities がない（`CapEff`、`CapPrm`、`CapBnd` が 0）。
3. `no-new-privileges` が効いている（`NoNewPrivs: 1`）。
4. seccomp が効いている（`Seccomp: 2`）。禁止されるはずのシステムコール（例：`mount`、`unshare(CLONE_NEWUSER)`、`ptrace` の一部）が失敗する。
5. Docker のソケットがない（`/var/run/docker.sock` などの既知の場所と、マウントの一覧）。
6. ネットワークが `none`（インターフェースが `lo` だけ。外への TCP、UDP、DNS が失敗する）。
7. 資源の上限が効いている（`pids` の上限で fork が止まる、メモリの上限で割り当てが失敗するか殺される、ワークスペースの上限で書き込みが失敗する）。
8. ルートのファイルシステムが読み込み専用、`/tmp` の大きさの上限。
9. ホストのファイル（ホームディレクトリ、`/etc/shadow` に当たるもの、ホストのリポジトリ）が見えない。

- **1つでも満たさなければ、Sandbox は「使えない」。** コードを実行するツールはすべて拒否する（`SANDBOX_UNAVAILABLE`）。ホストで実行しない。
- 自己診断の結果（項目ごとの合否、Docker と runtime の版、カーネル、cgroup の版、AppArmor の有無）を、P1 が Journal ではなく台帳の監査に記録する（内容は版と合否だけ）。
- 自己診断は Runtime を起動するたびに行う。前回の合格を引き継がない。

### 4.2 コンテナごとの照合（C1 の8.7）

- コンテナを作った後、起動する前に、inspect の結果を `sandbox_profile` と照合する（利用者、capabilities、`no-new-privileges`、読み込み専用のルート、ネットワーク、マウントの種類と ro／rw と元の場所、資源の上限、seccomp、イメージのダイジェスト）。
- 一致しなければ、そのコンテナを壊し、実行を拒否する。`sandbox_profile_hash` は、ConfigSpec と A.I11 の記録に入れる（`PHASE_2_EVALUATION_CONTRACT.md`）。

## 5. ファイルの4区分と、写しと反映（C1 の8.5、S18、S19）

Phase 1 の File Broker（ADR-0008、`dir_fd` による解決、目録の MAC）を土台にする。

| 区分 | Phase 2 の決め方 | 強制 |
|---|---|---|
| ① 写せるファイル | RunGrant の `files.read` とワークスペースのルートの重なりから、除外の一覧（`.env*`、`*.pem`、`*.key`、`id_*`、`.npmrc`、`.pypirc`、`.netrc`、`.git` の認証情報、クラウドの認証情報）を除いたもの | P2 が写しを作るときに選ぶ。`.git` は作業ツリーだけ書き出す |
| ② 中で読めるファイル | ①と同じ（ファイル単位の読み取りの権限は提供しない） | — |
| ③ 中で書けるファイル | ディレクトリの単位の ro／rw のマウント（例：`tests/` は ro） | マウント |
| ④ ホストに反映できるファイル | RunGrant の `files.write` | 取り出すときの検査（下） |

**取り出すときの検査**（1つでも満たさなければ、反映を**全体として**取り消す）：コンテナを止めた後に読む。写しを作ったときと比べて差分を作る。パスが④の内側。削除は方針で許すときだけ。普通のファイルだけ（リンク、デバイス、FIFO、ソケットを拒否）。setuid と setgid を拒否。大きさとファイルの数の上限。`openat2` 相当の、リンクを追わない読み取り（Phase 1 の `dir_fd` の方式）。反映は一時の置き場に書き、ファイルごとに原子的に置き換える（Phase 1 の WriteTicket の方式）。

- 評価の採点（Benchmark Runner）は、**Agent の Sandbox とは別の採点用の Sandbox** で、反映の後の作業ツリーに対して隠しテストを実行する。Agent の Sandbox に隠しテストは入れない（`PHASE_2_EVALUATION_CONTRACT.md`）。

| 項目 | 観測した値 | Sandbox への影響 |
|---|---|---|
| OS とカーネル | Ubuntu 24.04.5 LTS、Linux 6.18.44（Firecracker の VM） | Linux のホスト。対象の範囲 |
| Docker | `docker`、`dockerd` 29.9.3、`containerd` v2.4.2、`runc` 1.5.3 が**導入済み**。**daemon は動いていない**（ソケットなし） | 使うには daemon の起動が要る（**今回は起動しない。オーナーの承認が要る**） |

| seccomp | カーネルは対応している（`/proc/sys/kernel/seccomp` あり）。このプロセス自身は seccomp なし | Docker の既定の seccomp が効くかは**未確認** |
| AppArmor | **なし**（モジュールなし） | C1 の8.1 の「AppArmor／SELinux の既定のプロファイル」を**満たせない**（10章の判断の事項） |
| 利用者の名前空間 | `max_user_namespaces` = 64271 | `userns-remap` や rootless の可能性はある（**未確認**） |
| 資源 | 4 CPU、16 GiB、ディスクの空き 58 GiB | 評価の規模には足りる見込み |
| イメージの取得 | Docker のレジストリへの通信は、ネットワークの方針で許されるか**未確認** | 取得できなければ、イメージを固定の方法で用意する方法を決める（7.4） |

- **未確認の事項：** daemon を起動できるか（VM の権限、storage driver の `overlay2`）。seccomp と cgroup の上限が実際に効くか。`userns-remap` か rootless が動くか。レジストリへの通信。
- **Docker が使えない場合の代替の検証の環境**（安全の条件は下げない）：
  1. **GitHub Actions の標準の runner（ubuntu-24.04）**：Docker が動いており、AppArmor があり、cgroup v2。Sandbox の Safety Gate の試験の**正式な環境の候補**。実行のたびにオーナーの承認が要る（D7 と同じ扱い）。
  2. **オーナーが用意する専用の Linux の VM**（AppArmor か SELinux あり、rootless の Docker）。
  - 代替の環境がない場合は、Sandbox を使う機能を**使えないまま**にする（自己診断が失敗し、コードを実行するツールは拒否される）。安全の条件を下げた実行はしない。
- **試験の印：** Docker を要する試験は、Phase 1 の `privileged` と同じ方式の新しい印（例：`sandbox`）にする。Docker がない環境では `SANDBOX_NOT_RUN` として**失敗**させ、スキップしない。CI では専用の手順で選んで実行する。

## 7. P-4（A.I17）の最終の設計案

### 7.1 方針

- **3つの層**で時間の上限と停止を扱う。基本の方針（P1 の監視、P2 の外からの時間の上限、コンテナの中の補助の監督）は維持する。
  1. **主な強制：P2 の外からの停止。** P2 はコンテナを作るときに期限（単調な時計の絶対の時刻）を持ち、期限でコンテナごと止める（SIGTERM、猶予の後に SIGKILL、確認できなければコンテナの削除）。C1 の8.1・8.6 の正本。P1 の指示に頼らない。
  2. **P1 の監視：** 期限の検査、Run の期限の昇格、停止の要求、停止の確認の記録、新しい実行の拒否の判断。P2 の強制が働いたかを、記録と P2 の状態で確かめる。
  3. **補助：コンテナの中の監督（PID 1）。** P2 が止まったときに残る**補助の手段**にすぎない。**同じ UID の PID 1 という性質を、信頼しないコードから監督を守る根拠にしない**（中のコードが同じ UID なので、性質の検証の結果に関わらず、保護を主張しない）。
- 監視は限られた責任だけを持つ：承認、Permit の発行、保留の解放、結果の確定、完了、再実行、ポリシーの変更は行わない。
- **停止を確認できない操作は OUTCOME_UNKNOWN とし、費用の保留を維持する。** 自動で再実行しない。停止の要求と、実際の停止の確認を分ける（P-4 の9.3）。
- **設計上の保証は、実際の試験で確かめるまで「保証済み」と記録しない。** 7.4 の表の「状態」はすべて「設計・未検証」。

### 7.4 障害ごとに残る保証と、保証できない動作（**すべて設計・未検証**）

| 止まったもの | 新しい実行 | 実行中の Sandbox | Attempt と費用 | 保証できない動作 |
|---|---|---|---|---|
| **P1**（Runtime） | 始まらない（Permit を出す主体がない） | **P2 が期限で止める**（7.4.1 の条件のとき） | P1 の再起動の後、P2 の状態とラベルで照合。確かめられなければ OUTCOME_UNKNOWN、保留を維持 | 7.4.1 の条件が欠けたとき。P1 の停止中の Run の期限の昇格（再起動の後に行う） |
| **P2**（Broker） | **拒否する**：P1 は P2 の応答がなければ Sandbox を「使えない」とし、新しい実行の要求を出さない。要求を送ったが応答がない Attempt は OUTCOME_UNKNOWN | **止まる保証はない**：外からの停止が働かない。補助の PID 1 の監督が期限で止める**かもしれない**（保護の根拠にしない） | 期限と猶予を過ぎて停止を確認できない Attempt は OUTCOME_UNKNOWN、保留を維持、Run は RECONCILIATION_REQUIRED | P2 の停止中の実行の停止。P2 の再起動の後の回収（Reaper）までの資源の使用 |
| **補助の監督**（PID 1） | 影響なし | P2 の外からの停止が働く | 通常どおり | — |
| **Docker の daemon、containerd** | 拒否（自己診断が通らない、P2 が操作できない） | **止まる保証はない**（daemon の状態による） | OUTCOME_UNKNOWN、保留を維持 | daemon の停止中のコンテナの動作 |
| **ホスト**（電源、カーネル） | — | — | 再起動の後、すべて回収し OUTCOME_UNKNOWN | すべて |

#### 7.4.1 P1 が止まっても P2 の期限の管理が続く条件

1. P2 は P1 の子プロセスとして寿命を結び付けない（別のプロセスの集団とセッション。P1 の終了の信号を受け取らない。P1 の起動の後に P2 が死なない）。起動の方法はオーナーの承認が要る（例：P1 とは別に、P2 の利用者で起動しておく）。
2. P2 は、コンテナを作るときに期限を受け取り、**P2 の中とコンテナのラベル**に持つ。P1 からの後の指示に頼らない。
3. P2 は、P1 との接続が切れても、期限の管理を続ける（接続の喪失で停止の管理をやめない）。
4. P2 の期限の時計は単調な時計。P2 が再起動したら、ラベルの期限と作成の時刻から計算し直し、過ぎていれば止める。
5. P1 の再起動の後、P1 は P2 に状態を問い合わせ、記録と照合する。

### 7.5 生存の記録

- 台帳の1つの行（上書き）。項目：`owner_epoch`、監視の実行の ID（起動のたびに新しい乱数の ID）、周期の番号、台帳の時刻（high-water）、P2 の実行の ID。
- **信じない場合：** 行の `owner_epoch` が今の Journal の `owner_epoch` より古い。監視の実行の ID が今のものと違う。時刻が決めた遅れ（例：周期の3倍）より古い。行がない（以前の版の DB）。どれでも「監視は止まっていた」と扱い、新しい Permit と Sandbox の開始を拒否し、先に回収（8章）を行う。
- 再起動の前の監視の状態は引き継がない。毎回、記録（`run_status_times`、Attempt の状態、P2 の状態とラベル）から計算し直す。

### 7.6 P1 と P2 の IPC の契約

| 項目 | 契約 |
|---|---|
| 経路 | Unix ドメインソケット。ソケットのファイルは、P1 と P2 の利用者だけが入れるディレクトリに置く |
| 認証 | 両側で `SO_PEERCRED` を確かめる：P2 は接続の相手の UID が P1 の利用者であること、P1 は相手の UID が P2 の利用者であることを確かめる。違えば切断し、監査に記録 |
| 権限 | P2 は、P1 からの要求だけを受ける。要求は `prepare`、`start`、`status`、`stop`、`collect`、`reap`、`self_diagnose` だけ。P2 から P1 へは応答だけ（P2 は P1 に命令しない） |
| 要求と応答の対応 | 要求は `request_id`（一意）、`attempt_id`、`permit_id`、`receipt_id`（`start` の場合）、`owner_epoch`、`sandbox_profile_hash`、期限を持つ。応答は同じ `request_id` と `attempt_id` を返し、P1 が照合する。違えば捨て、OUTCOME_UNKNOWN の扱い |
| 重複の防止 | `start` は `receipt_id` ごとに**最大1回**。P2 は、同じ `receipt_id` のラベルのコンテナがあれば、新しく作らず、今の状態を返す（コンテナのラベルが永続の記録。P2 の再起動の後も効く）。`stop`、`status`、`collect`、`reap` は冪等 |
| 古い要求 | P2 は、見た中で最も新しい `owner_epoch` より古い要求を拒否する（再起動の前の P1 の要求で動かない） |
| 時間 | 応答がなければ、その要求の結果は不明。`start` の結果が不明なら OUTCOME_UNKNOWN |
| 大きさ | メッセージの大きさに上限。認証情報やファイルの内容を載せない（ハッシュと ID だけ。写しはファイルの4区分の経路） |
| 前提 | P2 は、有効な Receipt の証明がない `start` を拒否する。P2 は Journal と台帳を読まない。証明は、P1 が要求に付ける MAC（`receipt_id`、`attempt_id`、`owner_epoch`、期限、`sandbox_profile_hash` を覆う。鍵は P1 と P2 だけ。Phase 1 の Permit の MAC の方式）で確かめる |

### 7.7 P-5 の受入の試験（**既存の13項目を削除しない**）

- P-4 の5章の10項目（変えない）＋ 7.4 の旧版の A（P2 の外からの期限の停止が P1 の監視なしで働く）、B（中のコードが PID 1 の監督を止められないかの**確認**。結果に関わらず保護の根拠にしない）、C（生存の記録の行が1つで追記されない。以前の版の DB を開ける）＝ **13項目**。
- 加える項目（改訂）：
  - D. P2 が止まっているとき、新しい実行が拒否される（要求が出ない）。
  - E. P2 が止まった後の実行中の Attempt は、停止を確認できなければ OUTCOME_UNKNOWN で保留が残り、P2 の再起動の後に回収される。
  - F. 古い `owner_epoch` や違う監視の実行の ID の生存の記録を信じない。

## 8. 異常終了と回収（C1 の8.7、S26）

- 起動の後の最初の処理（自己診断の前）：Agent Core のラベルのコンテナ、ボリューム、一時の置き場を一覧にし、今の Lease の Attempt のものでないものを止めて消す。その結果はホストに反映しない。対応する Attempt は、確かめられなければ OUTCOME_UNKNOWN（保留を維持）。
- 回収したことを監査に記録する（内容は ID と結果だけ）。
- 反映の最中の異常終了は、反映を1つの単位として OUTCOME_UNKNOWN にする（P-4 の4.3）。
