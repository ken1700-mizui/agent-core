### 推奨：B（P3：期限の監督）＋ A を将来の候補として確認

設計の条件との対応：

| 条件 | B での実現 |
|---|---|
| P1 と P2 が異常終了しても時間の制限が働く | P3 は独立のプロセス（systemd が管理）。期限は P3 の記録 |
| 停止の機能が使えなければ新しい実行を拒否 | P2 の `prepare` と `start` は P3 の生存（MAC 付きの応答）と登録の確認を要する。なければ `DEADLINE_UNAVAILABLE`（開始の前の拒否） |
| 開始の前に停止の責任と期限が確立 | 登録（Receipt、コンテナの cgroup の識別、期限、猶予）→ P3 が同期して確認 → それから P2 が開始 |
| 監督自身の異常終了 | systemd が再起動。P3 が止まっている間は新しい開始を拒否。実行中のものは P3 の再起動の後に期限を戻して止める（戻せなければ直ちに止める） |
| 停止の権限は最小限 | KILL だけ。対象は登録された cgroup だけ |
| 承認・Permit・費用の確定・再実行をしない | P3 はそれらの経路を持たない（import と OS の権限で分ける） |
| Docker API の権限を広げない | P3 は Docker のソケットに届かない |
| ホスト・カーネルの障害まで保証しない | 主張しない |

### 受入の条件（実装の前に固定する案）

1. P1・P2 を SIGKILL しても、登録された期限＋猶予＋P3 の周期の内に、コンテナのすべてのプロセスが止まる（中のコードが監督を止めた場合を含む）。
2. P3 を SIGKILL すると、新しい開始は拒否される。P3 の再起動の後、期限を過ぎたものは止まる。
3. 壁時計を戻しても期限は延びない。boot ID が違う・記録が壊れているときは直ちに止める。
4. P3 は登録されていない cgroup に何もしない。承認・Permit・費用・Journal に触れない。
5. P3 の記録の破損・欠損は、すべての開始の拒否になる。
6. 停止を確認できなければ、P1 の側は OUTCOME_UNKNOWN と保留のまま。

実装には新しい OS の権限（P3 の利用者、systemd のユニット、cgroup の権限）が要るので、**別の承認**とする（D18 で承認されていない）。

## S-R02 P2 の再起動の後の期限（実装と試験）

- 受け付けたときに、**boot ID と CLOCK_BOOTTIME**（壁時計の変更で動かない、カーネルの時計）を記録に持つ。再起動の後は、同じ boot ID なら boot の時計で経過を計る。
- boot ID が違う、boot の時計が読めない：**期限を安全に戻せないので、直ちに停止**する。
- boot の時計がないときは、新しい開始を記録の前に拒否する（`DEADLINE_UNAVAILABLE`。P1 の側では「実行されていない」）。`prepare` も準備できないと答える。
- 停止を確認できないもの：P2 は停止を記録しない。P1 の側は OUTCOME_UNKNOWN と保留（Phase 1 のまま）。
- 試験：`tests/unit/test_sr_sandbox_remaining.py`（壁時計を1日戻しても延びない、別の boot と時計なしで直ちに停止、時計なしで開始の拒否、止められないものは ACCEPTED のまま）。
- 残る限界：同じ boot の中で P2 の記録そのものを書き換えられる者（root）には効かない。
