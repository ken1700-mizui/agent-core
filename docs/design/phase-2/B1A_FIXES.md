## 1. B1A-01 実行の記録の耐久性

方式：エントリごとの MAC（Broker の鍵）、**独立した head のファイル**（最後のエントリの `seq` と `hash`、`record_id`、MAC。書いて同期してから名前を替える）、genesis の乱数の `record_id`。Phase 1 の Journal の「head を別に持つ」設計と同じ考え方。

| 障害 | ハッシュの連鎖だけで | 今の方式 |
|---|---|---|
| エントリの途中の破損・書き換え・並べ替え | 見つかる | 見つかる（連鎖と MAC。鍵のない者は連鎖を作り直せない） |
| 末尾の完全なエントリの欠損 | **見つからない**（短い連鎖も正しい） | 見つかる（head が後のエントリを指す） |
| 書き込みの失敗 | 途中の行は見つかる | その場で記録を使わなくなる（`broken`）。途中の最後の行は、承認されていない書き込みなので切り捨てて報告（`repaired_partial_tail`） |
| fsync の失敗 | — | その場で使わなくなる。次に開くときに、書けていたエントリを数える（その Receipt は二度と実行しない） |
| ファイルの置き換え（別の記録） | 見つからない | 見つかる（`record_id` と MAC） |
| 異常終了と再起動 | — | head は高々1つ遅れる（エントリと head の間の停止）。1つだけなら前に進め、2つ以上なら拒否 |
| 記録と head の**一貫した巻き戻し**（古い本物の写し）、鍵を持つ者（root）による変更 | 見つからない | **見つからない。主張しない**（試験で限界を示した） |

使用済みの Receipt と owner_epoch は、同期してからでないと使わない（ACCEPTED と epoch のエントリは実行・受付の前に同期）。通常の障害（書き込みや同期の失敗、停止）でこれらが消えて古い権限が戻ることはない。

## 2. B1A-02 排他

記録のファイルの隣のロックのファイルに `flock`（排他、待たない）。**記録を読む前に取る**（試験で順序を確かめた）。2つ目の Broker は記録を使えず、すべてを拒否する。ロックはプロセスの終わりで OS が外す（異常終了の後も取り直せる）。ソケットのロックとは別。

## 3. B1A-03 停止と副作用

P2 は、開始のときに自分で確かめた設定から **閉じ込めの証拠（`Containment`）** を決めて記録に残し、状態・停止・回収の応答に付ける（`CONTAINED`：ネットワークなし、P2 の作業の場所を除いてホストに書ける場所がない、`collect` で返すもの以外は出ない。`UNKNOWN`：証拠なし）。

| 場合 | 結果 |
|---|---|
| 実行の前の中止（`prepare` の失敗、承認と違う内容） | ABORTED_BEFORE_DISPATCH、保留を解放 |
| P2 が記録の**前に**、認証された応答で開始を拒否した（`PRE_ACCEPTANCE_REFUSALS`） | 実行されていない：FAILED_DEFINITE |
| 終わった、かつ `CONTAINED` | 終了の符号で COMPLETED か FAILED_DEFINITE |
| 停止を確認した、かつ `CONTAINED` | FAILED_DEFINITE（外への副作用がないことの根拠は閉じ込めの証拠） |
| それ以外（停止の確認だけ、閉じ込めの証拠なし、開始の後の失敗、応答の消失、重複） | **OUTCOME_UNKNOWN、保留を保つ** |

開始の後の失敗は、P2 が「実行していない」と答えない（`RECORD_UNAVAILABLE` は開始の前だけ。開始の後は `SANDBOX_FAILURE`）。

## 4. B1A-04 承認の内容と実行の内容

Sandbox で動かすもの（実行物 `program_ref`、イメージ、Sandbox の設定、ワークスペース、時間の上限、停止の猶予）は、`sandbox_run` のツールの入力として ActionContent に入る。ゲートの claim が、それを承認された ActionDescriptor（Permit、Receipt に結び付く）と照合する。`run_sandbox_operation` は、実行する内容を**承認された内容から読む**。呼び出し側の期待が違う、または Sandbox の内容でないときは、実行の前に中止する（`ARTIFACT_MISMATCH`。6つの項目それぞれで試験）。P2 はさらに、設定とプログラムの許可と、コンテナごとの設定の照合（WP2-03）を行う。

## 5. B1A-05 監視の遅延

| 区分 | 周期 | 最大の遅延（設計） | 確かめたこと |
|---|---|---|---|
| P2 の期限の監視（`tick`） | 監視の周期（候補 1 秒） | 周期 ＋ ロックの下の最も長い要求（受け付けの 5 秒のタイムアウト、Backend の呼び出しのタイムアウト） | 周期で動くこと、遅い Backend の呼び出し（0.3 秒）の間の遅延が上限の内であること |
| P1 の IPC | 要求ごと | クライアントのタイムアウト（候補 5 秒）。応答がなければ結果不明 | 既存の試験 |
| P1 の監視（WP2-04） | Run の周期（候補 10 秒） | WP2-04 で定義 | WP2-04 |

P1 が止まっても P2 の監視は続く（P2 は P1 の子でない）。P2 が止まると監視は止まり、実行中のコンテナが止まることは保証しない（HIGH、WP2-04 で実測）。通信の異常はタイムアウトで結果不明になる。
