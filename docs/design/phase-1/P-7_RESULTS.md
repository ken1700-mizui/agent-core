## 1. 同一性（S1）

- 試験：`tests/unit/test_journal_identity.py`（A、B、C、停止、復旧、結果不明、後からの照合）。実行中の状態、再起動後の `RuntimeStateMachine.load`、`apply_event` を1件ずつ当てた参照の畳み込み、の3つの意味が一致すること、予約・費用・停止・Journal の head が読むことで変わらないこと、ページの大きさで状態が変わらないこと。Rebuild だけを変えた改変で 14 件が失敗することを確かめた（試験が差を見つけられる）。
- 版をまたぐ確認：`tools/perf/state_identity.py`。改善の前の版で7つの場面の Journal（小）と A・B・C の Journal（3,004／4,350／3,450 件）を書き、同じファイルを改善の前と、M1・M2・M5・P-2 の各段の後に読んで、意味と台帳・head のハッシュが**すべて一致**した。
- 派生の索引（M1）は意味の比較から外し、別に確かめた（全件の数え直しと毎イベントで一致、Rebuild と実行中で一致、不一致は `StateIndexError` で拒否）。

## 5. 満たさない基準の原因（確かめた方法つき）

1. **メモリ（基準 5）：Journal を開くときの連鎖の検査がイベントをすべて持つ。** A 10万件で、開いた直後の最大メモリが 740 MiB、Rebuild の後も 740 MiB（Rebuild は最大を増やさない。`ru_maxrss` を開く処理だけのプロセスと比べた）。2万件で関数ごとの割り当ての最大を測ると、`sqlite_journal._verify_tenant` が 134 MiB（行を `fetchall` し、`_verify_consecutive` で全イベントの一覧を作る）、`sqlite_ledger._journal_view` が 28 MiB。M5 は Runtime の読み込みだけを逐次にしたので、この最大は変わらない。**改善の案（承認が必要）：** 開く処理の連鎖の検査と `_journal_view` も、カーソルから1件ずつ検査する（検査の内容は変えない）。
2. **C の起動と増え方（基準 3、4）：`_unused` が Attempt を全部見る。** `plan_attempt_status` が予約・Permit・受領の ID の重複を `state.attempts` の全件で調べる（`state_machine._unused`）。C 5万件の Rebuild のプロファイル（参考の時間 33.6 秒）で、この式と `getattr` が約 13 秒。Attempt の数の2乗で増える。**改善の案（承認が必要）：** 使用済みの ID の派生の索引（M1 と同じく、正本ではなく、Rebuild の後に全件と照合）。
3. **追記（基準 6）：実行中の経路は、遷移ごとに書き込む表を丸ごと写す。** M2 は Rebuild だけを変え、追記の経路の写し（`_CopyOnWrite` が表を初めて書くときに写す）は前と同じ。A では Step の表（10万件で約 3.3 万）を Step の遷移ごとに写す。これは P-7 の M4（写しを減らす）の範囲で、今回は禁止。**M4 が必要。**

## 6. M4、M6 の要否

- **M4（追記の写しを減らす）：必要。** 基準 6 は M4 なしでは満たせない（原因 3）。
- **M6（開く処理と Rebuild の解析の共有）：基準のためには必須ではない。** 起動の時間は A・B で基準を満たし、C の超過の主な原因は `_unused`（原因 2）。メモリの基準は M6 ではなく、開く処理の検査の逐次化（原因 1）で下がる見込み（未検証）。M6 は起動の時間を定数倍で縮める追加の手段として残す。
- いずれもオーナーの承認の後。

## 7. P-2 の制限の値の推奨（計測に基づく。**承認はオーナー**）

| 項目 | 推奨 | 根拠 |
|---|---|---|
| `limit_events` | 50,000 | 最も重い C で起動 27.3 秒（最大 28.5 秒）。60 秒に約2倍の余裕。C は2乗の項があるので、10万件（68 秒）は超える |
| `warning_events` | 30,000 | 上限の6割。C の2万件で 9.3 秒 |
| `limit_bytes` | 160 MiB（167,772,160） | C の5万件の DB が 137.8 MiB（1件あたり約 2.9 KB）＋ WAL の余裕 |
| `warning_bytes` | 96 MiB（100,663,296） | 上限の6割 |
| `reserve_events` | 200 | Phase 1 の見本の作業の1回の Run の数十件に余裕。開始の4件は別に数える |
| `reserve_bytes` | 1 MiB（1,048,576） | 200 件 × 約 3 KB に余裕 |

- 原因 2 と 3 を直した後は、計測をやり直して上限を上げられる（A・B は10万件で 60 秒以内）。
- D9 は変えない。この表は提案。
