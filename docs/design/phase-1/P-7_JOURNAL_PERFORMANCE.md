## 2. 追加の計測（原因の分析）

### 2.1 方法

- 道具：`tools/perf/journal_profile.py`（開発の道具。標準ライブラリだけ。試験の世界 `tests/support` を使い、本物の `SqliteJournal`、台帳、ゲートを通す）。
- 構成：
  - **A**：1つの Run に多数の Step（作成、開始、取り消しで3件）。
  - **B**：多数の Run に、それぞれ3つの Step。
  - **C**：多数の Run に、それぞれ3つの Step、各 Step に1つのツールの Attempt（決定、予約、Intent、Permit、消費、claim、開始、使用量の報告、完了）、Step の確定。実際の利用に近い。
- 規模：A・B は約 2,000・4,000・8,000 件、C は約 1,000・2,000・4,000 件（倍々）。各1回、それぞれ新しいプロセス。
- 上限と停止の条件：1件の計測は 600 秒で打ち切る（打ち切りはなかった）。大きな規模は繰り返さない。
- 計るもの：生成の時間、追記の1件あたりの時間（生成の4分の1ごと）、開く処理（Journal の検査）、Rebuild（`RuntimeStateMachine.load`）を `cProfile` の下で（**プロファイラの分だけ遅い**。比較と内訳のためで、絶対の値ではない）、最大の常駐メモリ、時間の多い関数。
- 環境：P-1 と同じ（Xeon 2.3GHz の 4 vCPU、16 GiB、Python 3.12.3、SQLite 3.45.1）。

## 3. 原因：推定と確認の区別

| 項目 | 前回の推定（P-1） | プロファイラでの確認 |
|---|---|---|
| Step の作成のときの WP04-R03 の検査（`plan_step_create` が `_all_final(state.attempts_of_run(run))` で、その Run の**すべての** Step と Attempt をたどる） | 推定していなかった | **A の主な原因と確認。** 1つの Run の Step の数に比例する処理を Step ごとに行うので、1つの Run に Step が多いと2乗になる。Rebuild も同じ `plan_*` の検査を通すので、追記と Rebuild の両方で起きる |
| 遷移ごとの地図の写し直し（`_with` が `dict(...)` で地図の全体を写す） | 主な原因と推定 | **原因の1つと確認（A では2番目、B では1番目）。** 1回の費用が地図の大きさに比例し、実体の総数とともに2乗に近く増える。この規模では比例の部分（JSON、検査）より小さいが、10万件以上では支配的になる見込み（2.2 の B の伸び） |
| `run_steps` の組（tuple）の更新（`(*old, new)`） | 原因の1つと推定 | **プロファイラの上位には出なかった。** 1つの Run の Step の数に比例するので、A では2乗の項だが、`attempts_of_run` より小さい |
| イベントの読み込み（`RuntimeStateMachine.load` がすべてのイベントを一覧に集めてから Rebuild する） | — | 時間は比例。**メモリが件数に比例する**（10万件で 744 MiB の主な理由と推定。イベントの対象を全部持つため。確認はメモリの内訳のプロファイルではなく、構造からの推定） |
| ハッシュの連鎖の検証 | — | 比例と確認（開く処理の時間）。1件あたりの費用は JSON の書き出しと検査 |
| 台帳の整合の検査（`_journal_view` がすべてのイベントを解析し直す） | — | 比例と確認（10万件で約 2.1 秒） |
| 同じイベントの重ねた解析 | — | 開く処理（連鎖の検証と台帳の検査）と Rebuild で、1つのイベントを3回解析する（構造から確認） |
| イベントの追記 | — | 1件ごとに `plan_*` の検査（A では Run の Step の数に比例）、地図の写し直し、DB のトランザクション。A で伸び、B と C でほぼ一定 |

## 4. Rebuild の高速化の方式の比較

| 方式 | 計算量（Rebuild） | 起動の性能 | 追記の性能 | メモリ | 複雑さ | 保守性 | 既存のコードへの影響 | 安全性と整合 | Snapshot への接続 |
|---|---|---|---|---|---|---|---|---|---|
| **M1 索引の追加**：Run ごとの「未解決の Attempt の数」と Step の一覧を状態に持ち、WP04-R03 などの検査を O(1) にする | A の2乗の項を除く | A で大きく改善 | A で一定に | わずかに増える | 小 | 良い（索引は状態から決まる） | `state_machine.py` の状態と `apply_transition`、`plan_step_create` | 検査は残し、答え方だけ変える。索引と元の状態の一致を試験で確かめる | 索引も Snapshot に含める |
| **M2 Rebuild の中だけ変更できる内部の構造**（辞書と一覧に直接書き、最後に1回だけ不変の `RuntimeState` に固める） | 地図の写し直しを除き、比例に | 大きく改善 | 変わらない（追記の経路は別） | 減る（写しがない） | 中 | 良い（Rebuild の中に閉じる） | `rebuild_with_head`、状態の組み立て | 同じ `plan_*` の検査を同じ順に通す。結果の状態が今と同一であることを試験で確かめる | 固めた状態がそのまま Snapshot の元になる |
| **M3 イベントの適用と状態の保存の分離**（`apply` は変更の差分を返し、保存の段で一度に当てる） | M2 と同等 | M2 と同等 | 追記も改善しうる | 中 | 大 | 中（2つの段の契約が要る） | `apply_payload` とその呼び出しの全体 | 原子性を保つには差分の適用を1か所にする必要 | 差分を Snapshot と組み合わせやすい |
| **M4 全体の写しを減らす**（地図を区分けして、変わった区分だけ写す。または持続的な地図） | 追記の写しを O(N) から小さく | 改善 | **追記を改善**（M2 は追記に効かない） | 小さい | 中〜大（持続的な地図を自作すると大。新しい依存は使わない） | 中 | `RuntimeState` の地図の型 | 不変の見え方を保つ必要 | 影響なし |
| **M5 読み込みのメモリを減らす**（イベントを一覧に集めず、ページごとに検証しながら畳み込む） | 変わらない | 少し改善 | 変わらない | **件数に比例しなくなる**（状態の大きさだけ） | 小 | 良い | `RuntimeStateMachine.load` | 「読む間に Journal が伸びた」の検査と、head の一致の検査を保つ必要 | 影響なし |
| M6 重ねた解析の共有（開く処理で検証したイベントを Rebuild に渡す） | 定数倍の改善 | 改善（約3回が1回に） | 変わらない | 一時的に増えうる | 中 | 中（検証と Rebuild の結び付きが強くなる） | `SqliteJournal.open` と `load` | 同じ検査を同じ対象に行うことを保つ必要。検査を省かない | 影響なし |

## 5. 推奨する方式と、実装を分けた作業の計画（**実装は承認の後**）

| S1 | 同一性の試験を先に作る：今の Rebuild の結果（状態の全体と、状態のハッシュ）を、A・B・C と既存の試験の Journal で記録し、新しい実装と比べる試験。改変した Journal の拒否の試験はそのまま | `tests/unit/`（新しい試験）、`tools/perf/` | 今の実装で成功する |

## 6. 性能の改善の受入の基準（提案）

1. **同一性：** A・B・C と既存の試験の Journal で、新しい Rebuild の状態が今の実装と同一（状態のハッシュが一致）。
2. **検査：** 状態遷移の検査、ハッシュの連鎖、台帳の整合の検査を1つも省かない（改変、欠落、順序の違いの Journal を拒否する既存の試験がすべて成功）。
3. **起動：** 10万件で、起動の合計（開く処理と Rebuild）が 60 秒以内（A・B・C のどれでも）。
4. **増え方：** 件数を倍にしたときの Rebuild の時間が 2.2 倍以下（A・B・C、1万から10万件の範囲）。
5. **メモリ：** 10万件で最大の常駐メモリが、今（744 MiB）の半分以下。
6. **追記：** 10万件の時点の追記の1件あたりの時間が、1万件の時点の 1.5 倍以下（A・C）。
7. 8種類の品質の検査と、次回の CI の成功。

## 7. P-2 の具体的な実装の設計（**設計だけ。D9 の承認の内容は変えない**）

### 7.1 何を数えるか

| 量 | 求め方 | 信頼の根拠 |
|---|---|---|
| イベントの数 | `tenant_head` の `tenant_seq` の合計（Journal の正本の値） | 追記のトランザクションの中で決まる |
| ファイルの容量 | `PRAGMA page_count` × `page_size` | DB 自身 |
| 起動の時間 | 開く処理と Rebuild の時間を、開くたびに台帳の新しい小さな表に記録（直前の値） | 単調な時計。記録は台帳のトランザクション |

### 7.2 段階と動作

| 段階 | 条件（どれか） | 動作 |
|---|---|---|
| 通常 | すべて警告の値の未満 | 制限なし |
| 警告 | イベント数・容量・起動の時間のどれかが警告の値以上 | CLI の `status` と `shell` の開始の時に固定の通知を出す（件数、容量、起動の時間、上限、次の操作） |
| 制限 | どれかが上限以上 | **新しい作業の開始を拒否する**：新しい Task、新しい Run、実行中の Run の新しい Step（`JOURNAL_LIMIT_REACHED`）。**拒否しないもの**：停止、取り消し、復旧、照合、`declare-unresolved`、一時ファイルの回収、状態の確認、実行中の Attempt の終わり（完了、失敗、結果不明の記録、使用量の報告、未実行の証明）、Step と Run の終わりの遷移、オーナーの操作（ポリシー、上限、停止の解除）。安全のための追加のイベントは常に書ける |

- **実行中の Run がイベントを増やす場合：** 上限に達した後は新しい Step を作れないので、Run は今の Step を終えた後、検証して完了するか、上限で止まる。止まった Run は、既存の経路（`stop` と `recover`）で終える。
- **原子性：** 新しい作業の拒否の判断は、Journal の追記のトランザクションの中で、その時点のイベントの数から行う（同時の追記で上限を越えない）。起動の時間の段階は、開いたときの記録から決める。
- **再起動の後：** イベントの数と容量は Journal から、起動の時間は記録から求めるので、再起動しても制限は続く。上限は、オーナーの署名付きの操作（例：`SetJournalLimits`）で台帳に記録し、既定の値はコードに持つ（下げる方向は Permit の失効と同じく即時に効く）。
- **削除と切り詰めはしない。** 制限を解く方法は、上限の引き上げ（オーナーの承認）、新しいホームへの移行（新しい Journal で始める。古い Journal は読み取りと復旧のために残す）、後の Snapshot と性能の改善。
- **CLI の通知：** 固定の文言、機密を出さない、端末の制御文字を無害化する（既存の出力の規則）。

## 8. P-6 の互換性の確認（以前の版のデータ）

### 8.1 方法

- 一度だけ、本物の以前の版（P-6 の前の `d23b1e8`）で合成のホームを作り（承認待ちの Run を1つ）、今の版で、そのホームの**写し**を操作した（元のホームは変えていない。sha256 で確認）。
- 同じ振る舞いを CI でも確かめられるよう、以前の版の形を合成で作る試験を加えた（`tests/unit/test_p6_compatibility.py`、4件。今の版でホームを作り、P-6 の項目を設定と保存の本文から除く）。

### 8.2 結果

| 対象 | 以前の版のデータへの今の版の動作 | 分類 |
|---|---|---|
| CLI の設定のファイル（`profile` なし） | `status`、`shell` とも `PROFILE_REFUSED` で拒否。Journal を開く前で、Journal と設定のファイルは1バイトも変わらない | **安全側の拒否**。ただし、そのままでは状態の確認も復旧もできない（オーナーが設定に `profile` を書き足せば使える） |
| Journal（イベント、連鎖、台帳の整合） | `profile` を書き足せば、開く処理（連鎖と整合の検査）は成功する | 互換 |
| 読み取り専用の状態の確認 | `profile` を書き足せば成功する | 互換 |
| Recovery | `profile` を書き足せば、`recover all` で承認待ちの Run を FAILED で終えられる。保存された Policy と RunGrant の本文とハッシュは変わらない | 互換（A.I12 のとおり、承認待ちは再開しない） |
| 保存済みの Policy（`trusted_synthetic_tasks` なし） | 新しい Run を始めると、保存された Policy の読み込みが型の検査で失敗し、`INTERNAL_ERROR`（`ValidationError`、終了の符号 5）になる | **安全側（何も実行されず、新しい Run のグラントは入らず、費用もない）だが、型の付いた拒否ではない。** さらに、CLI の `start` が Task と Run をグラントの前に作るため、**グラントのない RUNNING の Run が残る**（`recover all` で FAILED にでき、復旧不能ではない） |
| 保存済みの RunGrant（`synthetic_task_ref` なし） | 以前の Run の再判定は、Run が承認待ちのまま再開しない（A.I12）ため、この確認の範囲では読まれなかった。読まれれば型の検査で失敗する見込み（未確認） | 安全側の見込み（未確認） |
| ハッシュと承認の整合 | 以前の承認待ちの操作の承認は `APPROVAL_TARGET_MISMATCH`（以前のセッションの承認待ちは引き継がない、A.I12）。保存された Policy と RunGrant のハッシュは書き換えていない | 互換（安全側） |

### 8.3 修正の案（**今回は製品のコードを変えない**）

1. 保存された Policy と RunGrant の読み込みの型の失敗を、`INTERNAL_ERROR` ではなく型の付いた拒否（例：`POLICY_FORMAT_OUTDATED`）にし、何をすればよいかを CLI に出す。
2. CLI の `start` で、グラントの登録を Task と Run の作成の前に確かめる（または同じ流れで失敗したら作った Run を直ちに終える）。グラントのない Run を残さない。これは P-6 の前からある順序の問題で、以前の版のデータで表に出た。
3. 以前の版のホームの扱い：Phase 1 は合成のデータだけなので、移行の道具は作らず、新しいホームで始め直すことを既定にする。以前のホームの状態の確認と復旧が要る場合は、オーナーが設定に `profile` を書き足す手順を文書にする（記録の書き換え、削除、再署名はしない）。
4. ポリシーの更新：以前の Journal で新しい Run を始めたい場合は、オーナーが新しい形のポリシー（新しい `policy_version`）を入れる。古いグラントはそのまま残る。
