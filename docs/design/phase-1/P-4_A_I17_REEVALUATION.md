## 2. 常時の監視の必要性

**結論：Phase 2 では必要。** 理由：

1. Phase 2 では Sandbox の中でシェルを実行する（信頼しないコード）。止まらない処理、応答しない子プロセス、資源を使い続ける処理を、オーナーの操作を待たずに止める必要がある。
2. 明示的な `recover` だけでは、オーナーがいないあいだ、CANCELLING・RECOVERING の Run と、その保留が期限を過ぎても残る（安全側ではあるが、停止の意図が実際の停止に結び付かない）。
3. 停止の操作（`stop`）の後、Sandbox の中の処理が実際に止まったことを確かめる主体が要る（C1.S22・S26）。

ただし、監視の権限は狭く保つ（4.2）。

## 4. 採用案 A の設計

### 4.1 周期と期限（提案の値。承認と計測が要る）

| 項目 | 提案 | 理由 |
|---|---|---|
| Sandbox の実行の上限 | Attempt ごとの壁時計の上限（例：既定 300 秒、ツールのマニフェストで狭めるだけ）を、コンテナの側で強制（D 案）し、監視の側でも検査 | 二重にすることで、P1 の遅れや異常に依らない |
| 監視の周期（Sandbox） | 1 秒 | 停止の遅れを小さくする。検査は読み取りだけで軽い |
| 監視の周期（Run の期限） | 10 秒 | CANCELLING・RECOVERING の期限は分の単位で、細かい周期は要らない |
| CANCELLING の期限 | 60 秒（Sandbox の停止の猶予を含む） | 停止の要求から実際の停止までの上限 |
| RECOVERING の期限 | 600 秒（今の試験の値と同じ） | 照合に必要な時間。過ぎたら RECONCILIATION_REQUIRED |
| 停止の猶予 | SIGTERM から SIGKILL まで 10 秒 | 子プロセスに後片付けの時間を与えるが、無期限にしない |

### 4.2 監視の責任の範囲

- **行うこと：** 期限の検査（台帳の high-water の時刻と `run_status_times` で）。期限を過ぎた Run の昇格（RECONCILIATION_REQUIRED、今の `escalated` と同じ遷移）。Sandbox の実行の停止の要求と、停止の確認。異常終了の後のコンテナと一時データの回収の要求（C1.S26）。監視自身の状態の記録（監査）。
- **行わないこと：** 承認、Permit の発行、保留の解放、結果の確定（照合）、Run と Task の完了、作業の再実行、ポリシーとグラントの変更。これらは今の経路（オーナー、ゲート、照合）だけが行う。
- 監視の処理の失敗は、安全側に閉じる：監視を止め、Runtime を再読み込みが要る状態にし、新しい Permit を出さない（停止の扱い）。

### 4.3 タイムアウトと異常終了の状態の対応（Phase 2 の Sandbox）

| 出来事 | Sandbox の中の実行 | Attempt の状態 | 費用の保留 |
|---|---|---|---|
| 正常に終わり、結果を検証できた | 完了 | COMPLETED（今のゲートの報告の経路） | 確定 |
| 実行の前に止めた（開始の記録の前） | 起動していない | ABORTED_BEFORE_DISPATCH（今の未実行の証明） | 解放 |
| 実行中のタイムアウト、停止、異常終了で、結果が分からない | 止めた | **OUTCOME_UNKNOWN**（失敗とみなさない、再実行しない） | **保留を維持** |
| 実行中の異常終了で、Sandbox の写しの外への効果がないと証明できる | 止めた | FAILED_DEFINITE（証明の条件はホストへの反映の前であること。C1.S19 の、検査を通った後だけの反映） | 確定（実際の費用） |
| ホストへの反映の最中の異常終了 | — | OUTCOME_UNKNOWN（反映は1つの単位として扱う） | 保留を維持 |

- 子プロセスは Sandbox の中だけで起動する。P1 はホストで子プロセスを起動しない。Sandbox を操作するのは、Docker の API を持つ P2 だけ（C1.S24）。Phase 1 の import の契約（プロセスを起動しない）は、Phase 2 で Sandbox の接続口に限って緩める必要があり、**オーナーの承認が要る**。

### 4.4 時計の逆行と再起動

- 期限は台帳の時計（high-water）で決め、壁時計が戻っても延びない（今と同じ）。
- 監視の中のタイマーは単調な時計。再起動の後は、記録（`run_status_times`、Attempt の開始の位置）から期限を計算し直し、0 から数え直さない。
- 再起動の前の Sandbox の実行は、再起動の後に結果を確かめられなければ OUTCOME_UNKNOWN とし、残ったコンテナを回収する。

### 4.5 既存の Runtime、Journal、台帳との接続

- 監視は `RuntimeStateMachine` の命令の排他（`_command_lock`、再入の拒否）を使い、命令と同時に状態を変えない。
- 昇格は `runtime/recovery.py` の既存の関数（期限の判定、`_set_run`）と同じ遷移で記録する。新しい遷移は作らない。
- Sandbox の停止は、新しい接続口（例：`SandboxPort.stop(attempt_id, grace_ms)`、`SandboxPort.status(...)`）を通す。Phase 3A で Process Supervisor の実装に差し替える。
- 費用は台帳の既存の操作（`MarkUnknown`、`ReconcileOutcome`）だけで扱う。

## 5. 受入の試験（Phase 2 で、信頼しないコードを実行する前に合格が必要）

1. 期限を過ぎた CANCELLING・RECOVERING の Run が、監視の1周期の中で RECONCILIATION_REQUIRED になる（オーナーの操作なし）。
2. 監視は、承認、保留の解放、結果の確定、完了、再実行を行わない（各操作の呼び出しがないことと、台帳が変わらないこと）。
3. 実行の上限を過ぎた Sandbox の処理が、停止の猶予の後に必ず止まる（SIGTERM を無視する処理を含む）。
4. 停止の操作の後、新しい Permit が出ず、Sandbox の中の処理が止まり、Attempt は OUTCOME_UNKNOWN になり、保留が残る。
5. 子プロセスのタイムアウトと異常終了は、結果が分からなければ OUTCOME_UNKNOWN で、再実行されない。
6. 時計を戻しても、監視を再起動しても、期限は延びない。
7. 監視の処理が異常終了しても、Journal と台帳の状態は変わらず、新しい Permit は出ない。
8. P1 を SIGKILL しても、コンテナの側の強制のタイムアウトで Sandbox の処理が止まる。
9. 再起動の後、残ったコンテナと一時データが回収される。
10. 自己診断に失敗した Sandbox では、コードが1行も実行されない（C1.S10）。

## 6. Phase 2 で信頼しないコードを実行する前に必要な安全の条件

- Docker の Sandbox の基本の設定（C1.S9）と、自己診断の失敗での拒否（C1.S10）。ネットワークの隔離（`--network none`）と自己診断（ROADMAP 0.2）。
- 5章の受入の試験の合格。
- Sandbox へのコピーとホストへの反映（C1.S18、S19 の Sandbox の部分）。
- Docker の API を P2 だけが持つこと（C1.S24 の該当する部分）。
- 資源の上限の OS による強制と、監視による停止の区別の記録（C1.S26）。
- 3A の OS のレベルの隔離の強化を待つことを理由に、隔離のないコードを実行しない。

## 7. 保守性

- 監視は小さな1つのモジュールにし、責任は 4.2 に限る。状態は持たず、毎回、記録から計算する（再起動に強い）。
- 時計と Sandbox は接続口で受け取り、試験では手動の時計と偽の Sandbox で決定的に試す。
- Phase 3A の Process Supervisor への置き換えは、`SandboxPort` の実装の差し替えで行う。
