## 5. 残る原因と実用上の影響（承認の範囲の外。報告のみ）

**許可の全経路の追記は、まだ件数とともに増える。** 2章の追記の基準は、登録した方法（Step の作成と終わりだけ）で満たした。一方、C の生成の中の全経路の追記は、件数とともに増える。全経路とは、予約、Permit、受領、開始、終わり、使用量の報告を含む経路のこと。

- 生成の最後の 1割の1件あたり：1万件で 2.0 ms、5万件で 3.1 ms、10万件で 4.6 ms。生成の時間は参考の値。
- プロファイルで原因を確かめた（参考の時間）：5万件で、Attempt の操作ごとに `sqlite_ledger._totals` が広い予算の範囲の予約の行を**すべて** Python で合計する（`cost.rules.checked_sum`、`fetchall`）。広い範囲とは、テナント、利用者、期間。プロファイルで 1.6 秒のうち、`checked_add` と `checked_sum` が約 0.9 秒。
- 予約の数に比例するので、上限の 5万件の付近で、全経路の1つの操作は 1万件のときの約 1.5 倍の時間になる。
- 実用上の影響：Phase 1 の暫定の上限（5万件）の内側では、1件あたり数ミリ秒で、運用の妨げにはならない。上限を上げる前に直すのが望ましい。
- 改善の案（承認が必要）：
  - 予算の範囲ごとの合計を、台帳の中の派生の値として持つ。
  - または SQL の集計（`SUM`）に、桁あふれの検査を加えて置き換える。
  - いずれも、合計の検査（`verify_consistency` など）で、全件の合計との一致を確かめる。

その他：
- 起動の時間の半分近くは、開く処理の検査（10万件で 12〜16 秒）である。検査の内容は変えていない。M6（解析の共有）で縮められるが、今回は許可されていない。
