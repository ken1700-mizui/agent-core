## 1. 目的と基準

- D9 の暫定の許容の基準：Journal の容量は 1 GiB か 100万件のイベントの先に達した方、起動・検証・Rebuild は 60 秒以内。
- この計測の結果で、基準の妥当性をオーナーが再評価する。計測の値は、この環境のこの手順での値であり、ほかの環境での性能の保証ではない。

## 2. 合成のデータの生成

- 道具：`tools/perf/journal_benchmark.py generate`（Agent Core の外の開発の道具。新しい依存なし）。
- 経路：実際の Runtime の経路（`RuntimeStateMachine`、`SqliteJournal`、`phase1_synthetic` のプロファイル）でイベントを書く。1つの Task と Run（4件のイベント）の後、Step を作り、開始し、取り消す（1つの Step で3件）。合成の ID と digest だけ。ファイル、モデル、ツール、ネットワークは使わない。
- 規模：1万、10万、100万件（指定の件数を超えない最大の「4 + 3 の倍数」。例：1万 → 9,997 件）。
- 制限：Step と Run の遷移のイベントだけで、Attempt、台帳の予約、Permit などは含まない。実際の利用の Journal の構成とは違う（1件あたりの大きさと、開くときの検査の量が違いうる）。

## 3. 計測の手順

1. 各規模で Journal を1回生成する（生成の時間も記録する。基準の対象ではない）。
2. 各規模で5回、生成した Journal を新しいファイルに写し、**それぞれ新しい子プロセス**で `measure` を実行する（前の計測のキャッシュをプロセスの中に残さない。OS のページキャッシュは残りうる）。
3. 1回の計測で記録するもの（単調な時計）：
   - データベースの検査（`_check_database`）、ハッシュの連鎖の検証（`_verify_tenant`）、台帳の整合の検査（`verify_consistency`）を、読み取りだけの接続で、それぞれの時間と合計（整合性の検証の時間）。
   - 通常の開く処理（`SqliteJournal.open`：上の検査のすべてと、新しい所有者の epoch）の時間（起動の時間）。
   - Runtime の状態の Rebuild（`RuntimeStateMachine.load`）の時間。
   - 起動の合計（開く処理と Rebuild）。D9 の 60 秒の基準と比べるのは、この値。
   - ファイルの容量、イベントの数、子プロセスの最大の常駐メモリ（`ru_maxrss`）。
4. 5回の中央値と最大値を記録する。
5. 小さい規模から順に行う。環境の容量や時間の制限に当たる場合は、無理に続けず「未計測」と記録する。
6. 計測が終わったら、一時ファイルを削除する。
7. 環境（CPU、メモリ、ストレージ、OS、Python、SQLite の版）を記録する。

## 7. 考察（計測の値と、その解釈を分けて書く）

**計測の値から言えること：**

- D9 の暫定の基準（起動・検証・Rebuild 60 秒以内）は、**1万件では満たし（5.7 秒）、10万件では満たさない（382.5 秒）。** 100万件と 1 GiB の基準は、60 秒の基準と両立しない（100万件の前に 60 秒を超える）。
- 整合性の検証（Journal の連鎖と台帳の検査）は、件数にほぼ比例した（1万件 1.39 秒、10万件 15.48 秒、約 11 倍）。
- Rebuild は件数の10倍で約 85 倍になり、比例より大きく増えた。生成の時間も同じ傾向（18.7 秒 → 1,014 秒、約 54 倍）。
- 容量は1件あたり約 1.6 KB で、10万件で 154 MiB。1 GiB に達する前に起動の時間の基準を超える。
- メモリは 10万件で約 744 MiB。

**原因の推定（コードを読んだ結果。計測ではない）：**

- `RuntimeState` は変更できない地図の集まりで、遷移を1つ当てるたびに、その地図を写し直す（`runtime/state_machine.py` の `_with`）。そのため、1件の当て込みの費用が実体の数に比例し、Rebuild と追記の全体が2乗に近くなる。
- この計測の作り方（1つの Run に Step を積み続ける）は、`run_steps` の組（tuple）も伸び続けるので、2乗の傾向を強める。実際の利用（Run ごとの Step が少ない）では、増え方が違いうる。

## 8. 基準の再評価の材料（オーナーの判断のため）

- 60 秒の基準を保つなら、今の実装で許せる件数は 1万件と 10万件のあいだにある（正確な境界は未計測）。
- 1 GiB と 100万件は、今の実装では起動の時間の基準と両立しない。
- Rebuild の2乗の増え方は、Snapshot（A.I6、Phase 4）の前に、Rebuild の中だけ変更できる地図で組み立てて最後に固める、などの方法で、件数に比例する形に直せる見込みがある（**実装は承認されていない。**直した後に同じ手順で計測し直す必要がある）。

## 9. P-2（上限を超えたときの新しい Run の停止と通知）の実装の提案

**今回は実装しない。** 提案：

| 項目 | 提案 |
|---|---|
| 何を数えるか | 開いたときの Journal のイベントの数、ファイルの容量、直前の起動の合計の時間（台帳に記録） |
| 上限の値 | 計測の結果から、60 秒の基準を守れる件数を、追加の計測（例：2万、5万件）で決める。決まるまでの暫定として、1万件（計測で 5.7 秒）を「警告」、件数の上限はオーナーが決める |
| 超えたとき | 新しい Run の開始を拒否する（`Session.start` と Runtime の開始の経路。安全側）。既存の Run の状態の確認、停止、照合、復旧は続けられる。CLI に固定の通知（件数、容量、上限、次の操作）を出す。Journal の削除と切り詰めはしない |
| 再起動 | 再起動の後も、上限を超えていれば拒否が続く（記録から計算する） |
| 試験 | 上限の直前と直後、再起動の後、既存の Journal が変わらないこと、通知の文言、停止と復旧の操作が使えること |
| 必要な時期 | **Phase 2 の開始の前。** Phase 2 の Benchmark Runner と評価の実行は、Phase 1 よりはるかに多くのイベントを書く見込みで、上限の対策（または Rebuild の改善）がないと、起動に数分以上かかる状態に入りうる。D9 の「上限の対策が整うまでは、管理された小規模な合成のデータの運用に限る」は、それまで続ける |
| 関連 | Rebuild の2乗の増え方の改善（8章）は P-2 とは別の変更として、オーナーの判断で扱う |
