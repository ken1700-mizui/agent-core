## 1. 何を数えるか

| 量 | 求め方 | 根拠 |
|---|---|---|
| イベントの数 | `tenant_head` の `tenant_seq` の合計（全テナント） | Journal の正本。追記のトランザクションで決まる |
| 容量 | **DB のファイルと WAL のファイルの大きさの合計**（`-shm` は数えない：データを持たない索引） | ファイルの実際の大きさ。WAL の書き戻しで WAL が縮んでも、その分 DB が増える |
| 起動の時間 | このプロセスで Journal を開いて Rebuild を終えるまでの時間（単調な時計、ミリ秒） | `shell` の `status` に表示する。保存しない（2.4 を参照） |

イベントは削除されず、DB は VACUUM しない（`auto_vacuum` は既定の無効）ので、2つの量は減らない。そのため、制限の段階は再起動の後も続く。

## 2. 段階と動作

| 段階 | 条件 | 動作 |
|---|---|---|
| 通常（`NORMAL`） | すべて警告の値の未満。制限の設定がないときは常にこれ | 制限なし |
| 警告（`WARNING`） | イベントの数か容量が警告の値以上 | 新しい作業は続けられる。`status` に段階を表示 |
| 制限（`LIMITED`） | イベントの数か容量が上限以上（新しい作業の分の見込みを足した値） | 新しい Task、新しい Run、新しい Step を `CAPACITY_LIMITED` で拒否。拒否の前に何も書かない |

### 2.1 拒否しないもの

- 既存の Attempt の終わり（完了、失敗、結果不明の記録、使用量の報告、未実行の証明）。
- 停止と取り消し（`stop`、Run の `CANCELLING`／`CANCELLED`）、Step と Run の終わりの遷移。
- 状態の確認（`status`）。
- 照合（`reconcile`）と復旧（`recover`）。
- 安全のための記録（停止の記録など）。

制限は予約（hold）を解放しない。Journal を削除も切り詰めもしない。

### 2.2 新しい作業の見込みと、開始の判断の一致

- 設定の `reserve_events` と `reserve_bytes`：新しい作業の1つが、次の判断までに増やすと見込む量。判断は「今の量 ＋ 見込み」で行う。
- 判断は Runtime の命令の排他の中（`RuntimeStateMachine` の命令の開始、何かを計画したり書いたりする前）で行うので、判断と作業の開始は同じ Journal を見る。
- CLI の `start` は、Task と Run と最初の状態の 4 件（Task、Run と Task への結び付け、`QUEUED`、`RUNNING`）を見込みに足して、**開始の全体を1回で判断する**。Task だけ作られて Run が拒否される途中の状態を作らない。
- エージェントのループの中で新しい Step が拒否されたときは、その回のループを結果 `CAPACITY_LIMITED` で終える。Run はそのまま待ち（終わらせず、ループも壊れない）、オーナーは停止できる。

### 2.3 オーナーの操作の区別（すべての操作を除外しない）

| 区分 | 操作 | 制限の段階で |
|---|---|---|
| 新しい作業の準備 | Run の権限（`InstallRunGrant`）と、Run の上限（`SetBudgetCap`、`SetCounterCap`、`SetRunWindow`、`SetStepCapDefault`） | 拒否（`CAPACITY_LIMITED`） |
| 復旧と管理 | 停止（`StopScope`）、復旧（`RecoverInFlight` など）、照合（`ReconcileOutcome` など）、既存の Attempt の承認、ポリシーと価格表の導入 | 拒否しない |

### 2.4 P-7 の7章の設計との違い

| 項目 | P-7 の設計 | 実装 | 理由 |
|---|---|---|---|
| 容量 | `page_count × page_size` | DB と WAL のファイルの大きさ | 指示に従い WAL を含むかを定義した。WAL はディスクを使うので含める |
| 上限の記録 | オーナーの署名付きの台帳の操作（`SetJournalLimits`） | ホームの `config.json` の `limits`（オーナーの鍵と同じホームのファイル） | 台帳の新しい表と操作が要らない（保存の形式を変えない）。設定の誤りは `HOME_UNSAFE` で拒否 |
| 起動の時間 | 台帳の小さな表に記録し、段階の条件にする | 表示だけ（保存せず、段階の条件にしない） | 新しい表が要る。保存する場合は台帳の形式の変更として互換性の確認が要るので、今回は行わない |

## 3. 設定

`config.json` の任意の項目 `limits`：

```json
{"limits": {"warning_events": 0, "limit_events": 0, "warning_bytes": 0, "limit_bytes": 0, "reserve_events": 0, "reserve_bytes": 0}}
```

（数値は形だけ。`0 < warning ≤ limit` でないと `HOME_UNSAFE`。）項目がないときは制限なしで、`status` は使用量だけを示す。

## 4. 推奨する値（計測に基づく。**承認はオーナー**）

`P-7_RESULTS.md` の7章（計測に基づく）：上限 50,000 件・160 MiB、警告 30,000 件・96 MiB、見込み 200 件・1 MiB。根拠は、最も重い形 C の5万件で起動 27.3 秒（最大 28.5 秒）、DB 137.8 MiB。C は10万件で 68.1 秒になり 60 秒を超える。原因（`_unused`）を直した後に計測し直して見直す。

## 6. 未検証の項目

- 起動の時間の保存と、それによる段階（2.4）。
- 複数のプロセスが同じホームを同時に使う場合（Phase 1 は OS のロックで1つだけ）。
- WAL の大きさは書き戻しの時点で変わる。上限の近くで警告と制限の間を行き来しうる（上限の値に余裕を持たせて運用する）。
