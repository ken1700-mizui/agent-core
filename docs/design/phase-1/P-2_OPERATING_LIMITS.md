## 1. 何を数えるか

| 量 | 求め方 | 根拠 |
|---|---|---|
| イベントの数 | `tenant_head` の `tenant_seq` の合計（全テナント） | Journal の正本。追記のトランザクションで決まる |
| 容量 | **DB のファイルと WAL のファイルの大きさの合計**（`-shm` は数えない：データを持たない索引） | ファイルの実際の大きさ |
| 起動の時間 | このプロセスで Journal を開いて Rebuild を終えるまでの時間（単調な時計、ミリ秒） | 開くたびに測る（4章） |

- イベントは削除されず、DB は VACUUM しない（`auto_vacuum` は既定の無効）ので、イベントの数は減らず、DB のファイルは縮まない。
- **WAL は縮みうる**（5章）。

## 2. 段階と動作

| 段階 | 条件（どれか） | 動作 |
|---|---|---|
| 通常（`NORMAL`） | すべて警告の値の未満 | 制限なし |
| 警告（`WARNING`） | イベントの数・容量・起動の時間のどれかが警告の値以上 | 新しい作業は続けられる。`status` に段階を表示 |
| 制限（`LIMITED`） | どれかが上限以上（イベントと容量は新しい作業の見込みを足した値） | 新しい Task、Run、Step、**Attempt** を `CAPACITY_LIMITED` で拒否。拒否の前に何も書かない |

### 2.1 拒否しないもの

- 既存の Attempt の終わり（完了、失敗、結果不明の記録、使用量の報告、未実行の証明）。
- 停止と取り消し（`stop`、Run の `CANCELLING`／`CANCELLED`）、Step と Run の終わりの遷移。
- 状態の確認（`status`）。
- 照合（`reconcile`）と復旧（`recover`）。
- 安全のための記録（停止の記録など）。

制限は予約（hold）を解放しない。Journal を削除も切り詰めもしない。古い記録を書き換えない。

### 2.2 新しい作業の見込みと、開始の判断

- `reserve_events`、`reserve_bytes`：新しい作業の1つが次の判断までに増やすと見込む量。判断は「今の量 ＋ 見込み」。**見込みは目安で、物理的な容量の保証ではない。**
- CLI の `start` は、Task と Run と最初の状態の 4 件を見込みに足して、**開始の全体を1回で判断する**（Task だけが作られる途中の状態を作らない）。
- 既存の Step の中の新しい作業も無制限には増えない：新しい Attempt（再試行を含む）は制限の段階で拒否する。エージェントのループの中で Attempt が拒否されたときは、その Step を終え（`CANCELLED`、何も実行していない）、その回を結果 `CAPACITY_LIMITED` で終える。Run はそのまま待つ（オーナーは停止できる）。新しい Step の拒否も同じ結果。

### 2.3 判断と書き込みの整合の保証の範囲

| 範囲 | 保証すること | 保証しないこと |
|---|---|---|
| プロセスの中の命令の排他（`RuntimeStateMachine` の命令のロック） | 判断は命令の開始（計画と書き込みの前）に行う。同じ Runtime の別の命令が、判断と書き込みの間に入らない | — |
| OS のロック（Journal を開くときに取る、1つのホームに1つの Runtime） | 別のプロセスが同じ Journal に書き込まない | — |
| DB のトランザクション | 追記そのものの原子性（イベント、head、台帳を一度に書く） | **判断の読み取りと追記は別のトランザクション**。判断の時点の量と、書き込みの時点の量の差は、見込みの範囲で吸収する前提であり、DB が上限を強制するのではない |

### 2.4 オーナーの操作の区別（すべての操作を除外しない）

| 区分 | 操作 | 制限の段階で |
|---|---|---|
| 新しい作業の準備 | Run の権限（`InstallRunGrant`）と、Run の上限（`SetBudgetCap`、`SetCounterCap`、`SetRunWindow`、`SetStepCapDefault`） | 拒否（`CAPACITY_LIMITED`） |
| 復旧と管理 | 停止（`StopScope`）、復旧（`RecoverInFlight` など）、照合（`ReconcileOutcome` など）、既存の Attempt の承認、ポリシーと価格表の導入 | 拒否しない |

### 3.2 新しいホームと既存のホーム

- **新しいホーム：** `init` が `config.json` に上の値を書く。制限なしでは始まらない。
- **既存のホーム（以前の版）：** 開くときに書き換えない（暗黙の書き換えなし）。`status` は「limits not configured」を示す。オーナーが明示的に次を実行して導入する：

```
agent-core-cli limits --home <ホーム> --apply-provisional
```

  - 制限がすでにあるホームでは `LIMITS_ALREADY_SET` で拒否する（上書きしない）。
  - `config.json` の他の項目は変えない（原子的な置き換え）。
  - 次の起動から効く。
- 設定の誤り（順序、型、片方だけの起動の時間）は `HOME_UNSAFE`。

## 4. 起動の時間の記録と再起動

- `shell` の起動ごとに、開く処理と Rebuild の時間を測る。そのセッションの段階に入れる（**60 秒以上なら、そのセッションの新しい作業を制限する**）。
- 測った値は、ホームの `startup.json`（`version`、`startup_ms`、`events`、`recorded_at_ms`）に原子的に置き換えて記録する（`owner.seq` と同じ方法：一時ファイル、fsync、名前の変更、ディレクトリの fsync）。読み取りだけの `status` は記録を表示し、その値で段階を示す。
- **再起動の後：** 起動のたびに測り直す。速く起動できれば、起動の時間による制限はそのセッションでは解ける（イベントと容量の制限は別に続く）。
- 以前のホームに `startup.json` がないのは正常（記録なし）。壊れた記録は `HOME_UNSAFE`。
- 台帳の形式は変えていない（新しい表なし）。旧形式との互換性の問題はない。

## 5. WAL の縮小と制限の解除

- 容量は「DB ＋ WAL」。WAL の書き戻し（自動では約 1,000 ページごと）で WAL のページは DB に移る。また、最後の接続が閉じるときに WAL は書き戻されて消える。そのため、**合計は WAL の大きさの分だけ減りうる**（DB のファイルは縮まない）。
- 段階は、判断のたびに今の量から決める。WAL の縮小で合計が上限の未満に戻れば、容量による制限はその時点で解ける。その幅は WAL の大きさまで（通常は数 MiB 以内。長いトランザクションの後は大きくなりうる）。
- 上限の値は、この幅と見込み（1 MiB）より十分大きくして運用する。イベントの数と起動の時間の制限は、WAL に影響されない。
